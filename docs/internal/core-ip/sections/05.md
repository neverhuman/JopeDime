# GP representation and evolution

GP means genetic programming here. Gaussian-process regression (`gpr`) is one possible fitted model head; it is not the evolutionary controller.

## Typed recipes and fitted state

An ordered pipeline recipe names transformations and a terminal predictor. Terminals include the original feature table X and grammar-restricted constants or expression references. Parsing produces a typed `GenomeIr`; `SynthesizedRecipe` preserves original bytes and records the production raw-input stage inserted into the executable recipe. That explicit adaptation is not a replacement winner.

Mutation and crossover operate on canonical recipes under the supported grammar. A mutation's child has one parent; crossover records two. Candidate identity includes arm, executable program, generation, slot, origin and parents. Duplicate executable recipes do not create independent measurements.

## Selection and stopping

The production population starts with 80 candidates. The accepted neural arm uses 64 ranked neural slots and 16 exploration slots, with explicit rejection fallback when generation cannot fill the neural slots. Four elites guide later generations; only actually measured completed parents may create eligible offspring. The study limits each arm to 96 candidate slots and 120 seconds, preserving failures and original deadlines.

A request limit differs from a count of successful candidates or physical fits. A completed five-fold candidate normally starts five production fit calls; interrupted candidates can have incomplete evidence. Counters must come from worker receipts. Unknown starts stay unknown.

## Proposal generation and ranking

Accepted proposals are generated under grammar constraints, and the neural pool is the first 64 distinct valid programs in draw order; any shortfall after the bounded sampling rounds is filled with distinct grammar-uniform programs labelled `neural_rejection_fallback`. Ranking orders that pool by the mean of four reward heads, descending; exact ties use program SHA256 then text. Runtime estimates are reported without subtracting an undocumented runtime penalty. Ranking binds the checkpoint, context and vocabulary and records that scoring labels and fitted GP scores were not read. It does not select or reject programs: all 64 ranked programs and the 16 exploration programs enter generation zero. Sources: `crates/jope-policy/src/ranking.rs:22`; `crates/jope-policy/src/decode.rs:9-11`, `:212-225`, `:359`; `crates/jope-policy/src/seeds.rs:257-270`.

Each ranked policy-pool program carries `rank_log_weight`, the log-softmax of its four-head mean predicted reward over that pool. Historical files called this `policy_logprob`. It is a within-context ranking weight, not a sampling/selection probability or propensity; do not use it for importance weighting or off-policy correction. Exploration candidates carry no rank weight.

The four reward heads read a masked mean of the program's token embeddings, with no position information (`crates/jope-policy/src/model.rs:555-567`). Within one context, two programs with the same token multiset therefore receive the same rewards in exact arithmetic, so their relative order carries no learned signal; an exact tie falls to the program-hash tie-break. This does not remove token order from the autoregressive proposal decoder ([historical manual section](https://github.com/veox-ai/JopeDime/blob/bcf2e6798aa753d4fda2cb15f967415d21cde3d6/docs/internal/asm-manual/sections/learning.md#distinguish-routing-ranking-and-search-recovery)). The owner's rule for this limitation (status: proposed): first measure how often such collisions occur and the ranking regret they cause, and defer architecture changes, including adopting an order-aware reward input, so that the first causal training experiment keeps architecture, objective, corpus and sampler changes distinguishable.

## Paired arms, generation zero and evolution

ASM compares a 64-slot policy pool plus 16 exploration generation-zero slots with 80 generic slots. The pool retains `neural_policy` versus `neural_rejection_fallback` origins explicitly. Both arms receive the same declared search and fit allowances, but encoding and proposal work consume the neural arm's own clock; fitting time can differ. A producer refusal, duplicate or failed candidate is an outcome to record. It cannot silently become another neural success or a free replacement arm. Actual inner-fold fits determine selection and offspring ancestry. A model's predicted reward never substitutes for measured loss.

Each arm starts with 80 generation-zero slots. In the neural arm, slots 0–63 form the ranked policy pool: distinct valid checkpoint samples are labelled `neural_policy`; any shortfall after the bounded sampling rounds is filled by distinct grammar-uniform programs labelled `neural_rejection_fallback`. Slots 64–79 are `random_exploration`. Only `neural_policy` roots and completed descendants with verified neural ancestry count as genuine neural evidence; fallback and exploration roots do not. In the origin proof at source `68f56404` all 64 pool slots were `neural_policy`, 48 completed all five inner folds, and no fallback slots were needed. Receipts retain initial-slot origin and descendant ancestry. Actual completed inner OOF losses select the best four parents. New generations alternate mutation and crossover attempts, canonicalize recipes, reject duplicate executable identities, and retain variation attempts in the journal. Source: `crates/jope-pipeline/src/neural_search.rs:27`, `:1380`.

Neither arm is seeded from the other, but at `a75e543d2` only the neural arm's initial population is authenticated against its producer. The neural arm's 80 generation-zero slots come only from the verified policy-producer artifact: the controller verifies the artifact against the worker request, requires exactly 80 slots and refuses any slot whose declared origin does not match its position (`crates/jope-pipeline/src/neural_search.rs:1066-1102`), and report recomputation replays that producer output against every generation-zero genome, origin and rank weight (`crates/jope-bench/src/panel/asm_campaign.rs:516-597`). The generic arm draws its 80 distinct candidates in process from its own grammar stream, seeded by the plan's `random_seed` (`neural_search.rs:1147-1176`). Resume and report replay check that population's slot count, `generic` origins and empty parents, but do not re-derive it from that stream: a resumed generic arm reloads its saved initial candidates (`neural_search.rs:1136-1146`), and the population check, by its own contract, does not authenticate proposal origins (`neural_search.rs:422-424`). Generation zero reads no candidate discovered by the other arm. Historical final searches differed: their arms shared incumbent, retained-teacher and exploration seed pools, and shared incumbents can create many ties ([historical manual section](https://github.com/veox-ai/JopeDime/blob/bcf2e6798aa753d4fda2cb15f967415d21cde3d6/docs/internal/asm-manual/sections/learning.md#distinguish-routing-ranking-and-search-recovery)). The owner's rule for future seeding (status: proposed; not yet met for the generic arm): initial populations must be authenticated, and a discovery cannot silently seed another arm. This manual proposes declaring any incumbent, retained teacher or another arm's discovery as an authenticated origin in the plan before execution.

## Dense-width refusals and the proposed feasibility preflight

At `a75e543d2` the 512-column cap applies to generated dense width, not to total schema or raw input width (`MAX_GENERATED_DENSE_WIDTH`, `crates/feat-math/src/advanced_v3/feature_block.rs:6`, `:107-110`). No check runs before launch: the recipe validation that precedes fitting checks task, schema, syntax and stage admissibility but does not predict generated widths, so an over-wide recipe fails inside a launched fit. In the origin proof those refusals were 130 failed commands from 26 recipes, including 16 of 64 `neural_policy` generation-zero candidates ([historical manual section](https://github.com/veox-ai/JopeDime/blob/bcf2e6798aa753d4fda2cb15f967415d21cde3d6/docs/internal/asm-manual/sections/status.md#failures-dense-width-refusals-and-the-earlier-failed-reproducer)).

A pre-launch dense-width feasibility check is **proposed**; nothing below is implemented. The owner's requirements (relayed 2026-09-23T22:27:11Z) and Codex's read-only source investigation (`plan-execution-20260923/feasibility-phase-accounting.md`, SHA-256 `0154e6b0…`) bound it:

- **Permitted fitting information only.** The check may read each inner fold's task, exact schema, class order and training-side fitting rows, never prediction rows or validation labels. One-hot and hybrid categorical widths depend on the fitting-side category layout, which the compiler deliberately refuses to guess; an undecidable case stays unknown and goes to the actual worker rather than being rejected.
- **Unchanged limits and clocks.** A rejected candidate keeps its slot, origin and ancestry, counts against the arm's evaluation allowance and earns no replacement draw. The check runs inside the existing arm allowance.
- **Separate reporting.** A preflight rejection is reported separately from a launched fit failure, with its own receipt and zero physical fit starts.
- **No unlimited free retries.** Resume neither retries a proven rejection nor changes the deadline.

The accounting hazard is specific. `PoolBackend::evaluate` records every job-preparation error as `Unavailable`, with zero physical fit starts and `retryable_inventory: true` (`crates/jope-pipeline/src/neural_search.rs:1608-1624`). A naive preflight that returned an error from job preparation would therefore mark a deterministically infeasible recipe as retryable and could repeat preflight work on resume. The investigation instead proposes a typed terminal outcome with accounting: all five folds are checked before any fold of the candidate launches, and the candidate keeps one observation with zero physical fit starts, no worker receipt, no out-of-fold loss and `retryable_inventory: false`. Recovery then verifies the retained preflight receipt without fitting. The closest existing precedent is the zero-fit terminal record for canonical duplicates (`evaluate_unique`, `neural_search.rs:884-925`).

### Generic and ASM demonstration commands

The pending generic demo fits one task-compatible registered recipe, saves complete private state, reloads it, verifies unchanged predictions and compares against a train-mean or train-prior baseline. It uses one CPU/worker, 2 GiB total, zero swap/GPU, 30 seconds per fit and 60 seconds total with five seconds reserved for reporting. Its synthetic mode is explicitly labelled; it is not evidence from a real panel dataset.

```sh
"$J" demo --dataset "$DATASET_ID" --manifest "$M" --datasets "$D" \
  --source-sha "$S" --output "$A/demo-real"
"$J" demo --synthetic multiclass --source-sha "$S" \
  --output "$A/demo-synthetic" --export python
```

The authenticated ASM route consumes a separately prepared single-regression proof plan:

```sh
"$J" demo --asm-plan "$WARM_PLAN" --asm-plan-sha256 "$WARM_PLAN_ID" \
  --manifest "$M" --datasets "$D" --output "$A/demo-asm" \
  --export python --export rust
```

### The under-sixty-second target and historical timing

The warm-target add-on treats under 60 seconds as a declared, measured goal, not a promise and not a cap that prevents a required real fitted demonstration. Both complete equal arm allowances must fit within the declared original execution window. Unequal, missing or globally clipped arms fail the matched-comparison condition. An explicitly admitted longer allowance can produce a successful complete execution with `target_met: false`; it cannot claim under-60 acceptance. It does not change the official panel's 120-second arm defaults.

The retained proof at source `3fd7d5b2` started the policy about 22.1 seconds into its original window, spent about 20.8 seconds in policy production and started the first fit around 50.4 seconds. Those are historical measurements, not a forecast or a proof that equal 20-second warm arms work. A suggested longer configuration is a sizing proposal until explicitly admitted. Neither a generic substitute nor clipping the second arm solves this requirement.

## Detailed evolutionary procedure: the bounded GP search

`neural_search.rs` runs two arms under the same declared budgets:

- the **neural** arm: 64 policy programs plus 16 exploration programs;
- the **generic** arm: 80 grammar samples.

Constants: `INITIAL_SIZE` = 80, `NEURAL_SLOTS` = 64, `ELITES` = 4 (`neural_search.rs:28-30`).

1. Every canonically distinct candidate is submitted for a real fit on the five inner folds under the execution pool's resource limits (at most 20 workers, 1 thread each, cgroup memory limits; `experiment.rs:58-97`). A canonical duplicate is recorded as failed without a second fit (`neural_search.rs:1192-1233`). A failed or deadline-cut fit gets no loss.
2. Its **selection loss** is the unweighted mean of its five inner-fold losses (`crates/jope-bench/src/panel/optimize_fit.rs:252`).
3. The four best by that loss are the parents.
4. Children alternate between mutation and crossover by attempt parity, and are deduplicated by canonical executable hash. A generation has up to 76 children: `min(76, max_evaluations − observed)` (`neural_search.rs:1718-1719`). The origin proof's cap of 96 allowed one wave of 16.
5. The arm normally stops at its evaluation limit or its original deadline, whichever comes first. It can also stop with `no_measured_parent` or `search_space_exhausted`, or in a resumable cancellation or admission-pending state (`neural_search.rs:1633`, `:1694`, `:1715`, `:1769`).
6. The winner is the minimum selection loss, with ties broken by program SHA-256 (`neural_search.rs:653-667`). It is frozen before any held-fold fit.

In the retained origin proof on `230_machine_cpu` (journal `68f56404`):

| | Neural arm | Generic arm |
|---|---|---|
| Completed candidates | 77 (62 in generation 0) | 89 (76 in generation 0) |
| Stop reason | original deadline | evaluation limit |
| Winner | generation 1, crossover | generation 1, mutation |

The neural winner descends from exploration candidates, not from a `neural_policy` proposal ([historical manual section](https://github.com/veox-ai/JopeDime/blob/bcf2e6798aa753d4fda2cb15f967415d21cde3d6/docs/internal/asm-manual/sections/status.md#canonical-proof-record-and-per-arm-facts)).

## Historical refit boundary: refit, the held fold and code emission

Each arm's winner is refitted on all 135 fitting rows and scored once on the 34 held rows (`asm_campaign.rs:197-250`). The refit sees the held rows' features only, and scoring happens in the parent process (`campaign.rs:279-289, :617`).

The legacy emitters (`crates/jope-pipeline/src/emit.rs`) write Python and Rust, and C++17, C++20 and JavaScript where their coverage gates admit the recipe. The emitted program contains `fit` and `predict` and refits from a training CSV at run time.

**They cannot emit an executable ASM recipe.** Every ASM recipe carries an inserted `(input …)` stage (`crates/jope-pipeline/src/synthesized_recipe.rs:34-47`), and the legacy planner rejects that stage (`crates/feat-math/src/spec.rs:383-389`, `:592`). A separate allowlisted fitted-state path is implemented in `fitted_export.rs` and `fitted_export_run.rs`, including synthesized worker artifacts through `FittedInferenceView::synthesized`. It packages supported saved state and qualifies emitted predictions; it does not make the legacy planner accept synthesized ASM recipes or establish general ASM-winner coverage. The historical deployment requirements are retained in [historical manual section](https://github.com/veox-ai/JopeDime/blob/bcf2e6798aa753d4fda2cb15f967415d21cde3d6/docs/internal/asm-manual/sections/inference.md#deployment-support-definition-priority-and-status).
