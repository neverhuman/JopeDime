### Timing boundaries

The headline is the actual whole request through all attempted backends. Python, Rust and C++ milestones are cumulative because those backends execute sequentially; they are not independent per-language E2E timings. Source-ready is a separate milestone.

#### Prediction path

Ten in-process API observations are reported separately from process wall time. The residual includes initialization, input parsing, printing and teardown; it is not claimed to isolate process startup alone. Rust's public API includes return serialization. Cold direct observations include process and model initialization individually, not as a warm percentile.

## Failure, protocol deviation and correction

The single admitted execution began **2026-09-25T19:11:34.939Z**, with its original deadline **20:11:34.939Z**. The controller stopped in **428ms of systemd service runtime**, with **294ms total CPU** and **`131.9M` service peak memory as printed by systemd**. These are controller failure diagnostics, not model memory or data-to-prediction latency. The parent command originally exited0 because the supervisor launch succeeded; retained `launch.json` records the actual child exit1. The corrected command now propagates an unsuccessful controller outcome.

The immediate failure was a receipt ownership collision: `ExecutionPool::admit` had already written `window.json`, and the timing adapter attempted to write a different schema to the same immutable path. The write guard correctly refused. CUDA model loading and numerical qualification never began; all direct, GP and prediction attempts remained unexecuted. The source correction writes `timing-window.json` separately. A regression test preserves the exact original admission bytes, accepts an identical resumed timing receipt and rejects a moved deadline. This is local proof of the correction, not a successful rerun.

**Staging violated the stricter input-access boundary.** The original planner called `load_development`, which parsed development labels including outer cut0, then selected only fitting rows. The paired-plan helper also constructed an outer hold partition. No sealed target table was opened, no outer score was computed and no campaign held look was consumed; nevertheless, parsing those outer labels did not comply with the requested do-not-open constraint. The original study must not be described as fully protocol-compliant.

The corrected planner accepts pre-existing pinned fitting-only projections and label-free split assignments. It checks the exact ten dataset IDs, panel and configuration identities, feature order/types, fitting membership, original target hashes, five group-aware inner folds and their complete values/labels. It never opens development or sealed target tables. The retained projection remains historically derived by the original flawed staging path; the new validation does not erase that history.

No new window was started after either finding. There is no qualified warm/cold latency distribution, stage-cost plot, full-GP time, prediction throughput or measured GPU memory result to publish. The full runner was restored and the GPU reservation released.
