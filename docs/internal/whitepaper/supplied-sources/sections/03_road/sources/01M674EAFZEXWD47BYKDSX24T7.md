# 3. The Road to Zero: Learning from Discovery

The ingredients for learned invention have developed along five connected paths: representation learning, program discovery, reinforcement learning, scientific games, and automated research. Together, they connect the four functions of innovation: defining a challenge, proposing a solution, testing its value, and learning from the outcome. Their convergence makes a consequential possibility testable: experience accumulated across problems may make the first algorithm proposed for an unseen problem competitive. EurekaZero investigates this possibility under a specific deployment contract—one complete algorithm proposal, without target-time experimental revision, candidate selection, or policy updates.

## 3.1 Deep learning makes problems and programs representable

Deep learning expanded what a machine could learn to recognize and produce. AlexNet demonstrated the strength of learned visual representations at ImageNet scale; the Transformer supplied an attention-based architecture for mapping between sequences. Codex demonstrated conditional generation of executable code, with functional correctness assessed by tests. These developments make a problem-to-program mapping a practical modeling target. Their significance is representational: a learned system can produce structured computational artifacts from context. Whether an artifact improves on an incumbent remains a question for evaluation. [[1]](https://proceedings.neurips.cc/paper_files/paper/2012/file/c399862d3b9d6b76c8436e924a68c45b-Paper.pdf) [[2]](https://proceedings.neurips.cc/paper_files/paper/2017/file/3f5ee243547dee91fbd053c1c4a845aa-Paper.pdf) [[3]](https://arxiv.org/abs/2107.03374)

Representations also let learning connect different kinds of object. CLIP learned which image–text pairs match, enabling transfer to visual categories specified in language. For algorithm discovery, the corresponding opportunity is to represent a problem's relevant properties and an admissible solution. A shared embedding space is one possible design, rather than a requirement imposed by this analogy. What matters is an expressive interface through which the problem can influence the proposed program. Experimental feedback then provides a direct signal for improving the usefulness of that mapping. [[4]](https://proceedings.mlr.press/v139/radford21a.html)

## 3.2 Program discovery closes the proposal–test loop

Machine invention predates language models. Genetic programming evolves executable programs through variation and fitness-based selection. AutoML-Zero applied this approach to learning algorithms assembled from elementary mathematical operations. These systems establish a crucial principle: a designer can specify a space of possible programs and a performance criterion without prescribing the successful algorithm. The evaluator makes unfamiliar compositions eligible to succeed. [[5]](https://mitpress.mit.edu/9780262111706/genetic-programming/) [[6]](https://proceedings.mlr.press/v119/real20a.html)

Language models strengthen the proposer inside this loop. FunSearch combined a pretrained code model, a program database, and an evaluator to discover mathematical constructions and bin-packing heuristics. AlphaEvolve extended evaluator-guided program evolution to broader algorithmic and computing problems. These systems provide concrete evidence that learned proposals and external evaluation can jointly produce useful advances. [[7]](https://www.nature.com/articles/s41586-023-06924-6) [[8]](https://arxiv.org/abs/2506.13131)

Retention already takes several forms. DreamCoder learns reusable program abstractions and a neural guide for subsequent synthesis. A database can also improve proposals by changing the examples supplied to a frozen model. The important distinction is therefore between discovering an artifact, improving a reusable proposal mechanism, and demonstrating that mechanism's quality on its first attempt. A discovered general algorithm can itself be reused without rerunning discovery. EurekaZero concerns the additional possibility of transferring discovery experience into the generation of algorithms for new problems. [[9]](https://doi.org/10.1145/3453483.3454080) [[7]](https://www.nature.com/articles/s41586-023-06924-6)

## 3.3 Reinforcement learning turns outcomes into proposal skill

Reinforcement learning makes behavior responsive to the consequences of actions. Exploration supplies experience, reward identifies desirable outcomes, and policy improvement changes the learned rule for choosing actions. AlphaGo Zero coupled these elements: self-play generated games, tree search improved move selection, and the network learned from search policies and game outcomes. Expert iteration makes the relationship explicit: a stronger search procedure teaches a policy, whose improvements then help subsequent search. [[10]](https://www.nature.com/articles/nature24270) [[11]](https://arxiv.org/abs/1705.08439)

The important result is that part of the work done by search can become reusable skill. AlphaGo Zero separately evaluated a strong raw-network player without tree search, although its strongest system remained search-assisted. The lesson is a mechanism for retaining the benefits of expensive exploration. For EurekaZero, the analogous hypothesis is that training-time evaluations can improve the first complete algorithm proposed for an unseen problem. Search generates experience; learning makes some of its value available before the next experiment. [[10]](https://www.nature.com/articles/nature24270/figures/6)

## 3.4 Games make scientific judgment operational

A useful game translates a goal into permitted actions and informative feedback. Foldit showed that such an interface could organize human scientific work: players produced models that enabled the determination of a retroviral protease structure. The value of the interface came from connecting exploration to evidence that mattered outside the game. [[12]](https://www.nature.com/articles/nsmb.2119)

Algorithm discovery already has explicit game formulations. AlphaTensor casts matrix multiplication discovery as TensorGame and trains an agent across multiple tensor sizes. AlphaDev casts instruction-level algorithm construction as AssemblyGame. These precedents supply both the game idea and evidence of learning within algorithm spaces. Its shared policy transfers decomposition techniques across tensor sizes, illustrating how an algorithm game can encompass a family of tasks. [[13]](https://www.nature.com/articles/s41586-022-05172-4) [[14]](https://www.nature.com/articles/s41586-023-06004-9)

The next step is to specify the distribution of problems a player encounters and the conditions under which its proposals are judged. For EurekaZero, the problem description, admissible program, evaluator, and incumbent provide that interface. Empirical algorithm scores depend on data, resources, and measurement uncertainty; the referee must account for them. A well-defined game turns these judgments into a repeatable source of learning, while independent evaluation tests whether the learned behavior remains useful beyond its training experience.

## 3.5 Automated research brings the improvement loop inward

Automated research can target the system that performs the research. The Darwin Gödel Machine explores changes to an agent's own code, evaluates the resulting agents, and retains an archive from which further changes can develop. Recursive describes its Eureka Machine as pursuing research branches, validating experiments, retaining context, and combining promising results. Parallel experimentation and retained experience can therefore complement learned proposal policies. [[15]](https://arxiv.org/abs/2505.22954) [[16]](https://recursive.com/updates/first-steps-toward-automated-ai-research)

Recent work also learns directly from the discovery process. Evolution Fine-Tuning trains on evolutionary trajectories across optimization tasks and evaluates generalization to held-out tasks, with search still used in its main evaluation. TTT-Discover instead updates model weights through reinforcement learning on the particular test problem. DiscoRL takes a third route, learning an RL update rule that transfers to unseen environments. These approaches place experience in different locations: a reusable proposer, a problem-specific proposer, or the learning rule itself. [[17]](https://arxiv.org/abs/2606.29082) [[18]](https://arxiv.org/abs/2601.16175) [[19]](https://www.nature.com/articles/s41586-025-09761-x)

Recursive improvement requires a further distinction. Discovering a better external algorithm improves an artifact. Improving a component of the discovery system changes the machinery. Improving the efficiency of subsequent discovery changes the process's ability to improve itself. The last claim requires evidence across generations: more independently validated progress under comparable resource budgets and challenges. A stronger proposal policy could contribute to that process; demonstrating compounding improvement requires measuring the feedback into future discovery.

## 3.6 The remaining question is competitive first-proposal quality

Table 3 separates the output of discovery from the machinery that accumulates experience. Fast deployment alone is not the distinction: TabPFN already learns a reusable prediction algorithm across datasets. EurekaZero investigates the combination of problem-conditioned algorithm generation, discovery experience transferred across problems, and one complete proposal without target-time experimental revision. The emitted algorithm may require ordinary fitting; generating it may require many autoregressive steps. The candidate budget counts complete algorithm proposals, rather than token steps or neural forward passes. [[20]](https://www.nature.com/articles/s41586-024-08328-6)

These developments make learned invention technically plausible. Representation learning supplies an interface, program discovery supplies evaluable moves, and reinforcement learning supplies a mechanism for changing future proposals. Games organize the feedback; automated research brings the loop to increasingly consequential components. An experiment can leave behind both an algorithm and a better ability to propose the next one. EurekaZero asks whether that second legacy can make the first proposal competitive on an unseen problem. To build that player, we first make invention a game.
