# Precision addendum — 2026-09-11

Smaller numeric types are useful only where they preserve the decision being made and reduce a measured bottleneck. Production neural training already uses BF16 autocast with FP32 master parameters, optimizer moments, gradient reduction and important loss arithmetic. The most plausible new experiments are selective FP32 screening for CPU fits, lossless compact data layout, and calibrated lower-precision neural inference. None is an authorized replacement for current exact f64 fit evidence.

This addendum reads source, existing telemetry and `/proc` metadata only. No benchmark, fit, model loading or GPU work was started. Original hardware/runtime observations are retained in [learning-precision-hardware.json](learning-precision-hardware.json) and [learning-gpu-models.json](learning-gpu-models.json). The underlying learning audit remains [learning-hpc.md](learning-hpc.md).

## Existing precision and actual hardware

Native-v3 [runtime.cpp:38](evidence/learning-native-v3/runtime.cpp#L38) explicitly sets CUDA autocast to BF16 and clears cached casts at the outer scope exit. Native-v3 [training.rs:790](evidence/learning-native-v3/training.rs#L790) enters that scope for each forward pass, exits before backward, and keeps FP32 gradients. The C++ NCCL wrapper requires contiguous FP32 tensors and sums them in FP32 ([runtime.cpp:28](evidence/learning-native-v3/runtime.cpp#L28)). AdamW's parameters, first/second moments and updates remain FP32. Its learning rate, decay and continuation semantics must not change inside a precision trial. The program identifiers are already compact signed-16-bit storage interpreted as unsigned IDs after gathering; the 401-token vocabulary does not fit arbitrary IDs into uint8.

Autocast does not mean every operation is BF16. Source explicitly casts loss softmax/log-softmax, ranking, runtime loss and pooling/reduction operands to FP32; backend kernels may make further choices. No explicit TF32 switch was found in the inspected native wrapper, so its actual enabled/default state is **unverified**. Record the deployed LibTorch/CUDA version and relevant GEMM/SDPA reduction flags in the proposed precision manifest; current library defaults must not be projected onto the frozen release.

The remote hardware exposes **eight NVIDIA A100-SXM4-40GB GPUs** and an **AMD EPYC 7542** CPU model. The exposed CPU flags include AVX2, FMA and F16C; they do not include AVX-512, AVX512-BF16 or AMX. This is a virtualized CPU presentation, so the model name alone is insufficient for topology or performance assumptions. FP32 can hold eight values in a 256-bit SIMD vector versus four FP64 values, and uses half the element bytes. These are capacity ratios, not a measured 2× application speedup. There is no basis here for assuming CPU BF16 tensor acceleration. [Intel's ISA overview](https://www.intel.com/content/www/us/en/support/articles/000005779/processors.html) describes the 256-bit AVX/AVX2 facilities.

For an A100, NVIDIA publishes dense peaks of 9.7 TFLOP/s ordinary FP64, 19.5 FP64 Tensor Core/ordinary FP32, 156 TF32, 312 BF16/FP16 Tensor Core and 624 INT8 TOP/s. A100 40GB memory bandwidth is listed as 1,555 GB/s. These are hardware ceilings for qualifying operations, not Jope throughput. Sparsity figures are separate and must not be applied to this dense model. [NVIDIA A100 datasheet](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf.)

BF16 has FP32's exponent range but much less significand precision. TF32 is a reduced-precision Tensor Core computation mode for FP32 matrix operands, not a 19-bit storage format that automatically shrinks matrices. BF16 Tensor Core products accumulate in FP32, and A100 also has FP64 Tensor Core instructions. These facts make selective mixed precision possible; they do not guarantee identical results across implementations. [NVIDIA Ampere tuning guide](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html)

## Candidate uses and exclusions

| Representation | Plausible use | Limitation and proposed boundary |
|---|---|---|
| FP64 with contiguous layout | Existing exact fit path; reduce row-allocation/pointer overhead and reuse immutable buffers. | Preserve arithmetic/reduction order and compiler flags; demonstrate exact prediction/semantic parity. Layout alone does not prove bit identity, nor is a speedup free. |
| FP32 CPU screening | Bounded transform-heavy or batched linear-algebra screening where conditioning and ranking recall are acceptable. | Use an explicitly different precision/input-policy identity. Keep final metric accumulation and sensitive solves FP64 where needed. Lower memory traffic helps only if measured as a bottleneck. |
| BF16/FP32 neural training | Existing forward path; potentially better kernel coverage/layout without changing storage of optimizer state. | Already deployed. Switching to FP16 has no higher advertised dense A100 tensor peak and narrows exponent range; it is not an obvious next optimization. |
| TF32 selective GEMM | Candidate FP32 neural inference or well-conditioned screening GEMMs with explicit flags. | Only relevant GEMMs/convolutions accelerate; input mantissa truncation can alter solves, distances and ranking. It does not halve FP32 storage. |
| INT8 neural inference | Separately calibrated proposal/reward inference where supported kernels and batch sizes amortize quantize/dequantize overhead. | Not an AdamW training replacement or arbitrary regression-fit datatype. Freeze per-channel/scaling/calibration policy and check top-k decisions, score tails and near ties. |
| FP32/BF16 stored contexts | Potential transfer/cache reduction if staging dominates. | New context/embedding lineage unless lossless. Validate exact dimensions, provenance and the existing `3e-4` composition tolerance where applicable; passing that tolerance does not authorize replacing exact f64 predictions. |

Do not initially place GPR/KRR covariance factorization, near-singular ridge/normal-equation solves, PLS/SVD, tiny regularization, large-offset variance/centering, near-zero denominators or cancellation-prone distance formulas into BF16/TF32. Tree split thresholds, nearest-neighbor ties and near-equal GP fitness can also change under FP32/INT8 even when average prediction error is small. A faster low-precision stage may lose the best candidate before f64 sees it. This is a head-specific numerical risk assessment, not an empirical finding that every such head fails. PyTorch documents backend/reduction-order differences, ill-conditioned solvers and TF32 accuracy tradeoffs; FP64 improves many cases but does not cure conditioning. [PyTorch numerical accuracy](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html)

## Corrections to the latest chat proposal

Claude's “layout first” direction is reasonable as a hypothesis. Its stronger claim that flattening automatically stays bit-identical is unproved: SIMD reduction order, FMA contraction, alias/alignment choices or changed backend dispatch can affect arithmetic. Test the original exact fixture suite against a frozen compiler/runtime; a representation change can remain in the same computation lineage only after its required identity and parity rules permit it.

A screening fit **still needs authority, funding, an absolute deadline, a distinct complete computation identity, retained acceptance/completion evidence and a no-repeat exclusion policy**, even if it never writes a teaching observation. “No publication” is not “no governed computation.” Current precision validation accepts f64 only; a screening namespace is a proposed separately qualified extension, not an available bypass. A subsample changes the fitting problem in addition to precision, so test those axes separately before a combined multi-fidelity system. Final f64 observations remain original full-data fits, with compatible committed results reused and ambiguous originals unavailable.

The latest chat's **66 ms median candidate**, **12 ms startup**, and derived **18% startup share** do not have an identified, cohort-bound original timing receipt in this audit. They are **unverified**, not a planning denominator. Do not subtract an isolated process microbenchmark from a fit duration measured under different concurrency/cache/load. The current active context geometry from admission is median 275, p90 800, p99 819 and maximum 4,751 training rows; the chat's p90 2,790 and p99 26,880 describe another population. Profiling must join exact rows, transformed width, head, cache state, process setup, compilation, fitting, prediction and output-commit time. The retained 128-step training timings are neural-task timings and cannot establish GP process overhead.

## Proposed gated precision experiment

The first precision decision should use a frozen, deterministic **training-only** fixture manifest, selected before opening its files. Stratify by actual rows, transformed width and head, and deliberately include ill conditioning, cancellation, target scale and near-tie cases. Use retained original f64 outputs as references when available; do not rerun known or ambiguously started f64 fits. A new reference fit needs the existing authority and funding path. No protected panel is needed for this engineering stage.

Compare three separately identified conditions in sequence: **current exact f64**, **contiguous exact f64**, then **FP32 screening on the same rows and candidate programs**. Keep row subsampling and BF16/TF32 fit arithmetic out of the initial comparison. For each condition, freeze source/binary/compiler/ISA flags, dtype and accumulation choices, dataset/cut transforms, seeds, candidate list, task ceiling and output contract. Use the existing two-thread evaluator configuration with an explicitly reserved canary of at most 16 aggregate slots; the reservation sets a fixed candidate count and absolute deadline before any execution. Canonical funding is currently unavailable in the bounded check, so this remains a plan.

Suggested engineering acceptance criteria to freeze **before** the pilot, without replacing existing promotion thresholds:

- Exact-layout condition: every required exact output and semantic hash agrees; zero new failures/nonfinite results; median full-task latency improves by at least 10% with no more than 5% p95 regression on the declared fixture population. Otherwise retain the current path.
- FP32 screening: finite outputs, unchanged feature dimensions, no silent fallback or changed task denominator; at least 99% recall of the f64 reference top-10 candidates in a fixed shortlist, retaining all reference best candidates within the predefined tie tolerance. Report per-head/per-family misses and worst baseline-relative regret; any reference champion missed rejects that head for screening in the pilot.
- Useful speed: at least 1.25× reduction in **total screening plus required f64-finalist task time**, including startup/transfers, verification, failures and reconciliation. Report cold and warm cases separately. A kernel speedup alone does not pass.
- Finalists: use the unchanged full-data f64 evaluator and retained original evidence; all ordinary promotion/protected-reference gates remain intact. Screening labels never enter the strict teaching corpus as f64 evidence. The outcome is a versioned screening policy and its limitations, not a new serving model.

Only after that result should a separate neural-inference precision experiment compare existing BF16 against FP32/explicit-TF32 or calibrated INT8 on a common retained proposal pool. Freeze the model, all five loss semantics, sampler and FP32 optimizer state if training is involved; honor the already selected three-seed, batch-2,048, 1,000-new-step/300-second limits and at most 12 distinguishable funded conditions. Changes to precision semantics or calibration get a new lineage. The evidence must show useful completion or latency gains without violating the existing quality, regression or exact-finalist rules.
