# JopeDime: a learning system that invents better regression algorithms

## Final engineering specification, independent review, and research roadmap

**Date:** 17 October 2026  
**Repository:** [neverhuman/JopeDime](https://github.com/neverhuman/JopeDime)  
**Audited revision:** `5b8b8d56b4ff2458c97486c2ba6f1ebcd9a887bc`, main, commit timestamp `2026-10-17T14:05:21Z`  
**Status:** proposed engineering requirements grounded in a pinned source audit; no implementation, deployment, campaign, S3 mutation, or new performance result is claimed.  
**Deliverable:** one self-contained Markdown document. The five supplied specifications are reviewed here; their useful ideas are resolved into one design rather than appended as competing architectures.

> **Recommendation:** connect the existing measured-search, training, support-versioning, custody, and qualification machinery into one demonstrable learning cycle. Fix misleading cross-validation states first. Make successful new GP programs reachable by the next policy. Establish whether policy learning adds value beyond retrieval and archive growth. Then expand the language and search intelligence under the same evidence and resource contracts.

The most consequential opportunity is **learning the distribution of useful learning algorithms**, including their fitting procedures, rather than merely selecting a predictor from a larger archive. The next decisive experiment is a new checkpoint whose fresh, equal-budget search improves on independent regression families after consuming measured discoveries. Its support, optimizer state, data exposure, search procedure, and accepted deployment state must all be reconstructible.

## 1. Decisions and priorities

### 1.1 The five most important changes

| Priority | Change | Why it precedes the alternatives | Observable completion |
|---|---|---|---|
| P0-A | Repair inner-CV failure semantics and cross-fit all target-derived surrogate features | A stronger optimizer can amplify a contaminated or fabricated target | Failed/insufficient CV is typed as unavailable; inner-held labels cannot affect inner-training features; historical method identities remain distinct |
| P0-B | Close support-to-learning-to-search integration | A network can update successfully while being unable to propose successful new GP descendants | A newly measured TRAIN-only program enters an immutable support epoch, receives a valid training target, has nonzero proposal probability, and is emitted by a child checkpoint |
| P0-C | Run a complete fresh-search learning comparison | Archive growth, surrogate ranking gains, and a changed checkpoint are different achievements | Independent fixed-budget searches isolate the effect of learned weights with a common archive and support |
| P0-D | Extend existing durable progress and claim infrastructure | The repository already has substantial outbox, CAS, evidence, and recovery code | One accepted-state manifest binds checkpoint, support, search, replay, archive, and qualification; crash recovery returns one coherent state |
| P0-E | Compile compact research memory and implement bounded replay before destructive retirement | Future learning needs representative evidence, including failures; storage must remain affordable | Deterministic capsules answer research questions correctly, bounded replay retains coverage, packs restore exactly; deletion stays gated behind exact-version proof |

These are a coherent first program of work. They do not require a new MCTS framework, a new collection of core crates, a larger foundation model, or arbitrary source-code mutation.

### 1.2 Architectural decisions

1. **Use GP-backed Expert Iteration as the organizing loop.** Search creates better measured proposals; the learner amortizes those discoveries into a distribution that improves future searches. Weighted imitation is the first descendant-learning method. The existing direct-sample RLOO path is a separate, gated comparator. [R01], [R07], [R15]

2. **Keep exact program transitions authoritative.** Types, fitting scope, feature binding, masks, compilation, and prediction semantics come from executable contracts. Learned models estimate expensive outcomes and the value of additional work. They never certify an evaluation.

3. **Treat support as a first-class model component.** A vocabulary, legal-action mask, finite program catalog, macro library, decoder, and evaluator jointly determine what the learner can actually invent. Support changes are versioned transitions, not incidental cache refreshes.

4. **Retain one optimizer owner per checkpoint lineage.** Accepted lineage B remains the existing serving authority. The continuous Python research lineage remains separately identified. A research result does not authorize silently loading a 282-token checkpoint into a 401-token runtime. A new production authority requires a measured compatibility and release decision.

5. **Use one primary scientific endpoint.** The primary is the family-balanced mean improvement in **outer log error-ratio gain of the inner-selected incumbent at a fixed total discovery budget**. Anytime AUC, failure rate, diversity, cost, and predictive performance against external algorithms are secondary endpoints with their own definitions.

6. **Store raw measurements, then derive rewards.** Never overwrite RMSE, SSE, runtime, failure status, or resource counters with a moving scalar reward. Teacher cross-entropy, pairwise ranking accuracy, benchmark Elo, and tabular prediction error remain different metric families.

7. **Separate three kinds of progress.** Better archive retrieval; better search given a proposer; and better learned proposal behavior are independently measurable. The full product can benefit from all three without pretending they establish the same claim.

8. **Make learning memory bounded and evidence durable.** Retiring an example from active sampling is reversible. Packing a payload requires verified restoration. Deleting its only recoverable version requires a separate proof and governed application protocol.

9. **Reuse existing modules before extracting new ones.** Extend `feat-math`, `jope-policy`, `jope-learning`, `jope-records`, `jope-motifs`, the existing search adapter, and `jope-datasets::store`. Preserve their current dependency directions.

10. **Make advanced ideas compete for budget.** Neural subtree repair, semantic QD, learned allocation, Gumbel search, macro discovery, curricula, GFlowNets, and optimizer changes each receive a finite experiment, a comparator, a stop condition, and an independent endpoint.

### 1.3 What success would mean

A convincing demonstration has four separately labeled levels:

| Level | Claim | Necessary evidence |
|---|---|---|
| L1: mechanism closure | A measured search can change a learner and drive a subsequent search | Fresh observations, actual optimizer update, complete checkpoint, reload, subsequent proposal trace, reconciled accounting |
| L2: learned transfer | Updated weights improve fresh search on unseen task families | Frozen controls, common archive/support, independent assessment, paired uncertainty, resource parity |
| L3: cumulative improvement | Repeated research improves the system beyond archive accumulation | Multiple training trajectories and rounds, archived rejected rounds, archive-only/frozen-policy controls, independent final evaluation |
| L4: language or algorithm invention | The system discovers useful new compositions, macros, or bounded algorithms | Explicit novelty class, executable correctness, transfer beyond discovery families, cost-aware comparison, retained provenance |

An accepted parent after an inconclusive round is compatible with a functioning L1 system. Three favorable-looking adjacent rounds are not a substitute for L2 or L3 evaluation. Structural novelty without transfer is not L4 generalization.

### 3.3 S1 — Unified (1): 77/100

**Best contribution.** S1 is an effective synthesis. Its central decision to prove an actual search-to-learning cycle before adding MCTS is sound. It keeps Rust semantic authority, treats GP descendants as potential teachers rather than automatic truth, separates draw multiplicity from execution deduplication, and favors incremental integration. Its compact contract table and staged PR plan are easier to implement than an unresolved stack of reference architectures.

**Main deductions.**

- The evidence boundary is honestly disclosed, but most current-state diagnoses are inherited from an older revision. The credential-process complaint, universal zero-update implication, and single quality-head diagnosis are no longer safe present-tense descriptions.
- Its historical H1 summary labels the triplets as wins/losses/ties. The repository's actual categories are lower/equal/higher error; this reverses the meaning of some entries. It also needs the missing-run and unequal-attempt caveats.
- The primary AUC recommendation lacks a fully specified utility transform, budget integration rule, independently frozen incumbent selection, and missing-run handling.
- It points to a companion CSV for detailed scoring, reducing the self-contained value of the requested single file.
- S3 preservation is much stronger than its retirement policy. “Keep evidence” does not supply a bounded replay algorithm or a safe way to recover storage.
- The exact production trainer is deferred despite being a major dependency. Some P0 prerequisites delay the first measurable learning experiment unnecessarily.

**Keep:** the conservative ExIt sequence, existing-crate ownership, explicit outcome vectors, immutable identity, search-teacher eligibility, and empirical gates.

**Change:** turn inherited claims into a current call-path matrix; choose one learner lineage per experiment; define the primary estimator and storage lifecycle; move the smallest support/learner integration ahead of optional QD and broad language work.

| CLOVER/frozen-pool ratchets | Real measured-pool ranking, replay/corpus workflows, multi-round diagnostic analysis | Some paths explicitly do not claim fresh proposal learning or promotion | Label them selector/search diagnostics and use their evidence carefully |
| Support subsystem | Immutable support extension, canonical token/program/hash checks, TRAIN-only provenance, old-leaf preservation | An activation bridge and declared deployment gate remain distinct from a support fixture | Connect support epochs to trainable masks and accepted-state publication |

The v6 runner explicitly calls an anchored update and requires changed parameters; a blanket statement that “the repo has no actual optimizer updates” is false at this revision. Conversely, a successful update does not establish proposal support growth or generalized discovery gains. [C-ADR], [C-POLICY], [C-V6], [C-POLICYLM], [C-NATIVE], [C-ONPOLICY], [C-SUPPORT]

### 4.3 High-priority findings

#### F01 — Inner-CV failure states can look like exceptional quality

In `jope-learning/src/pools/selectors.rs`, parent OOF ridge subfits are converted to optional values with `.ok()`. Later scoring can use `unwrap_or(&model.ridge)`, falling back to the full training ridge. Failed or insufficient inner-CV cases can produce `inner_cv_loss = 0.0`. That makes an unavailable estimate indistinguishable from perfect prediction. [C-SELECT]

The same path constructs target-derived priors/kNN/SoS features over the outer-training set before the inner ridge-selection loop. Subtracting held-fold normal equations does not refit those target-derived features. This is an **inner model-selection contamination risk**. The code excludes the outer held-out parent fold; the mapping from parent identities to independent research families still needs explicit review. The audit does **not** establish an outer-test-label leak.

**Required repair:** a typed CV result, no in-sample fallback labeled OOF, and fold-local refitting of every target-derived feature pipeline. Preserve the old method identity and do not silently rewrite historical results.

#### F02 — Support closure is a more immediate bottleneck than model size

The v6 learner can learn from new measured labels while continuing to sample from the original catalog trie. The support subsystem already supplies useful immutable-extension machinery. The missing product invariant is that admitted discoveries can become trainable and deployable proposals. [C-V6], [C-SUPPORT]

**Required repair:** atomic activation of a compatible support/checkpoint epoch, with exact support-mass and novelty diagnostics.

#### F03 — Neural guidance currently has different meanings in different paths

The pipeline's neural-seeded search bounds the initial proposal population and subsequently evolves measured elites using mutation/crossover. Later children are not uniformly passed through a newly learned offspring scorer. Engine seed weights also do not automatically become child-score predictions. [C-NEURAL-SEARCH], [C-ENGINE-GP]

**Required repair:** instrument source/parent/operator/outcome identity first. Then compare seed-only GP, learned operator allocation, periodic reseeding, and neural repair at equal total cost.

#### F04 — Existing program semantics exceed ordinary search reachability

Executable representations include legacy pipelines/symbolic forms, versioned typed families, and advanced typed programs. Admission in the main pipeline-oriented search is narrower. Some family-specific typed mutation exists already. [C-WIRE], [C-KERNEL-SEARCH], [C-ROWVECTOR], [C-ADVANCED]

**Required repair:** produce a representation × parse × execute × edit × score × emit × teach × sample matrix. Close high-value reachability gaps before adding more operators.

#### F05 — Numeric semantics remain path-dependent

The inspected symbolic prediction path clamps outputs to ±60. Pipeline heads without target wrappers can pass predictions through unchanged, while target wrappers have legacy and range-aware behaviors. Quantile partition-point bounds exist as an opt-in compatibility change; source presence does not establish product-wide activation. [C-MODEL], [C-NUMERICS]

**Required repair:** version numerical policies, add scale/edge fixtures, and migrate explicitly. Avoid silently changing all old program predictions.

#### F06 — Qualification diagnostics are deliberately non-promoting

The round-qualification module states `qualified_claim: false`, `promotion: false`, and `l6_claim: false`. Some referenced artifacts are syntactically checked hashes, not fetched/rehashed/authenticated raw producer evidence. This is an intentional diagnostic boundary. [C-ROUND-QUAL]

**Required repair:** retain this tool's semantics. Implement a separate verified evidence resolver/authority path that can supply a real qualification decision. Do not obtain promotion by changing three booleans.

#### F07 — Durable progress is already substantial infrastructure

The existing progress system has a frozen census, attempt events, bounded fsynced outbox, create-only payloads, dependency-first publication, closure verification, a single conditional run HEAD, revocation checks, and rebuild/restore functions. [C-PROGRESS], [C-OUTBOX], [C-PUBLISH], [C-REBUILD]

**Required repair:** extend its schema and adapters for the complete learning epoch. A second unrelated ledger would increase failure modes.

#### F08 — Retention has implementation, but no destructive authority

The current retention subsystem classifies, packs, distills, and reports. Its plan rejects EXPIRE and explicitly performs no S3 application or deletion. It already contains indexed zstd packing and typed distilled output. [C-RETENTION], [C-RET-PLAN], [C-RET-PACK]

**Required repair:** improve proof completeness and bounded training selection first; add a separately governed exact-version application protocol only after safe restoration and concurrency protection.

#### F09 — Some retention proofs are weaker than their intended future use

Current reference parsing can lose VersionId information. Inventory equality by object count and bytes is insufficient to prove an unchanged deletion snapshot. A configured reservoir percentage is not equivalent to an implemented uniform sampler. Distillation reconciliation based on sets of source keys does not prove bucket/version/multiplicity-complete raw coverage; some converters intentionally filter unscored or incomplete records. [C-RET-REFS], [C-RET-PLAN], [C-RET-CLASSIFY], [C-RET-DISTILLED]

These are prerequisites for a future retirement executor, not evidence that the present read-only classifier has deleted data.

#### F10 — The credential-process gap described in older specs is substantially addressed

The current credential code supports more provider paths than the older complaint implies. One remaining operational issue is that an exported profile can become a static provider without automatic expiration/refresh. Malformed store prefixes and alternative URL paths also need fail-closed qualification. [C-CREDENTIALS], [C-STORE]

**Required repair:** test long-running refresh and strict store identity; do not reimplement the already corrected provider chain.

### 4.4 Interpret historical results precisely

The repository's H1 report describes a small, non-qualifying, incomplete pilot. On seventeen complete cases, policy seeding versus ordinary GP had **10 lower / 2 equal / 5 higher** errors; retrieval versus ordinary GP had **16 lower / 1 equal / 0 higher**. These are not the win/loss/tie tuples repeated in some inputs. There were twenty-four planned contexts, excluded/incomplete cases, and unequal attempt totals across arms. This supports a strong retrieval baseline as a research priority; it does not establish a causal production win. [C-EXPERIMENTS]

The repository also reports newer surrogate improvements on a much larger frozen pool, including pairwise ranking and best-of-budget gains, while explicitly retaining a false flywheel-established claim. Those results concern that pool, cut, method, and protocol. They cannot be compared directly to a roughly 0.506 quality-head result from another lineage as if one were a matched before/after experiment. [C-EXPERIMENTS], [C-POOLS-FLYWHEEL]

### 4.5 The most important invariant

For any claimed learned improvement, the system must answer:

> Which newly measured evidence changed which parameters, under which support and objective, and how did that checkpoint change fresh search on independent problems when archive, evaluator, search code, and resources were controlled?

Everything else in this specification makes that question answerable.

## 5. Formal game, objective, and data boundaries

### 5.1 The object being invented

Distinguish three objects:

1. **Algorithm recipe:** a program describing transformations, parameter estimation, model composition, and prediction.
2. **Fitted model:** the realized state produced by running that recipe on allowed fitting data under a specified budget and seed.
3. **Discovery policy:** the procedure that spends a bounded amount of computation to select or invent a recipe for a new task.

The repository already supports more than closed-form symbolic expressions: pipelines, fitted heads, target transforms, portfolios, and typed ordered families exist. The design extends those capabilities; it does not begin by replacing every program with a neural network or a free-form source string. [C-GENOME], [C-MODEL], [C-ADVANCED]

The future common interface is:

~~~rust
trait AlgorithmRecipe {
    fn check(&self, task: &TaskContract, profile: &CapabilityProfile)
        -> Result<CheckedRecipe, AdmissionError>;

    fn fit(
        &self,
        data: FitView,
        plan: &FitPlan,
        budget: &FitBudget,
        rng: &RngIdentity,
    ) -> Result<FittedArtifact, FitFailure>;

    fn predict(
        &self,
        fitted: &FittedArtifact,
        query: QueryView,
    ) -> Result<Predictions, PredictFailure>;
}
~~~

This is a proposed interface sketch, not a claim that these exact Rust symbols already exist. Adapters must preserve existing fitting and prediction semantics. Search budget and per-recipe fit budget are separate fields.

### 5.2 State and action model

For the initial production experiment, one episode is a **single-agent finite-budget discovery problem**. It does not require a manufactured opponent.

Let

$$
s_t=(c_D,\mathcal P_t,\mathcal A_t,H_t,b_t,\nu),
$$

where:

- \(c_D\) is a context derived only from allowed fitting information;
- \(\mathcal P_t\) is the current population, including explicit recipe/fitted-state distinction;
- \(\mathcal A_t\) is the accessible immutable archive snapshot plus episode-local additions;
- \(H_t\) is the history visible to the actor, including completed observations and pending work;
- \(b_t\) is the remaining resource vector;
- \(\nu\) binds grammar, numerical policy, evaluator, search implementation, support, objective, and hardware profile.

The initial actions are:

| Action | Inputs | Exact transition | Learned component allowed |
|---|---|---|---|
| Propose | Context, support, source mixture | Produce a recipe/construction trace and origin | Neural prior, retrieval choice, grammar proposal |
| Edit | Parent(s), typed edit, RNG | Apply a legal mutation/crossover/repair | Operator choice, edit location, parameter distribution |
| Evaluate | Recipe, fit plan, fidelity, cap | Reserve resources; execute; record outcome | Priority and fidelity selection |
| Refine constants | Recipe, parameter subset, fitting budget | Fit declared constants on allowed rows | Initialization or bounded optimizer selection |
| Retrieve | Role-filtered immutable index, query | Return eligible artifacts with provenance | Query/ranking model |
| Restart | Frozen restart rule and remaining budget | Replace declared population slots | Restart timing/allocation |
| Stop | Incumbent and pending-work policy | Freeze selected incumbent and episode census | Stop policy after a separate experiment |

A one-shot completed-program proposal with one reward is a contextual bandit. A sequence of edits, evaluations, and restarts is a decision process. A token-by-token decoder can be modeled sequentially, but that does not automatically make token-level MCTS economical.

**Exact transition rules:** no child can bypass compiler admission; no action can increase its resource budget; no actor can read outer assessment labels; and no speculative score becomes a measured observation.

### 5.3 The deployed objective is selected quality, not an oracle maximum

Let \(\mathcal S_B(\pi,D,\xi)\) denote the search transcript at budget \(B\), and let \(\operatorname{Select}_{\mathrm{inner}}\) be the preregistered incumbent rule using only actor-visible fitting/inner-validation information.

$$
\hat p_B=\operatorname{Select}_{\mathrm{inner}}
          (\mathcal S_B(\pi,D,\xi)).
$$

The system objective is

$$
J_B(\pi)=
\mathbb E_{D,\xi}
\left[
u_{\mathrm{outer}}(\hat p_B,D)
\right].
$$

This is deliberately not \(\max_p u_{\mathrm{outer}}(p,D)\) over all tried programs. The latter gives the search access to an oracle chooser and exaggerates deployable performance.

For regression, define a training-derived positive scale \(s_D^2\) and a fixed \(\epsilon>0\). The protocol must specify the scale estimator, units, constant-target treatment, and clipping policy before qualification. One usable assessment transform is:

$$
u_D(p)=
\log
\frac{\operatorname{MSE}_{D,\mathrm{outer}}(p_{\mathrm{ref}})
      +\epsilon s_D^2}
     {\operatorname{MSE}_{D,\mathrm{outer}}(p)
      +\epsilon s_D^2}.
$$

The reference recipe is frozen and fitted without outer labels. The evaluator retains both raw MSE values, SSE/count, scale, epsilon, and the derived gain. Positive gain means lower error than the reference. This is **log error-ratio gain**, not classification log loss.

For a paired challenger/control comparison, the difference simplifies to a log ratio of their regularized errors; the common reference cancels. Use uncapped finite values for the primary report unless a capped estimand was preregistered. Training may use a separately versioned clipped utility for stability.

A fit-only mean predictor is the default fallback. Its execution cost is included. A failed candidate does not have an invented MSE; a failed **search system** can still return the declared fallback. A total infrastructure outage has a separate disposition and the fixed-budget intention-to-treat rule in Section 12.

### 5.4 Feasibility before utility

Feasibility is a tagged predicate with reasons:

~~~text
Executable
AdmissibleForTask
WithinFitMemory
WithinInferenceLatency
NumericalProfileSatisfied
RequiredBackendAvailable
EvidenceEligibleForThisUse
~~~

Only candidates satisfying the required conjunction enter the comparable utility set. Do not compute `is_qualified * reward`: an invalid zero can outrank a valid negative reward.

For learning, invalidity is a failure-class label. It may also receive a declared penalty in a particular policy-gradient reward, but that is a new objective definition with explicit bounds. Unknown quality stays unknown.

Use Pareto reporting over error, fit cost, inference cost, artifact size, and numerical reliability. A product profile may impose constraints and then optimize error. A different profile may optimize a declared scalarization. Changing profiles changes the objective identity.

### 5.5 Two independent axes of data separation

**Across tasks:**

| Role | Purpose | Permitted use |
|---|---|---|
| META_TRAIN | Discovery and learner training | Proposals, outcomes, retrieval, replay, macro mining, loss fitting |
| DEVELOPMENT | Configuration and model selection | Architecture/loss/budget calibration; all exposures logged |
| QUALIFICATION | Preregistered promotion decision | Frozen protocol and bounded query count; no training |
| SEALED_AUDIT | Independent reporting | Final frozen analysis; consumed status recorded after access |

**Within a task:**

| Partition | Purpose | Boundary |
|---|---|---|
| FIT | Fit transforms, heads, constants, context encoders | Target information permitted only under declared fit plan |
| INNER_VALIDATION | Adaptively choose recipes and fitting hyperparameters | Search may use it; repeated search can overfit it |
| OUTER_ASSESSMENT | Measure the frozen inner-selected recipe | Actor, learner, retrieval, and macro miner cannot access labels or outcomes during selection |

Group/time tasks require group/time-aware partitions and causal ordering. Dataset families include known source lineage, transformed variants, duplicated tables, synthetic generating templates, and repeated benchmark cuts. A different filename or random seed does not create an independent family.

The role boundary propagates through **embeddings, program priors, strength-of-schedule corrections, retrieval indexes, replay records, research prose, and checkpoints**. An embedding trained on a forbidden outcome is an exposure even when the downstream record contains no label column.

### 5.6 Fit plans and leakage controls

A `FitPlan` is a typed DAG of fitting and transformation steps. Each fitted node records:

- exact input object and row-role identities;
- feature schema and target availability;
- fitted state hash and algorithm/parameter/budget/seed;
- parent fitted-state references;
- OOF partition and coverage;
- whether state is reused, warm-started, recomputed, or unavailable.

For stacking and target-derived meta-features, every row used to train a downstream supervised model must receive features from upstream state fitted without that row's held group. Nested hyperparameter selection refits the **whole outcome-derived feature pipeline** inside each inner fold.

The immediate q-hat repair therefore has this order:

1. Partition outer-training parents into inner folds.
2. For each inner fold, fit priors, neighbor outcome statistics, SoS offsets, base predictions, and other target-derived components using only inner-training parents.
3. Construct inner-training features using the declared OOF strategy; transform inner-held examples with a closure that has never read their outcomes.
4. Select regularization using only inner-held scoring.
5. Refit the selected complete pipeline on outer-training parents.
6. Evaluate once on the held outer family.

Pure input-derived transforms can use a separately declared inductive/transductive policy; do not silently treat target-derived transforms as unsupervised.

The necessary counterexample test changes only inner-held outcomes and verifies that the fitted closure and predictions are unchanged before scoring. This directly detects the issue that normal-equation subtraction alone cannot resolve. Model-selection overfitting is a general risk even without an explicit data leak. [C-SELECT], [R60]

## 6. One control plane, identities, and round protocol

### 6.1 Extend the existing architecture

The existing progress system is the durable backbone. Add learning-epoch objects and adapters to it rather than create another generic ledger. [C-PROGRESS], [C-OUTBOX], [C-PUBLISH]

~~~mermaid
flowchart TD
  A["Frozen task, policy, support, archive"] --> B["Bounded GP search"]
  B --> C["Exact evaluation and attempt ledger"]
  C --> D["Eligible replay and teacher targets"]
  D --> E["One lineage-owned learner"]
  E --> F["Checkpoint and support epoch"]
  F --> G["Independent qualification"]
  G --> H["Accepted-state manifest"]
  H --> A
  C --> I["Research capsules and bounded memory"]
  I --> A
~~~

The diagram describes dependency flow, not permissions. Evaluation, learner, judge, and publisher have different authorities.

### 6.2 Stable identities

Use domain-separated SHA-256 over a specified canonical payload. Reuse existing canonicalization where the ABI is already established; introduce a new version for incompatible encoding.

| Identity | Includes | Explicitly does not mean |
|---|---|---|
| `RecipeId` | Original codec/version and exact canonical recipe bytes | All numerically equivalent programs have the same ID |
| `ProgramViewId` | Adapter/version and canonical analysis graph | Replacement of historical recipe identity |
| `FittedArtifactId` | Recipe, fit-plan, data/split, parameter state, seed, runtime/numerical versions | The recipe alone identifies learned weights |
| `ProposalDrawId` | Episode, draw ordinal, source component, behavior identity, raw construction | Identical final programs collapse into one stochastic draw |
| `EditId` | Parent(s), exact edit, pre/post program identities, RNG, repairs | Parent neural probability is child probability |
| `EvalRequestId` | Recipe/fitted-state contract, task/split, evaluator/fidelity, hardware class, seed, resource cap | Different fidelities or numerical policies can share results |
| `AttemptId` | Logical request plus attempt ordinal/executor identity | A retry is free |
| `ObservationId` | Complete immutable measurement payload and provenance | The payload is authenticated merely because it hashes |
| `ReplaySnapshotId` | Eligible observation IDs, weights, sampler, role/compatibility rules | A mutable S3 prefix is a frozen corpus |
| `SupportId` | Legal program/action catalog, grammar/tokenizer, masks, provenance | New support is automatically a teacher |
| `PolicyCheckpointId` | Weights, optimizer/scheduler/scaler, RNG, model ABI, support, exposure chain | A weights file alone can resume training |
| `AcceptedStateId` | One coherent policy/support/archive/search/replay/qualification epoch | Several independent mutable heads form a transaction |
| `CapsuleId` | Canonical evidence-summary payload | An LLM explanation supplies new evidence |

Hashes are in an envelope outside the payload they identify:

~~~text
digest = SHA256(domain_tag || canonical_payload_bytes)
envelope = { schema, digest, payload, attestations }
~~~

The payload must not include its own digest or a rendering whose identity depends on that digest. Reject duplicate JSON keys, non-finite numbers, ambiguous float encodings, invalid Unicode, oversized objects, and unknown fields where schema strictness is required. Preserve exact float bits for recipe identity when the existing codec requires them; a human-friendly JSON rendering is not the identity codec.

### 6.3 Logical sampling and physical execution

Two identical stochastic draws both remain in the likelihood dataset. The execution cache may fulfill both from one compatible measured request when the protocol permits reuse. That optimization must not reduce the observed draw multiplicity.

Every physical retry remains in the resource ledger, even when the logical request is recorded once. If speculative parallel attempts produce several valid outcomes, select the canonical outcome using a preregistered rule such as the first authorized successful attempt under a deterministic event ordering. Never choose the best observed score among retries.

Resource accounting separates:

- proposal draws and rejected constructions;
- unique logical evaluation requests;
- physical attempts;
- successful, invalid, timeout, preempted, failed, and cancelled attempts;
- cache hits, origin of cached evidence, and charged lookup/restore cost;
- reserved, consumed, released, and outstanding resources.

Duplicate transport delivery is not an extra draw, request, or consumed fit. A separately executed retry is consumed compute. The current progress census/outbox already provides much of this distinction. [C-PROGRESS], [C-OUTBOX]

### 6.4 One round state machine

A round has immutable plans and events; its derived state is rebuilt from committed evidence.

| State | Entry evidence | Allowed next state |
|---|---|---|
| DRAFT | Proposed configuration | FROZEN or CANCELLED |
| FROZEN | Valid plan, roles, budgets, sources, parent accepted state, authority grant | SEARCHING or FAILED |
| SEARCHING | Durable work census and admitted jobs | SEARCH_SEALED or FAILED |
| SEARCH_SEALED | Every planned work unit reconciled; observations fixed | TARGETS_FROZEN or NO_UPDATE |
| TARGETS_FROZEN | Replay/support/teacher eligibility verified | TRAINING or NO_UPDATE |
| TRAINING | One checkpoint lineage and exact input snapshot | CHECKPOINT_SEALED or FAILED |
| CHECKPOINT_SEALED | Actual update/resume state verified, candidate epoch fixed | QUALIFYING |
| QUALIFYING | Preregistered independent assessment | ACCEPTED, REJECTED, INCONCLUSIVE, or INVALID |
| ACCEPTED | Authorized decision and conditional publication | Terminal; may parent another round |
| REJECTED / INCONCLUSIVE / INVALID / NO_UPDATE / FAILED / CANCELLED | Reason and complete census | Terminal; evidence retained |

A failed round can be retried through a new execution identity under a declared continuation rule. It does not mutate the original plan or erase the failed denominator.

“Invalid” means protocol integrity failed. “Rejected” means valid evidence did not satisfy the acceptance rule or established unacceptable regression. “Inconclusive” means valid evidence could not resolve the decision. “No update” can mean no eligible teacher data, no useful expert gap, or a preregistered choice to retain the parent.

### 6.5 Accepted-state publication

Add a versioned `AcceptedState` object to the existing progress graph. It contains:

- policy checkpoint and complete resume manifest;
- model/context/tokenizer/decoder ABI;
- support and operator/numerical profile;
- search implementation/configuration;
- accessible archive and retrieval-index generation;
- replay snapshot and objective configuration;
- qualification decision and exact evidence seal;
- parent accepted state and rollback target.

Publication follows the existing dependency-first pattern:

1. Store immutable payloads and complete manifests through the durable outbox.
2. Verify their remote content and dependency closure.
3. Verify independent qualification and publisher authority.
4. Confirm that all referenced payloads are protected from concurrent retirement.
5. CAS **one authoritative accepted-state pointer** from the observed predecessor to the new immutable state.
6. Build convenience projections only after success.

A per-run progress HEAD remains the run's durable event tip. The accepted-state pointer is a typed use of the same publication machinery for the deployment scope; it is not a second independently authoritative checkpoint/league pair. Explicitly distinguish “run progress committed” from “deployment accepted.”

A CAS conflict produces an immutable unaccepted candidate and an explicit conflict. It must not overwrite the winner, merge unsupported optimizer histories, or retry unconditionally.

### 6.6 Producer trust and qualification

Content hashes establish byte identity. They do not establish that a producer ran the declared evaluator or respected a role boundary.

The verified qualification path therefore resolves:

- the frozen plan and grant;
- exact source/config/container/hardware identities;
- all raw observations or declared sufficient assessment artifacts;
- complete planned/terminal counts;
- split and exposure manifests;
- metric reconstruction;
- actor-visible versus judge-only data;
- resource parity and missing-data disposition;
- attested producer roles and revocation state.

The present diagnostic `round_qual` remains useful and non-promoting. A new verifier consumes authenticated, resolved evidence and returns a distinct schema. Existing diagnostic reports cannot be upgraded by renaming the field or changing a flag. [C-ROUND-QUAL]

### 6.7 Failure recovery requirements

At every durable boundary, killing a process must leave one of three states: no committed work; committed pending work that will be replayed idempotently; or a coherent accepted state. There must be no state in which serving uses checkpoint \(k+1\) with support \(k\) merely because one pointer update completed before another.

Checkpoint resume includes weights, optimizer moments, scheduler state, precision scaler, RNG streams, data-sampler position, support, loss normalizers, and exposure/update indices. Replaying exactly the same examples at a new optimizer step is a new exposure, not a deduplicated event.

Use the current outbox bounds and cadence as the initial baseline unless the implementation experiment explicitly changes them. Their existence and owner-adoption history are already recorded in source; this specification does not invent a new default flush policy. [C-OUTBOX], [C-CADENCE]

### 7.5 Highest-value language additions

**First: schema-bound feature selection.** Add a versioned feature-pointer/feature-set action that can address the actual admitted schema, with width bounds and stable mapping. Test a known target dependence on column 17 or 63. Search should not be restricted to the first eight columns merely because the baseline generator was small. Column permutation must remap the generated recipe appropriately.

**Second: structure/constant separation.** Use typed AST nodes for expression edits and store fitted constants as parameters with provenance. Add bounded local optimization on FIT rows—closed-form affine/linear fits where appropriate, stable regularized solves, and bounded gradient methods for smooth constants. Count this as fit/search compute. Do not allow constant refinement against outer labels.

**Third: fit-aware composition.** Introduce feature unions, residual correction, gated experts, and small ensembles only through declared fit plans. Existing portfolio and advanced-v3 mechanisms are the starting point. A residual model trained on in-sample upstream predictions is a different algorithm from one trained on OOF residuals.

**Fourth: an explicit numerical profile.** Make clipping, protected functions, target scaling, quantile bounds, finite checks, and backend precision visible. A new wide-range profile can replace legacy ±60 behavior for new programs after qualification; old programs retain their old predictions.

**Fifth: bounded reusable macros.** Reuse the existing motif miner. The first macros are parameterized, typed, exactly expandable subgraphs observed across independent META_TRAIN families. Qualification measures search compression and transfer, not just occurrence count.

Adding more transcendental functions is lower priority than making useful existing operators reachable, fitted correctly, and exportable.

### 7.6 Mutation and crossover contracts

Every edit records parent IDs, family, location, parameter values, pre/post codec hashes, RNG, repairs, compiler disposition, and expected capability profile.

| Edit | Preconditions | Failure/result semantics |
|---|---|---|
| Parameter jitter | Parameter domain and active condition satisfied | Reject out-of-domain or use a declared bounded transform |
| Insert/delete stage | Input/output schema and fit effects compatible | Fresh recipe; never presumed equivalent |
| Subtree replacement | Matching result type/shape/effect envelope | New evaluation required |
| Adjacent swap | Compiler accepts reordered dependencies | Search mutation unless commutation is proved |
| Crossover | Compatible typed holes and allowed fitted-state policy | Refit child state; do not inherit incompatible trained weights |
| Head replacement | Task/width/backend compatible | Preserve actual head during fidelity evaluation |
| Shrink | Legal smaller program | Equivalent only with a valid rewrite proof |
| Constant optimization | Fitting scope, budget, seed declared | New fitted artifact; structural identity may be unchanged |
| Macro expansion/contraction | Exact typed expansion under fixed macro ID | Canonical expanded identity and surface identity both retained |

The existing repeated-stage deletion operator is an exploratory shrink mutation. Two identical adjacent nonlinear stages are not generally an identity. [C-EVOLVE]

### 7.7 Three kinds of equality

1. **Identity equality:** exact declared canonical bytes.
2. **Proven semantic equivalence:** a particular rewrite under explicit type, fit, numeric, and effect assumptions.
3. **Behavioral similarity:** similar predictions or errors on a finite probe set.

Only the first two can justify reuse of a compatible evaluation without a new scientific assumption. Behavioral similarity is useful for QD, parent selection, and retrieval but does not justify destructive evidence deduplication.

Equality saturation is a later optimization over a proved rewrite subset. Real-number algebra is not automatically IEEE floating-point equivalence. Reassociation, signed zero, NaNs, saturation, clipping, overflow, target inverses, stochastic fitting, and differing runtime cost all matter. The `egg` work supplies an extensible search mechanism, not a proof that JopeDime's proposed rewrites are valid. [R71]

### 7.8 Numerical and backend verification

Create a named compatibility corpus containing:

- quantile duplicate values and boundary ties;
- constant and near-constant targets;
- very large and very small target units;
- signed zero, extreme finite values, missing values, and protected-domain inputs;
- row/column permutation cases where invariance/equivariance applies;
- nonlinear repeated-stage examples;
- ordered continuation and truncated-prefix cases;
- multi-head/portfolio fitting and target-inverse examples.

For a new quantile profile, test the **active product option propagation**, not only the helper implementation. Bind the resulting recipe/fitted artifact and emitter version to the profile. Compare interpreter/native/Python/Rust/C++/JavaScript only where each capability is actually supported, with declared exactness/tolerance per backend. [C-NUMERICS], [C-TRANSPILE], [C-MODEL]

### 7.9 Code invention tiers

| Tier | Search object | Admission standard |
|---|---|---|
| 0 | Existing recipe parameters and compositions | Current typed runtime and fit/evaluator checks |
| 1 | Exact macros over existing operators | Expansion proof, bounded cost, transfer experiment |
| 2 | Bounded pure numeric subprograms in a restricted IR | Static types, fuel/memory bounds, sandbox, differential tests |
| 3 | New trusted primitive implementation | Human-reviewed source/ABI, independent correctness and performance evidence, new registry version |

The optimizer, loss function, or small neural architecture of an invented **task-level algorithm** may become a Tier-2 recipe component. It is distinct from the outer discovery policy's optimizer. Candidate code cannot change the evaluator, metric, split generator, evidence verifier, or promotion rule.

## 8. Evolution beyond generation zero

### 8.1 Start from the actual product baseline

The checked neural-search path uses an 80-slot initial population with 64 neural slots, then measured elites and ordinary mutation/crossover. Another campaign has its own elite/mutant/crossover composition and niche strategy. Preserve these as named baselines rather than blend their statistics or call paths. [C-NEURAL-SEARCH], [C-ENGINE-GP], [C-CAMPAIGN-EVOLUTION]

The closest published neural-GP hybrid seeds GP from a neural model and feeds selected GP results back into neural training. Its experiments favored substantial GP work between neural interactions. This is direct reason to preserve a seed-only control; it is not a guarantee that JopeDime should use the same schedule. [R07]

### 8.2 An initial finite experiment

After P0 correctness and support closure, run these arms sequentially in two stages:

| Stage | Arm | Mechanism isolated |
|---|---|---|
| E1 | Ordinary/random GP | Existing classical search |
| E1 | Retrieval-seeded GP | Value of historical measured programs |
| E1 | Frozen neural generation-zero GP | Value of neural prior |
| E1 | Updated neural generation-zero GP | Learned weight transfer |
| E2 | Updated seeding + operator bandit | Allocation among existing variation arms |
| E2 | Updated seeding + periodic reseeding | Benefit of mid-search neural proposals |
| E2 | Updated seeding + neural subtree repair | Benefit of learned structured edits |

E2 begins only if E1 establishes a stable baseline and enough measured edit data. This avoids an underpowered seven-arm omnibus campaign.

Report final inner-selected outer gain, unique executable behaviors, numerical failure rate, exploration coverage, inference overhead, and measured teacher yield. Count compiler rejections and repairs.

### 8.3 Proposed source mixture

For the first **new experimental profile**, use an 80-slot generation-zero pool:

- 32 slots from the selected frozen neural policy;
- 24 eligible retrieval proposals;
- 16 grammar/random proposals;
- 8 bounded incumbent or diverse archive proposals.

These are proposed quotas, not current behavior or validated optima. Preserve the existing 64-neural-slot route as the comparator. Quota failure becomes an explicit typed event; a fallback source and its probability are declared in the profile. Never silently reassign slots and still report the original mixture.

For policy-gradient experiments, use a separate sampling profile with tractable direct draws. A quota mixture followed by deterministic deduplication/repair has different behavior probabilities from independent neural sampling.

### 8.4 Learn operator allocation first

Use the existing explicit mutation arms as the initial action set. Start with a cheap contextual bandit or regularized linear controller, not a large autoregressive edit model.

Context features:

- task embedding/statistics and regime;
- parent structural family, size, fitted cost, and numerical diagnostics;
- recent stagnation and operator success counts;
- remaining fit/evaluation budget;
- calibrated uncertainty and archive novelty;
- fidelity/head family.

The initial measured reward can be the incremental inner utility over a same-context incumbent, with a separate cost denominator for acquisition. Keep the absolute outcome, parent outcome, and source-selection probability. Use a sliding or versioned training window because the policy, archive, and task mix evolve.

Reserve at least 20% of **this experimental controller's** edit allocation for declared exploration during the first study. Tune that floor only on development data. An exploration percentage does not supply an unbiased counterfactual estimator by itself; actual randomization and overlap must be logged.

### 8.5 Separate immediate fitness from descendant productivity

A potentially valuable advanced signal is:

$$
V_{\mathrm{desc},h}(p,c)=
\mathbb E[
u_{\mathrm{inner}}(\operatorname{Select}(\mathrm{Descend}(p,h)))
-u_{\mathrm{inner}}(p)
],
$$

under a fixed descendant operator policy and budget \(h\).

This measures whether a parent is a productive stepping stone. It is not the reward of the parent and should not overwrite it. Estimation requires controlled sibling experiments: select parents, assign equal descendant budgets, include no-op/ordinary-variation controls, and account for correlated siblings. Large descendant counts from one lucky family must not dominate the learner.

This is a proposed JopeDime research direction. Its practical benefit is falsifiable: it must improve final search utility at equal total cost over selecting parents solely by current quality and diversity.

### 8.6 Quality diversity with a bounded archive

Use two to four **descriptor axes**, not two to four total archive cells. Begin with a fixed total capacity, for example 256 cells with at most two elites per cell, only if the resulting budget is affordable.

Candidate descriptors might include:

- expanded structural complexity;
- measured prediction-behavior cluster on a TRAIN-only probe panel;
- fit/inference cost band;
- model family or residual specialization.

Define bins on development data and freeze them for an experiment. Do not use outer outcomes to construct the behavior panel. Keep a Pareto/random-diverse archive with the same total capacity as a comparator.

A cell champion is admitted by measured compatible quality, not only novelty. Empty cells do not earn arbitrary rewards. Archive maintenance time and probe prediction bytes count against the system budget. MAP-Elites and novelty search motivate the mechanism; they do not establish that any particular descriptor grid will transfer. [R30], [R31]

### 8.7 Semantic and lexicase experiments

For epsilon-lexicase, use per-case inner errors, or a declared bounded stratified subset, with automatic epsilon computed only from eligible search data. Compare against tournament/Pareto selection. Track selection diversity, best-of-budget performance, outlier concentration, and memory cost. [R68]

For semantic mutation/crossover, use a probe panel and parent prediction differences to propose complementary children. Measure bloat and numerical pathologies. A semantic-distance heuristic is not proof of algebraic identity; all new child recipes require evaluation. [R69]

Residual-directed edits may use FIT/INNER residual structure to propose feature interactions, robust transformations, or specialist heads. They may not inspect OUTER residuals. A policy conditioned on residuals has a different context ABI from a policy conditioned only on the raw dataset.

### 8.8 Fidelity and allocation

Reuse the existing true-head reduced-budget path before inventing another ridge-only proxy. A fidelity record includes row subset, folds, solver iterations, feature budget, constant-fit budget, actual head, warm-start state, and resource cap. [C-EVOLVE], [C-PIPELINE-SEARCH]

Before pruning aggressively, measure per-family/per-head:

- low/full-fidelity rank correlation;
- recall of eventual top candidates;
- false-negative rate among screened-out candidates;
- time-to-completion and instability;
- whether slow-starting algorithms are systematically rejected.

Randomly select a small, preregistered fraction of screened-out candidates for full evaluation. This audits the allocator's blind spots. A proposed acquisition heuristic is expected positive improvement **conditional on feasibility**, multiplied by feasibility probability and divided by expected cost, plus exploration. If an improvement predictor already incorporates infeasibility as zero gain, do not multiply the same probability again. This is a heuristic; finite-budget opportunity cost and information value can make greedy ratios suboptimal.

Start with fixed allocation and successive halving. BOHB or more complex multi-fidelity control enters only if it improves the final endpoint after overhead. [R35], [R36]

### 8.9 The teacher must outperform its source policy

Distillation is justified by an **expert gap**: under a fixed context, budget, and eligible comparison, the searched distribution or selected examples improve on the frozen proposal baseline. A search algorithm that merely amplifies a flawed surrogate should not become a teacher.

Teacher records contain candidate slate, evaluated subset, compatible measurements, allocation rule, selection rule, uncertainty, and target weights. Unevaluated candidates are not losers. Search visit counts are not automatically training targets; their interpretation depends on the search algorithm and evidence quality.

Initially, qualified measured descendants can train weighted sequence imitation. All measured candidates may train supported outcome/failure/runtime heads. These eligibility decisions are separate.

## 9. Neural architecture and expanding proposal support

### 9.1 Start with the current models as controlled baselines

The first support/learning experiment uses the existing native research checkpoint architecture and exact model configuration. It does not combine a support change, a new encoder, a new optimizer, and a new decoder in one treatment.

The accepted lineage-B serving contract and the native research contract remain distinct:

| Property | Accepted lineage B | Native continuous research |
|---|---|---|
| Context interface | 2048 values in the inspected accepted configuration | 2051 finite float32 values |
| Vocabulary | 401 tokens | 282 tokens |
| Program quality representation | Masked mean token embeddings in accepted reference/inference path | Causal transformer EOS hidden state plus context |
| Training ownership | Existing Rust lineage and accepted compatibility contracts | Python continual updater with pinned imports/config |
| Support | Accepted tokenizer/grammar/producer contract | Finite catalog trie and immutable support experiments |
| Migration implication | New tensor shapes/semantics require successor identity | No renaming into the accepted ABI |

The accepted regression configuration describes width 512, six layers, four heads, FFN 2048, and a sequence bound of 128. A support fixture describes a much smaller 128-wide, two-layer, four-head, FFN-512 native model with max length 640. **A fixture is not evidence of every deployed model's size.** Every experiment loads its exact serialized configuration and hashes it. [C-POLICY-CONFIG], [C-POLICY-MODEL], [C-NATIVE], [C-POLICYLM], [C-SUPPORT-README]

### 9.2 Six stages of support

For each program, record membership in six sets:

$$
\mathcal R
\rightarrow \mathcal G
\rightarrow \mathcal X
\rightarrow \mathcal A
\rightarrow \mathcal T
\rightarrow \mathcal D.
$$

| Set | Meaning | Example gap |
|---|---|---|
| \(\mathcal R\) | Representable in a declared codec | Reserved form parses but has no execution |
| \(\mathcal G\) | Generatable by the selected decoder/edit policy | Valid runtime operator absent from trie or mutation profile |
| \(\mathcal X\) | Executable and fit-capable | Recipe emits but fitting is unsupported |
| \(\mathcal A\) | Admissible for this task/numerical/backend profile | Ordered operator used on an IID table |
| \(\mathcal T\) | Eligible for a particular training target | Measured variant allowed for q but not CE |
| \(\mathcal D\) | Deployable under the accepted runtime/qualification contract | Research fixture not qualified for serving |

These are a diagnostic progression, not a universal subset theorem: training an outcome head on an invalid attempted program can be useful, while that program remains outside deployment. Store per-use eligibility rather than one misleading `supported` bit.

The key telemetry is the flow between sets: counts, reasons blocked, newly reachable mass, evaluation share, teacher uptake, and accepted descendants. A rich \(\mathcal R\) with a tiny \(\mathcal G\) is a practical invention bottleneck.

### 9.3 Support-epoch transition

Reuse `jope-learning::support`. Its current freeze/extend/check functions already retain old leaves, validate canonical token/program identity, and restrict noncatalog sources to frozen TRAIN provenance. Its explicitly blocked qualification state remains meaningful. [C-SUPPORT]

A successor research integration performs:

1. **Collect:** measured TRAIN-only candidate programs with original codec, source receipt, evaluator, fit plan, and capability status.
2. **Separate eligibility:** action availability, outcome-head labels, sequence teacher labels, and deployment approval are independently evaluated.
3. **Freeze:** construct \(U\), the old support, and \(V\), eligible newly added terminal programs. Reject collisions, unsupported tokens, overlong programs, missing EOS, invalid roles, or incompatible numerical semantics.
4. **Export:** legal-child indexes and exact canonical construction paths for the specified decoding law.
5. **Bind:** create the new support/decoder/reference/objective configuration at a closed epoch boundary.
6. **Train:** consume the exact replay snapshot with support-aware targets.
7. **Verify:** sample/score/gradient conformance, old-leaf preservation, nonzero new-leaf probability, resume equality, and capability closure.
8. **Publish:** make checkpoint/support/archive/index/qualification coherent through the accepted-state mechanism, after the appropriate release gate.

Initial development limits are **at most 512 added leaves per epoch** and a total catalog bound chosen from measured exact-KL/decode cost. The existing four-million-program parser limit is a safety ceiling, not an initial operating target. If the baseline catalog already exceeds a proposed small test cap, preserve its full identity and restrict the experiment's added leaves; do not silently drop baseline support.

Use at least two distinguishable novel leaves with unequal teacher weights for the probability-learning fixture. With a single leaf in the novel branch and fixed branch mass, its probability is fixed and its sequence-imitation gradient through that normalized branch is zero. Test that singleton separately for reachability.

### 9.4 Support-aware KL without impossible densities

If the old reference \(p_0\) has support \(U\), a new policy assigning positive mass to \(V\setminus U\) has

$$
D_{\mathrm{KL}}(\pi_{\mathrm{new}}\Vert p_0)=\infty.
$$

Do not report a finite full KL by ignoring those terms.

The first proposed expansion profile uses an **explicit disjoint mixture**:

$$
\pi_{\theta,\eta}(p\mid c)=
\begin{cases}
(1-\eta)\,q_{\theta,U}(p\mid c), & p\in U,\\
\eta\,q_{\theta,V}(p\mid c), & p\in V.
\end{cases}
$$

Here \(q_{\theta,U}\) and \(q_{\theta,V}\) are separately normalized, declared branch distributions using shared model logits. In the first expansion each branch uses its own trie-rollout law. This defines a new policy law. It is **not** asserted to equal conditioning an unrestricted or expanded-trie policy by simply masking local logits.

For the first experiment, set \(\eta=0.05\) when \(V\neq\varnothing\), and \(\eta=0\) when it is empty. Treat this as a fixed development configuration. Measure new-branch failure and resource consumption separately; 5% proposal mass is not necessarily 5% compute.

Control:

$$
D_{\mathrm{KL}}(q_{\theta,U}\Vert p_0)
$$

on the old branch, and bound novel mass explicitly through \(\eta\). A later learned \(\eta(c)\) requires its own cap, training law, and experiment.

For later support epochs, \(p_0\) must be the **actual previously committed mixture law**, including its branch masses and factorization. Define the next old branch by retaining that factorization with the current shared logits; do not load the previous weights into a newly merged trie and call that distribution the old policy. Preserve the nested mixture representation, or supply an exact mass-preserving migration with enumerated conformance. Bound mixture depth/decoding cost as part of the support operating envelope. A simplifying refactor that changes probabilities is a new policy transition and must be evaluated as such.

If a future implementation truly conditions an expanded policy on \(U\), it must compute terminal completion masses or an equivalent exact transformation. Local renormalization can define a different law. Sampler, likelihood scorer, KL implementation, and gradients must all agree on the chosen distribution.

The weight-learning comparison freezes the **same expanded support and mixture law** for updated and frozen-weight arms. A separate experiment measures the value of support expansion itself. Otherwise support growth is confounded with parameter learning.

### 9.5 Context encoder progression

A learned dataset encoder should preserve relevant structure:

- IID row permutation invariance;
- feature permutation equivariance with corresponding recipe remapping;
- explicit categorical/numeric/missingness/target roles;
- training-derived scaling;
- group/time structure when applicable;
- no task-name shortcut that leaks benchmark identity or source family.

Use this progression:

| Encoder | Proposed role | Entry gate |
|---|---|---|
| Existing fixed context + simple statistics | Baseline and first closure | Exact current configuration |
| Small Deep Sets encoder | Low-cost learned fit-data summary | Beats statistics/current context on independent tasks per total cost |
| Set Transformer with inducing points | Cross-row/feature interactions | Measured interaction deficiency and bounded memory |
| Perceiver-style latent encoder | Larger heterogeneous inputs | Input scaling bottleneck demonstrated |
| Learned residual context adapter | Add information missing from accepted context | Compare frozen base versus adapter at equal inference cost |

Deep Sets, Set Transformer, and Perceiver provide relevant architectural mechanisms. Their published success does not establish the best JopeDime encoder. [R40], [R41], [R42]

A concrete first **new encoder** experiment may use at most 256 sampled fitting rows and a bounded feature set with learned feature pointers, a 128-dimensional representation, and deterministic sampling manifests. Its dimensions are development choices. It must compete against the existing context rather than silently replacing it. Wide tables require schema-aware subsampling or factorization; flattening arbitrary columns into an order-sensitive vector is insufficient.

### 9.6 Program encoder and decoder

Use three separate outputs:

1. **Proposal distribution:** a normalized law over legal construction/edit actions.
2. **Outcome model:** quality, feasibility, and cost of a completed candidate under a declared fit profile.
3. **Continuation model:** expected value of further search or fitting from a partial state.

These targets are not interchangeable.

The program encoder progression is existing token representation → order-aware token baseline where needed → typed tree/DAG features. Input features include operator/version, types, exact constant representation or numeric embedding, expanded size, fit effects, feature pointers, and dependencies.

The hierarchical edit decoder factorizes:

~~~text
edit family
→ eligible parent / node
→ replacement operator or subtree
→ feature references
→ parameter values
→ declared local fit/refinement
~~~

Log the actual conditional probabilities. If rejection, repair, beam search, or deterministic local optimization changes the sampled object, retain the raw construction and transformation trace. Do not claim its final marginal probability unless it is actually computable.

### 9.7 Efficient inference before a larger model

The active native decode path repeatedly evaluates growing prefixes. Experimental KV decoding already exists elsewhere. Integrating a qualified cache can be a lower-risk efficiency experiment than changing architecture. [C-DECODE], [C-KV]

Acceptance requires the same legal masks, EOS handling, cache reset, batch isolation, probability law, RNG sequence, and declared numerical tolerance. Throughput is measured end to end: batching wait, tokenization, context encoding, device transfers, CPU sampling, and compilation all count.

Use performance evidence to choose between batched finite-catalog scoring, incremental decoding, and direct edit prediction. Do not assume autoregressive sampling is the fastest representation for a bounded support catalog.

## 10. Training objectives, estimators, and optimizers

### 10.1 Preserve the current native baseline exactly

The inspected native supervised coefficients are:

$$
L_{\mathrm{native}}=
L_{\mathrm{CE}}
+0.25L_{\mathrm{BT}}
+0.10L_{\mathrm{list}}
+0.25L_q
+0.10L_{\mathrm{feas}}
+0.05L_{\mathrm{runtime}}.
$$

The v6 anchored step adds a positive, separately configured exact trie KL term:

$$
L_{\mathrm{total}}
=L_{\mathrm{native}}+\lambda_{\mathrm{KL}}
D_{\mathrm{KL}}(\pi_\theta\Vert\pi_{\mathrm{anchor}}).
$$

The current path uses support-aware/global reductions, an immutable reference, eval-mode KL, gradient clipping, and an actual optimizer step. Its L6 history and its total KL-regularized objective are not the same reported number. [C-NATIVE-OBJECTIVE], [C-ANCHORED]

| Current term | Actual baseline meaning | Do not silently reinterpret as |
|---|---|---|
| CE | Supported teacher/token objective | All measured variants are sequence teachers |
| BT | Same-context measured q comparisons | Pairwise comparisons across arbitrary tasks/costs |
| Listwise | Supported measured slates | A complete ranking including unevaluated candidates |
| q | Scalar `q_opt` Huber regression | Quantile prediction or calibrated epistemic uncertainty |
| Feasibility | Supported three-class classification | A universal binary correctness proof |
| Runtime | Huber on log1p time plus lower-bound penalty for censoring | A fitted survival likelihood |
| Anchor KL | Exact finite-support policy-to-reference KL | A valid unchanged objective after support expansion |

The current runner's plateau control is part of its baseline. A cosine-schedule helper elsewhere does not make v6 a cosine-scheduled training run. Record actual imports and configurations.

### 10.2 Initial new objective: supported sequence imitation

Use one explicit initial successor objective: retain the six native supervised terms at their current coefficients and add weighted **sequence** imitation for eligible measured search descendants. The unchanged v6 native/anchor objective remains a separately reported baseline. The successor also needs the §9 old-branch KL because support expansion makes the old full-support KL inapplicable; that is an explicit new objective version, not an unchanged v6 run.

For a context/family-balanced collection of eligible measured programs \(C_D\), define a training utility \(u_i\), a declared context baseline \(b_D\), temperature \(T\), clipping \(a_{\max}\), and weight cap \(w_{\max}\):

$$
w_i=
\min\left(
w_{\max},
\exp\left[
\operatorname{clip}(u_i-b_D,-a_{\max},a_{\max})/T
\right]
\right),
\qquad
\bar w_i=w_i/\sum_{j\in C_D}w_j.
$$

Then

$$
L_{\mathrm{ExIt}}
=
-\mathbb E_D
\sum_{i\in C_D}
\bar w_i
\log \pi_\theta(\tau_i\mid c_D,\mathrm{support}),
$$

where \(\tau_i\) is the canonical supported construction sequence including EOS.

The first proposed v7 loss is exactly:

$$
L_{\mathrm{v7,first}}
=L_{\mathrm{native}}
+0.25L_{\mathrm{ExIt}}
+\lambda_{\mathrm{old}}D_{\mathrm{KL}}(q_{\theta,U}\Vert p_0).
$$

The coefficient 0.25 is a proposed DEVELOPMENT setting, not an established optimum. Preserve the native reduction/eligibility rules for its six terms; the sequence term has its own supported teacher mask and family reduction. Carry the pinned baseline KL coefficient into \(\lambda_{\mathrm{old}}\) as the initial recorded setting, while reporting that its distributional scope has changed. A coefficient/loss ablation compares configurations under common support and cost.

This is a selected-data imitation objective, inspired by search distillation, AWR-style weighting, and priority-queue training. It is not an unbiased policy gradient. The sampling and selection rules define its target. [R01], [R07], [R19]

Proposed first development settings: \(T=1\) after the declared utility normalization, \(a_{\max}=2\), \(w_{\max}=10\), one normalized unit of sequence-target mass per supported context, and a maximum per-family contribution. Tune a small preregistered grid on DEVELOPMENT only.

Do not conflate per-token mean CE with sequence NLL: they weight long programs differently. Keep the current L6 reduction unchanged in its baseline and give sequence imitation a distinct objective ID. Report sequence length and gradient contribution distributions.

### 10.3 Teacher eligibility

Sequence targets require:

- a valid canonical construction under the chosen support;
- compatible task, fit plan, numerical profile, and evaluator;
- allowed META_TRAIN source and no forbidden exposure;
- a measured, resolved outcome;
- declared teacher selection and weight;
- any required expert-gap/admission evidence.

Measured invalid/timeout attempts can train appropriate failure/runtime heads even when they cannot train quality or sequence imitation. A program added to support can be sampled for exploration without being a high-quality teacher. A high-quality measured program outside support must be admitted through a support transition or receive only supported non-generative labels.

For a context with no eligible sequence teacher, the numerator and support count are both zero. Do not normalize by an invented denominator of one and report a supported target. Existing global support-normalization machinery should be reused. [C-NATIVE], [C-SUPPORT]

### 10.4 Quality and ranking targets

Choose a metric-specific target schema. For a new tabular quality head, use a declared normalized inner error-ratio utility or another fixed training target—not a mixture of RMSE, L6 cross-entropy, Elo, and ordinal rank without calibration.

A Huber term is useful for robustness:

$$
H_\delta(e)=
\begin{cases}
\frac{1}{2}e^2,& |e|\le \delta,\\
\delta(|e|-\frac{1}{2}\delta),& |e|>\delta.
\end{cases}
$$

The threshold is in target units. Fit normalization on eligible training data; freeze it for qualification.

For compatible measured pairs, use:

$$
L_{\mathrm{pair}}=
\log\left(1+\exp[-(f_\theta(p_i,c)-f_\theta(p_j,c))/T_{\mathrm{pair}}]\right),
$$

when \(i\) is reliably better. Ties and uncertain small differences are handled by a tie/soft target or omitted from this specific pair loss with an explicit reason. Pair selection may not hide the denominator of the overall experiment.

Listwise learning is optional when a genuinely measured compatible slate exists. The ListMLE literature is relevant, but its loss does not turn censored candidates into a known ranking. [R57]

### 10.5 Runtime, failure, and uncertainty

A timeout at \(c\) means completion time is greater than \(c\) under that run's conditions. It does not establish exact runtime \(c\), and it does not reveal the candidate's unconstrained predictive quality.

Retain the existing runtime baseline first. A separate survival-head experiment may use:

$$
L_{\mathrm{time}}
=
-d\log f_\theta(t\mid x)
-(1-d)\log S_\theta(c\mid x),
$$

with observed-completion indicator \(d\). This likelihood requires an appropriate censoring model. Adaptive early stopping can be informative; include the stopping state/reason and randomized full-budget audits.

Use distinct failure classes for syntax/admission, numerical fault, resource exhaustion, infrastructure failure, preemption, and cancellation. Some are properties of the candidate, others of the platform. Do not train one candidate-invalidity head to blame every host outage on the program.

A first uncertainty comparator is a small independently initialized ensemble or calibrated residual model. Quantile heads can estimate conditional outcome spread; they do not automatically separate epistemic uncertainty from repeated-execution noise. Evaluate calibration and top-candidate recall on fresh measurements. [R56], [R58]

### 10.6 True on-policy RLOO

Reuse the existing `rlfw/onpolicy` implementation and conformance tests. For \(G\ge2\) independent direct draws from one frozen policy/context:

$$
\hat g=
\frac1G\sum_{i=1}^{G}
\left(
r_i-\frac1{G-1}\sum_{j\ne i}r_j
\right)
\nabla_\theta\log\pi_\theta(\tau_i\mid c).
$$

The other-sample baseline is action-independent for term \(i\) under those conditional independence assumptions. Beam outputs, without-replacement draws, post-hoc selection, repaired programs, and GP descendants require different analysis. [R14], [R15]

Initial gated experiment:

- direct supported samples, with replacement;
- one frozen behavior-policy snapshot per scored update batch;
- exact EOS-inclusive sequence likelihood;
- \(G=8\) as a development starting point;
- all failures counted and rewarded according to a frozen finite objective;
- accumulate gradients over that batch **at the frozen behavior parameters, then take one optimizer step**; collect fresh direct draws before the next uncorrected step;
- independent search evaluation against the imitation baseline.

No group-standard-deviation normalization in the baseline RLOO estimator. Such normalization changes the weighting and is a separate method.

An ordinary epoch containing several minibatch optimizer steps is not on-policy after its first step. Reusing the same draws after parameters change requires a separately justified importance-corrected or trust-region surrogate and must be labeled with that actual estimator.

### 10.7 Importance sampling and best-of-B objectives

The existing code distinguishes per-draw importance ratios for dense objectives and joint ratios for the best-of-B/PKPO estimator. Preserve that distinction. Ranking weights attached to GP seeds are not behavior probabilities. [C-ONPOLICY], [C-ENGINE-GP]

For a direct sampled trajectory, the ratio is

$$
\rho_i=
\frac{\pi_{\mathrm{target}}(\tau_i\mid c_i)}
     {\pi_{\mathrm{behavior}}(\tau_i\mid c_i)}.
$$

It is meaningful only with compatible support, actual behavior law, and recorded construction semantics. Report overlap, ratio range, ESS, policy lag, and exclusion reasons. Clipping or self-normalization changes the estimator; do not call the modified result the same unbiased estimator.

A fixed-\(N\) direct-proposal experiment can target maximum sampled reward with a score-function estimator using other-sample maxima as baselines. That is distinct from the user-facing variable-cost adaptive-search objective. Existing PKPO is likewise a best-of-B sampled-utility estimator, not automatic proof of optimal compute allocation.

GP descendants may have many ancestral generation paths with an intractable marginal law. The ancestor's neural probability does not supply the descendant's probability. Use imitation or an explicitly identified full stochastic search trajectory; do not fabricate importance correction. [R07]

### 10.8 PPO, GRPO, and preference objectives

PPO is a gated option when several update passes over recent direct rollouts materially improve sample efficiency. Its clipped surrogate limits parts of the update; it does not guarantee monotonic real-world improvement or fix support mismatch. [R11], [R12]

GRPO supplies a group-relative PPO-style approach without a separate learned critic. For JopeDime, variable program lengths, zero-variance groups, expensive terminal rewards, and truncated generations need explicit normalization and accounting. Dr. GRPO and DAPO are useful implementation lessons; they are not evidence that an LLM training recipe transfers unchanged. [R13], [R63], [R64]

DPO-style preference training is an optional generator objective after paired labels and exact conditional likelihoods are stable. It discards some magnitude, uncertainty, and resource information unless those are encoded in the preference contract. Existing DPO helper functions are not proof that the accepted learner currently optimizes DPO. [R25], [C-ENGINE-OBJECTIVE]

### 10.9 Loss ablation plan

Do not launch a many-term “best possible” objective with no attribution.

| Experiment | Baseline | One change | Success evidence |
|---|---|---|---|
| L-A | Exact current native L6 + anchor KL | Supported descendant sequence imitation | Better fresh search, no support/validity collapse |
| L-B | Best L-A configuration | Replace/add calibrated metric-specific quality head | Better allocation and independent endpoint |
| L-C | Best supervised configuration | Direct RLOO | Benefit per total evaluation/training cost |
| L-D | Direct RLOO | PKPO or another fixed-sample tail objective | Better user-facing search after separate validation |
| L-E | Stable direct-rollout learner | PPO/GRPO update reuse | Benefit with bounded lag/support and full failures |
| L-F | Stable measured pairs | DPO-style preference target | Improvement over weighted imitation with magnitude-aware baseline |

Run gradient diagnostics by task/family and loss support. A head with no observed labels should not contribute a fake “perfect zero” loss. Detect conflict or domination before adding learned loss weights.

### 10.10 Optimizer and schedule specification

**Default for new proposer experiments:** AdamW, with the existing optimizer preserved for exact baseline continuation. Do not change optimizer family in the support-only experiment.

A proposed independent small-model AdamW starting configuration is:

~~~yaml
optimizer: adamw
learning_rate: 0.0001
betas: [0.9, 0.95]
epsilon: 0.00000001
weight_decay: 0.01
decay_exclusions: [bias, normalization]
gradient_clip_global_norm: 1.0
warmup_fraction: 0.05
schedule: cosine
precision: explicitly_pinned_per_run
~~~

These are proposed development settings, not a claim of optimality or the current v6 runtime. The initial continuation baseline restores its exact optimizer/scheduler state; a new schedule starts a new experiment.

| Optimizer | Relevant mechanism | Decision |
|---|---|---|
| AdamW | Decoupled weight decay with adaptive gradients | Default new-model comparator; avoid duplicate L2 penalty [R50] |
| Momentum SGD | Simple alternative dynamics and regularization | Small bounded comparator when affordable |
| Shampoo | Structured tensor preconditioning | Trial only if learner optimization is a material cost; measure memory/root-update overhead [R51] |
| Sophia | Approximate diagonal curvature and clipping | Deferred; language-model results do not establish a JopeDime speedup [R52] |
| Muon | Matrix-oriented updates for suitable hidden weights | Controlled trial with explicit tensor partitioning, aspect-ratio scaling, decay, and AdamW fallback where required [R53], [R54] |

Compare time and total compute to independent task quality, not training loss per optimizer step. If training is 5% of total lifetime cost, even eliminating half of it saves only about 2.5% end to end before secondary effects. Measure that fraction before spending a major optimizer research budget.

Checkpoint conformance includes optimizer-state loading, exact parameter-group identity, scheduler/precision state, and a controlled resume-vs-uninterrupted comparison. A lower CE achieved by a different reduction is not an optimization improvement.

## 11. RL and algorithm-discovery research: what transfers

### 11.1 Scope of the literature review

This is a broad, primary-source map of the method families relevant to JopeDime. It does not claim to enumerate every RL paper, architecture, loss, or optimizer. The purpose is to choose experiments, understand assumptions, and avoid importing algorithms whose guarantees do not apply.

The references include original papers, author-hosted manuscripts, official research explanations, and official AWS documentation. Results in games, robotics, language modeling, or mathematical discovery are evidence for mechanisms, not measured JopeDime performance.

### 11.2 How AlphaGo Zero and AlphaZero actually inform this system

AlphaGo Zero combines a policy/value network with search, generates its own game experience, and trains the network to predict search-informed moves and eventual outcomes. AlphaZero generalizes the approach across games. The useful transfer is the repeated connection between stronger planning and a network that generalizes its decisions. [R02], [R05]

JopeDime differs in several important ways:

| Board-game setting | Regression-algorithm discovery |
|---|---|
| Cheap exact legal moves | Exact syntax/edit transitions, but expensive fitting/evaluation |
| Terminal win/loss under fixed rules | Noisy predictive error and resource constraints under a statistical protocol |
| Opponent provides competition | A single-agent search objective suffices; task-generator competition is optional |
| State symmetries are known | Row/column invariances depend on schema and task kind |
| Huge self-generated experience volume | Each useful measurement may consume substantial CPU/GPU time |
| Game outcomes do not require a held-out dataset split | Adaptive validation can overfit; independent task/row separation is essential |
| Search visits often define training targets | Allocation counts can reflect proxy error and cost; teachers must be validated |

Expert Iteration expresses the planning/generalization decomposition directly. Here, GP is the initial expert, and a learned proposer is the apprentice. The adaptation should be called **GP-backed ExIt-style learning**, with its exact target and data rules documented. [R01]

MuZero learns dynamics relevant to reward, policy, and value when the environment model is unavailable. JopeDime already knows program syntax, types, and edit transitions. Learning those transitions would introduce avoidable uncertainty. A learned predictor of final quality, runtime, or benefit of additional fitting is a more defensible first use of a world-model idea. [R03]

Gumbel planning improves limited-search action coverage and target construction. Its policy-improvement statements rely on correctly evaluated action values. A noisy low-fidelity regression surrogate does not inherit that guarantee. [R04]

### 11.4 Lessons that change the engineering order

**Known dynamics favor exact search.** A learned transition model should earn its complexity where fitting dynamics or allocation outcomes are genuinely unknown.

**Experience quality can dominate update sophistication.** A mathematically correct PPO loss cannot fix mislabeled CV failures, an unusable proposal support, or outer-label contamination.

**An archive of winners is not a transition dataset.** Offline RL requires the state/action/next-state/reward structure it assumes. Do not retrofit fictitious transitions from final program scores.

**A better reward-model fit is not a better search system.** Measure top-candidate recall, missed winners, calibration under novelty, and actual selected quality.

**Published wins are regime-specific.** A neural-GP paper about exact symbolic recovery, a language-model optimizer speedup, and a foundation model's predictive benchmark each motivate different experiments. They do not compose into a promised record.

### 11.5 Prediction baselines are a separate comparison

JopeDime should ultimately compare its invented algorithms with strong fixed/tuned predictors: mean/ridge, existing kernel baselines, XGBoost, CatBoost, tabular MLP/ResNet/FT-Transformer, TabM, and an eligible pinned regression-capable TabPFN implementation. The 2026 TabPFN-3 report is a relevant newer reference; freeze exact weights/software and supported workload rather than use an unversioned product name. [R43], [R44], [R45], [R46], [R47], [R70]

TabArena emphasizes evaluating methods under realistic validation, tuning, and ensembling practices. Its benchmark machinery can inform a fair external ladder, subject to dataset/exposure checks. [R72]

The retrieved 2025 TabICL paper concerns classification. It must not be cited as evidence of regression capability without verifying a suitable version. [R49]

Separate two questions:

- Can the discovered task-level algorithm predict competitively?
- Does the discovery policy find better algorithms after learning from prior research?

One can improve without the other. Both matter for the product, and they need distinct evidence.

## 12. Experiments, statistical decisions, and the public demonstration

### 12.1 Separate the estimands

| Question | Controlled comparison | What may change |
|---|---|---|
| Does the selector rank better? | Same fully measured candidate pool, same budget/visibility | Selector/allocation rule |
| Does the generator discover better candidates? | Same task distribution, legal space, total per-task budget | Proposed candidates and search transcript |
| Do learned weights help? | Same support, archive, search code, evaluator, and per-task budget | Checkpoint weights |
| Does memory help? | Same policy and search procedure | Declared archive/retrieval snapshot |
| Does the full flywheel help? | Same lifetime compute/storage envelope and target task distribution | Learning, memory, and their interaction |
| Is a new language useful? | Explicit common versus expanded language arms | Legal programs/macros; all extra cost counted |

Forcing identical candidate pools while claiming a better generator removes the mechanism under study. Allowing an updated learner a larger archive while claiming a weight-only gain confounds the mechanism.

### 12.2 Primary endpoint

For independent task family \(g\), average paired differences across its preregistered tasks/cuts and search seeds:

$$
d_g=
\frac{1}{|I_g|}
\sum_{i\in I_g}
\left[
u_i(\hat p^{\mathrm{challenger}}_B)
-u_i(\hat p^{\mathrm{control}}_B)
\right].
$$

The primary estimator is:

$$
\hat\Delta=\frac1G\sum_{g=1}^{G}d_g.
$$

Each family receives equal weight. The mapping from current parent IDs to deduplicated research families is itself a frozen, reviewed artifact. Parent identity alone is not a guarantee of semantic independence.

The current Rust pool bootstrap resamples parent clusters while retaining context-weighted averaging. That is a legitimate **different declared estimand**. Implement this family-balanced protocol as a new version; do not reinterpret historical intervals under the new definition. [C-BOOTSTRAP]

Initial primary eligibility is nondegenerate regression tasks whose FIT partition supplies a usable target-scale estimate and valid splits. Constant-target/insufficient-data regimes are preregistered separate strata with absolute-error and failure reporting, not silently removed after outcomes are known.

### 12.3 Incumbent selection and AUC

At each predetermined budget checkpoint, search freezes its incumbent using inner evidence only. Outer assessment occurs after the identities are fixed and is never fed back into the episode.

For the secondary anytime endpoint, use normalized budget grid:

~~~text
0, 0.0625, 0.125, 0.25, 0.5, 0.75, 1.0
~~~

At zero budget the declared fallback is a conventional reporting anchor. Its actual initialization/fit cost is charged before the first positive-budget interval; the anchor does not grant free computation. If initialization exceeds the first checkpoint, return the declared already-available fallback state or mark that profile infeasible according to its frozen contract. For grid \(x_0,\ldots,x_K\), define right-continuous step integration using the incumbent fixed at \(x_k\):

$$
\operatorname{AUC}_i=
\sum_{k=0}^{K-1}
(x_{k+1}-x_k)\,u_i(\hat p_{x_kB}).
$$

This is an explicitly chosen discrete anytime statistic; trapezoidal or log-budget AUC would be different protocols. Report the full grid and raw selected-program identities.

An inner-best incumbent's outer quality may go down at a later checkpoint. Do not make the outer curve artificially monotonic by retrospectively choosing the best outer score. If a stopped episode returns its last valid incumbent, carry that identity through later grid points and retain the stopping reason.

### 12.4 Decision rule and practical effect

For the first confirmatory campaign:

- one preregistered primary comparison;
- one final efficacy look;
- one-sided nominal \(\alpha=0.025\);
- no early stopping for a favorable point estimate;
- practical threshold \(\delta=-\log(0.99)\approx0.0100503\), corresponding to **1% lower regularized MSE** on the paired geometric-error scale;
- accept the learning-benefit claim only when the one-sided 97.5% lower confidence bound exceeds \(\delta\), protocol integrity passes, and the declared failure/resource constraints pass.

The tested null is \(H_0:\Delta\le\delta\), not merely \(H_0:\Delta\le0\). A point estimate above 1% combined with a significance test against zero supports a weaker claim.

Use a paired family-cluster **percentile bootstrap** with 20,000 replicates as the initial interval estimator: resample \(G\) families with replacement, compute each replicate's equal-family mean, and take its 0.025 quantile as the one-sided 97.5% lower bound. Fix the RNG and quantile interpolation convention. Report all family differences, robust secondary summaries, and sensitivity to influential families. Bootstrap coverage is nominal and can be poor with few or highly skewed clusters; there is no claim of exact finite-sample coverage. Validate calibration on development simulations and retain an independent statistical review before a consequential promotion. [R62]

A failed integrity check yields INVALID, not a negative scientific effect. A valid but unresolved interval yields INCONCLUSIVE. The product-release decision can additionally require a separately preregistered comparison against the currently accepted shipped route or retrieval-rich baseline. That is not silently made another primary endpoint after results appear.

### 12.5 Power and sample-size planning

Estimate the standard deviation \(\sigma_d\) of **paired family effects**, not candidate scores or context-level residuals, using DEVELOPMENT data.

For a planned alternative \(\Delta_\star>\delta\), a rough normal-approximation planning formula is:

$$
G\approx
\left[
\frac{(z_{1-\alpha}+z_{1-\beta})\sigma_d}
     {\Delta_\star-\delta}
\right]^2.
$$

This is a planning approximation, not a substitute for simulation or an executed power study.

For illustration only, with \(\sigma_d=0.08\), 80% power, one-sided \(\alpha=0.025\), and \(\Delta_\star=0.03\), the formula gives about **127 families**. A thirty-family study would primarily detect larger effects under these assumptions. Thousands of programs per family do not create thousands of independent families.

The launch artifact must contain the actual development estimate, the minimum effect sought, available eligible independent families, budget, and expected power. If the required family count is unavailable, report the limitation and use the study as a developmental or less precise result. Do not substitute many additional seeds for missing family diversity.

### 12.6 Training randomness and multiple rounds

A family-cluster interval comparing two fixed checkpoints conditions on those trained weights. It does not capture variation from rerunning the learning process.

For L3, run at least three independently initialized or independently randomized **training trajectories** as a first characterization, with the same declared protocol and checkpoint horizon. Three is a resource-conscious starting point, not a strong universal reproducibility guarantee. Report each trajectory separately.

Evaluation families are crossed with training trajectories and search seeds. Use an explicitly hierarchical/crossed uncertainty analysis or report conditional family intervals plus trajectory dispersion. Do not pretend \(R\times G\times S\) rows are independent samples.

Run a preregistered three-round development horizon initially, reporting every round, including no-update/rejected rounds. Select the final confirmatory checkpoint by a rule fixed on DEVELOPMENT. Do not require each round to improve or label ancestry-linked rounds independent.

### 12.7 Essential controls

The first L2 weight-learning experiment uses:

1. frozen parent weights, common support, common archive;
2. updated child weights, same support/archive/search;
3. strong retrieval-seeded GP as a separately reported reference;
4. ordinary GP as a mechanism baseline.

A later L3 study uses a staged factorial:

| Learner | Archive | Interpretation |
|---|---|---|
| Frozen | Fixed | Base search |
| Frozen | Growing | Memory/archive accumulation |
| Updated | Fixed for assessment | Learned parameter benefit |
| Updated | Growing | Full product interaction |

Within training, compare fresh feedback with a matched replay-only/passive-data control if claiming the value of new research acquisition. A restart-from-origin control can test whether continuation helps beyond repeatedly fitting the accumulated corpus.

The full factorial is launched only after the smaller comparisons are viable. Avoid consuming the entire budget on many weakly powered arms.

### 12.8 Resource parity and lifetime efficiency

The primary per-task discovery budget includes:

- context extraction and neural inference;
- retrieval and necessary remote reads/restores;
- parsing, compilation, and admission;
- candidate fitting, constant refinement, and prediction;
- all physical attempts and retries;
- search/selection and required evidence publication overhead.

Record CPU core-seconds, GPU-seconds by device class, wall time, peak memory, I/O bytes, and requests separately. A preregistered resource-credit conversion can support one scalar cap, but preserve the underlying vector and hardware calibration. Equal proposal counts are insufficient.

**Meta-training cost is reported separately from the primary per-task endpoint.** This is necessary to isolate learned weight quality. The L3 lifetime-efficiency study charges training and data acquisition as well, comparing against a control allowed to spend the same lifetime resources on additional search/retrieval.

Outer assessment happens after candidate identities freeze and has its own campaign account, including assessment retries. It cannot retroactively consume the actor's discovery budget or alter which candidate the actor selected. Publication needed during search is charged to discovery; later scientific reporting/qualification is charged to the campaign.

Report amortized scenarios over 1, 10, 100, and 1,000 future tasks, with those scenarios declared before analysis. Let \(C_{\mathrm{upfront}}\) be incremental training plus any material acquisition/index-building cost relative to the comparator. If the learned system saves \(\Delta C>0\) per future task at matched quality, the simple break-even estimate is \(C_{\mathrm{upfront}}/\Delta C\); report assumptions and uncertainty. When savings are nonpositive there is no finite break-even under this model. Do not assume infinite future use to make any training run look economical.

Caches are either cold/common, or explicitly evaluated as a product-memory scenario. Historical expensive fits are not free in lifetime accounting.

### 12.9 Missingness, timeouts, and censoring

Freeze the planned census before execution.

- Candidate numerical failure: record failure; it is not a measured high MSE.
- Candidate timeout: runtime lower bound and unknown unconstrained quality; search retains its previous valid incumbent.
- Administrative preemption: distinct retry policy and consumed resources.
- System failure with a valid incumbent: return it under the fixed-budget rule.
- System failure before any valid candidate: return the preregistered fallback when the assessment can execute.
- Completely unavailable assessment: record missing outcome and apply the preregistered campaign integrity rule; do not complete-case filter it after inspecting arm performance.

The initial confirmatory protocol invalidates a comparison with unresolved primary assessment outcomes rather than imputing favorable values. A predefined bounded recovery window may rerun assessment only, with all attempts charged and without changing candidate identities. This is stricter than discarding failures and clearer than invoking generic “right censoring” for every missing value.

Time-to-target is a separate secondary analysis requiring a censoring model. Fixed-budget final quality and AUC do not become unbiased simply by calling missing runs censored.

### 12.10 Repeated testing and adaptive exposure

A repeatedly queried qualification set becomes development evidence even if the actor sees only a scalar. Track query count, revealed statistics, and decisions. Retire panels from sealed status after exposure according to the declared policy.

The first campaign's one-look \(\alpha=0.025\) is for that declared claim family. If a later program wants multiple confirmatory stages, allocate a finite error budget **before** launching them—for example 0.010, 0.0075, 0.005, 0.0025 across four declared stages—or adopt a justified sequential procedure. Do not retroactively claim that an already-spent 0.025 test left an unused budget.

Alpha allocation does not itself repair arbitrary adaptive reuse of the same holdout. Use fresh independent panels, a carefully validated reusable-holdout method, or explicitly weaker claims. The adaptive-data-analysis literature makes this distinction necessary. [R61], [R73]

### 12.11 A public demonstration that is actually informative

The demo should show one real, frozen episode/round with:

- the regression problem's allowed context and budget;
- the starting recipe population and source mixture;
- typed edits and measured outcomes;
- the inner-selected incumbent's evolution;
- compilation/fit failures and their cost;
- the child checkpoint and added support;
- fresh searches from parent and child under the same assessment contract;
- the resulting effect and uncertainty, including an inconclusive outcome if that is what occurred;
- the compact research capsule and the next experiment it supports.

Use a replay of committed evidence for the polished presentation. The replay must identify the source run and not pretend to be live training. A successful demo need not claim a world record; it should make the causal chain visible.

## 13. Replay and cumulative research memory

### 13.1 Memory is part of the learning system

The repository already has curated experiment JSONL, synthesis documents, claim records, source binding, and revocation handling. Extend them into a deterministic research-memory compiler. Do not create a parallel “AI truth database” that disagrees with the existing claim graph. [C-EXPERIMENTS], [C-CLAIMS], [C-CLAIM-INVENTORY]

Memory has four distinct jobs:

| Layer | Job | Typical content |
|---|---|---|
| Measured record | Preserve what happened | Program, task/split, raw metrics, failure, cost, behavior, evidence refs |
| Learning replay | Choose what to train on now | Compatible observations, weights, source mixture, snapshot/cursor |
| Research capsule | Explain what an experiment supports | Hypothesis, comparison, effect, uncertainty, caveats, next falsifier |
| Research index | Find relevant evidence quickly | Role-aware lexical/structured/vector indexes over capsules and programs |

A capsule cannot recreate a deleted optimizer state or infer an unlogged propensity. A replay sampler cannot upgrade a diagnostic report into qualification.

### 13.2 Immutable outcome record

The compact record must contain at least:

- schema and immutable observation identity;
- task/context/parent/family/role/split identities;
- recipe and fitted-artifact references;
- source/parent/edit/construction lineage;
- evaluator, numerical profile, fit plan, fidelity, seed, hardware;
- measured status and failure/censoring reasons;
- raw SSE/count/MSE or metric-specific sufficient statistics;
- runtime/resource vector, including failed attempts;
- actual proposal/selection propensity when known, otherwise null plus reason;
- visibility at each decision time;
- eligibility by training head and use;
- exact raw/pack/artifact references and retention contract.

Store per-case predictions/errors only when needed for a declared scientific or future-learning purpose, such as promotion audit, semantic selection, calibration, or a failure witness. Their size is often much larger than aggregate records; select their retention prospectively and record the limitation.

### 13.3 Deterministic research capsules

The authoritative capsule is compiled from verified structured artifacts. An LLM may add a separately labeled explanation, but the compiler must not use free-form prose to invent numerical results or causal conclusions.

Required capsule fields:

| Group | Required information |
|---|---|
| Identity | Experiment/run/round, source commit, schema and renderer version |
| Question | Hypothesis and competing explanation |
| Design | Treatment, control, role, sample unit, budget, primary endpoint, preregistration |
| Census | Planned, completed, excluded, failed, missing; reasons and attempt totals |
| Result | Estimate, interval, units, direction, practical threshold, decision |
| Mechanism | What changed; what was controlled; support/archive/weights distinction |
| Evidence | Typed exact refs to plan, measurements, checkpoint, judge, source |
| Limitations | Exposure, power, missingness, unmatched resources, numerical scope |
| Negative knowledge | Failed configurations, known counterexamples, unresolved contradictions |
| Next experiment | Smallest discriminating test, comparator, cost cap, stop condition |
| Status | Active/superseded/revoked; parent claim and replacement refs |

Separate **fact**, **inference**, **hypothesis**, and **decision**. Every inference names supporting facts and an explicit assumption. A superseded result remains historically queryable under its original protocol; its current recommendation can change.

### 13.4 Compression that is useful to an AI

Generate three views from the same payload:

1. **Evidence atom:** a compact statement of one comparison/result with exact units, scope, and refs.
2. **Brief:** approximately 2,048 tokens under a pinned tokenizer, containing decisions, strongest evidence, contradictions, and next tests.
3. **Dossier:** a larger structured view with methods, tables, and source expansion.

These are proposed presentation budgets. The compiler records actual byte/token counts and tokenizer version; “2,048 tokens” is not universally the same size across models.

Use an information-priority order:

~~~text
decision and evidence class
→ primary result and denominator
→ exact treatment/control/budget
→ limitations and conflicting evidence
→ source references
→ next falsifier
→ optional narrative
~~~

Never drop an interval, failed-run count, or non-claim to preserve decorative prose. If required fields cannot fit, return a valid short index with a “needs expansion” flag rather than truncate a result into a misleading sentence.

Stable IDs should be short references inside the view and exact hashes in the payload. Repeating a 64-character hash in every sentence wastes context. Derived views may use local aliases whose mapping is included once.

### 13.5 Research graph and contradiction handling

Reuse the current claims graph's source/scope/subject and revocation mechanisms. Add explicit edges:

~~~text
tests_hypothesis
compares_with
uses_protocol
derived_from
contradicts
supersedes_recommendation
invalidates_evidence
reproduces
fails_to_reproduce
requires_followup
~~~

A contradiction is scoped. A method can help under a short budget and hurt under a long budget without either result being wrong. Retrieval should return the relevant conditions, not collapse all results into a universal recommendation.

When a source observation or evaluator version is revoked:

1. identify dependent capsules and claims;
2. mark derived recommendations stale/invalid according to dependency type;
3. remove them from active teaching/qualification eligibility;
4. regenerate briefs and indexes;
5. preserve the original record and the revocation reason;
6. record whether any checkpoint consumed the invalidated data.

Revocation does not magically untrain a checkpoint. The response can be quarantine, retraining, a bounded corrective update, or a scoped claim withdrawal, depending on evidence.

### 13.6 Bounded replay policy

Initial proposed mixture for a new replay profile:

| Component | Share | Purpose |
|---|---:|---|
| Recent compatible outcomes | 30% | Track current search distribution |
| Strong diverse frontier | 20% | Teach useful programs without one-family collapse |
| Loss-independent historical reservoir | 20% | Preserve representative coverage and calibration |
| Failures/counterexamples/near misses | 15% | Learn feasibility and avoid repeated mistakes |
| Rare task/structure strata | 10% | Reduce systematic blind spots |
| Regression anchors | 5% | Detect forgetting on previously solved regimes |

These are experiment settings, not validated optimal proportions. Define eligibility per loss head: a failure sample may contribute no quality or sequence target.

First sample a family/context under the declared balanced distribution, then the replay component and eligible observation. If a component is unavailable, apply a frozen redistribution rule and record the resulting probability. With overlapping components, the marginal sample probability is the sum of their weighted component probabilities, not simply the chosen component's probability.

Cap contribution from one prolific program lineage and one task family for training. Keep the representative reservoir's sampling law separately intact; do not apply utility-driven caps and still call it uniform.

### 13.7 A real bounded reservoir

Use fixed, finite strata—for example a preregistered coarse task-regime × outcome-status taxonomy, with an overflow stratum for unknowns. Do not create an unbounded new storage allocation for every arriving family.

For stratum \(s\), keep the \(k_s\) smallest keyed hashes of immutable observation IDs. Under the hash-as-uniform assumption this is uniform sampling without replacement from that stratum's declared eligible population. Each record's inclusion probability is:

$$
p_s=\min(1,k_s/N_s),
$$

where \(N_s\) is the exact eligible population count.

Persist stratum definitions, seed/key identity, population counts, selected IDs, thresholds, and inclusion probabilities. Deterministic merges/restarts must reproduce the same selected set.

Count bounds alone do not bound bytes. Define a maximum retained inline/dependency footprint \(b_{\max,s}\) for a compact reservoir record and choose capacities satisfying \(\sum_s k_s b_{\max,s}\le B_{\mathrm{reservoir}}\). Shared heavy artifacts have a separate pinned byte budget. Enforce a size-valid admission schema before observing the sampling rank; oversized raw detail can be summarized under that fixed contract or held separately. Never drop a selected record opportunistically by utility or size and still claim the same uniform law. If the promised footprint cannot be retained, pause admission and mark coverage incomplete until the contract is restored.

A fixed-seed bottom-k threshold can only fall as the same population grows, so previously rejected high-hash records need not be resurrected. Changing the seed, strata, or eligibility after deletion requires a new coverage claim. A fixed 5% rate grows forever; bounded \(k_s\) solves a different problem.

The union of reservoir and value-selected examples is not uniformly sampled. Use the reservoir component with appropriate stratum weights for historical bias checks. Retention probabilities do not replace original action propensities for offline policy evaluation. [R59]

### 13.8 Value-aware active selection

After hard roots and representative coverage are protected, use a bounded heuristic for cache/replay priority:

~~~text
marginal frontier contribution
+ missing behavioral/task coverage
+ failure or counterexample novelty
+ measured recent reuse
+ uncertainty worth resolving
+ estimated cost of recomputation
− marginal bytes and restore cost
~~~

Normalize terms on development data and publish the policy. This is a practical priority model, not a calibrated economic value theorem. Measure whether it improves future discovery under the same storage/read/compute budget.

Avoid a winner-only feedback loop: the model that chooses retained evidence must not erase all evidence that challenges its own ranking. Keep the loss-independent reservoir and protected failure witnesses even when the current model assigns them low utility.

### 13.9 Memory acceptance experiment

Build a frozen set of research questions from verified experiment records:

- Which change improved which endpoint under what budget?
- Was the result fresh search, frozen-pool ranking, or a true weight update?
- How many independent families and missing runs were involved?
- Which checkpoint/support/objective was used?
- Which negative experiment already ruled out an idea?
- Which evidence was revoked or superseded?
- What is the next cheapest discriminating experiment?

Compare:

1. existing document retrieval with a strong lexical baseline;
2. deterministic capsule retrieval;
3. capsule plus structured graph expansion;
4. optional vector retrieval;
5. optional LLM-generated explanation.

Use the same context-token budget and representative retrieval quality, not a deliberately weak “first 2,000 tokens of a giant document” control.

Acceptance targets are proposed: exact deterministic reconstruction of all numerical facts; zero unsupported qualification upgrades; zero forbidden-role retrievals in the test corpus; at least 95% retrieval coverage of required evidence on the frozen question set; and measured downstream answer quality/cost. The LLM answer layer is evaluated separately from the deterministic fact layer.

### 13.10 Finite memory requires admission control

A bounded store cannot preserve an unbounded stream of unique raw evidence forever. Compression reduces growth; it does not eliminate it.

Declare separate budgets for protected evidence, hot replay, staging, compact history, and cold raw bodies. Estimate irreducible protected bytes before launching a campaign. If protected roots alone exceed budget, pause new work or expand capacity through the existing operating process. Do not silently delete claim evidence to satisfy a quota.

Prospectively label verbose logs, intermediate caches, repeated renderings, and reconstructable encodings with disposable contracts. Keep exact inputs and outputs needed for the questions the experiment promises to answer. Irreversible loss of unique information is a declared retention decision, not described as lossless compression.

## 14. S3 publication, recovery, cost, and safe retirement

### 14.1 Current foundation and exact scope

The repository already implements a conservative retention classifier, Inventory parsing, reference scans, indexed zstd packs, distilled Parquet records, tags, and lifecycle reporting. The current plan refuses EXPIRE and performs no S3 application. Reuse this foundation. [C-RETENTION], [C-RET-PLAN], [C-RET-PACK], [C-RET-DISTILLED]

This specification defines a future operational design. It does not authorize or perform bucket changes. Existing historical storage totals, price tables, and lifecycle decisions are evidence about their recorded dates, not a current inventory or bill.

The required storage outcome is not “delete old failures.” It is:

> Preserve the evidence and active state needed for future learning, audit, and recovery, while reclaiming redundant physical representations and explicitly disposable history under a verified contract.

### 14.2 Separate content, location, and obligation

Use three identities:

| Identity | Fields | Purpose |
|---|---|---|
| Content | SHA-256, length, schema/codec | What bytes or logical payload are required |
| Physical object version | Account/bucket, key, VersionId, content hash, length | Where an exact recoverable copy resides |
| Obligation | Root/consumer, edge type, retention contract, expiry/release condition | Why those bytes must remain available |

Unknown VersionId and the literal S3 null version are different states. The first destructive executor supports only unambiguous versioned targets; version-suspended/null/unknown cases stay HOLD until separately implemented.

ETag is a conditional-write token, not a universal SHA-256 content proof. Multipart and encryption behavior make generic “ETag equals checksum” assumptions unsafe. Use the stored content hash plus actual readback.

### 14.3 Proposed logical layout

Preserve existing progress paths and add versioned logical namespaces within the explicitly configured store:

~~~text
blobs/sha256/<content-digest>
progress/runs/<run-id>/...
progress/accepted/<deployment-scope>/HEAD.json
epochs/<accepted-state-digest>.json
support/<support-digest>.json
observations/<partition>/<immutable-shard-digest>.parquet
packs/<pack-digest>.zst
pack-indexes/<index-digest>.json
locations/<location-manifest-digest>.json
replay/<snapshot-digest>.json
research/capsules/<capsule-digest>.json
research/indexes/<index-generation>/...
retention/plans/<plan-digest>.json
retention/proofs/<proof-digest>.json
retention/catalog/<generation-digest>.json
retention/catalog/HEAD.json
retention/receipts/<commit-digest>.json
~~~

These are proposed logical paths, not claims that every path currently exists. Avoid a broad rename of historical keys. Location manifests resolve content to current retained physical copies. Mutable pointers remain few and conditional.

Partition observation shards by compatible schema/role/protocol and coarse time or run ranges. Do not create one tiny object for every scalar statistic. Avoid overpartitioning into millions of nearly empty files.

### 14.4 Correct S3 semantics

S3 object reads/writes and listings provide strong consistency, while **S3 Inventory is an asynchronously generated report** that can omit recent changes. It is useful for discovery and cost accounting, not a transactional deletion snapshot. [AWS-S], [AWS-I]

Use:

- create-only immutable writes through `If-None-Match: *`;
- observed ETag/version information from the same pointer read;
- conditional pointer updates through the backend's supported `If-Match` semantics;
- explicit conflict/precondition handling and reread;
- destination readback and content validation before publication.

An S3 conditional write protects one object. It does not make two independent pointer updates atomic. Existing `Store`, mirror, sync, and progress publication already implement useful pieces of this protocol. [AWS-C], [C-STORE], [C-MIRROR], [C-SYNC], [C-PUBLISH]

### 14.5 Credential and store qualification

Retain the corrected existing credential chain. Prefer workload-role providers with refresh behavior suitable for long-running jobs. A profile exported into a static provider needs bounded expiration-aware refresh or a documented short-lived-job constraint; do not assume successful startup proves a twelve-hour run will keep credentials. [C-CREDENTIALS]

Add meaningful operational checks:

- malformed S3 prefix is rejected rather than falling back to bucket root;
- explicit bucket/prefix/account/region identity appears in the run manifest;
- alternative URL paths cannot silently use a different credential/endpoint contract;
- credential subprocess timeouts and failures are bounded and redacted;
- no worker receives publisher or retirement credentials merely to emit results;
- readback/restore requires access to the relevant encryption keys as well as S3 bytes.

These checks target source-observed integration risks. No credential material belongs in research capsules or logs.

### 14.6 Compaction before deletion

Extend the existing pack writer rather than replace it. Add:

- source bucket and exact version identity;
- checked record/chunk/pack length limits;
- bounded streaming uniqueness checks;
- final short-pack accounting;
- immutable source and output manifests;
- remote upload/readback verification;
- range-based individual-object restoration;
- a typed location resolver used by real consumers.

Suggested development targets are 64–256 MiB packs with smaller independently decodable chunks. Measure actual compression ratio, CPU cost, request count, tail packs, and restore latency. These are tuning targets, not a promised compression factor.

Maintain independent exact mappings:

~~~text
source object version
→ source byte hash and length
→ pack/index version
→ chunk range
→ entry range/hash
→ restored byte hash
~~~

An upload checksum is not a complete restore drill. Restore a declared sample and all protected critical artifacts from the destination using the production reader; full source/entry verification is required before claiming lossless replacement.

### 14.7 Distillation completeness

The existing distilled table is real, but its current source-key set reconciliation is weaker than a complete raw-record proof. Some converters intentionally filter unscored/incomplete-provenance rows. Their skip counts are useful; they do not authorize deleting the source. [C-RET-DISTILLED]

Introduce two distinct receipts:

1. **Filtered-index conversion:** states exactly which rows were included and skipped.
2. **Complete scientific distillation:** proves that every independently enumerated source observation is represented exactly according to the retention contract.

The source manifest must be generated independently of the filtered output. It includes bucket/key/version, source checksum, subrecord ordinal or stable observation ID, metric/fold/seed, and multiplicity. Reconcile a multiset or unique observation identity set with explicit duplicate rules—not only a set of filenames.

Preserve failures, timeouts, invalidity, incomplete attempts, and unknown provenance as typed records or retain their raw source. `qualified=true`, an L6 delta field, or a caller's `champion_qualified` Boolean does not establish qualification. Resolve the actual immutable qualification evidence before using supersession as a retention reason.

### 14.8 Existing progress ancestry prevents naive GC

The current progress graph treats parent corpora, parent checkpoints, parent commits, exposures, and state blobs as dependencies. Publication/reuse walks the entire closure, including ancestors. [C-PROGRESS-INVENTORY], [C-PUBLISH]

Therefore, two stages are required:

**Stage A: physical relocation with unchanged obligations.** Add a pack-aware immutable resolver that returns the exact bytes required by existing v1 references. The v1 graph still means what it meant. Mutable pointer reads, observed versions, and CAS operations remain direct physical store operations; they must not be served from a stale pack-location cache.

**Stage B: explicit snapshot semantics.** Add versioned snapshot/corpus/checkpoint **and progress-root/Commit/verifier** contracts with:

- strong byte dependencies required for current resume/evaluation;
- historical identity edges preserving ancestry but not every payload;
- retained metadata/claim/revocation evidence;
- a migration receipt describing what remains reproducible;
- a root transition releasing only explicitly retired obligations.

Do not silently reinterpret a v1 parent edge as historical. A current resumable checkpoint may not require every earlier optimizer state, but an old published reproducibility claim might. Those obligations must be resolved separately.

Changing only corpus/checkpoint edges is insufficient while the new root still reaches an old `Commit.parent` chain that recursively requires those blobs. The new verified root must establish the actual ancestry traversal boundary. In an accepted-state object, type ordinary parent ancestry as a history identity and explicit rollback targets as strong dependencies; otherwise every accepted parent becomes an accidental permanent rollback obligation. Retain old roots in the authoritative root set for as long as their exact reconstruction contract remains active.

This makes scientific forgetting explicit: after a valid root transition, the system might preserve “which update occurred and which evidence it consumed” while relinquishing “resume at every historical step.” The capsule records that limitation.

### 14.9 Retention classes

| Class | Examples | Default treatment |
|---|---|---|
| Protected roots | Accepted checkpoints, active learner resume, qualification evidence, split/grammar registries, unresolved failure witnesses, published claim artifacts | Keep recoverable; release only through an explicit root/contract transition |
| Hot learning | Current replay, active support/indexes, recent observations | Bounded cache; immutable snapshots pinned by active consumers |
| Compact history | Canonical programs, measured outcomes, exposure/decision metadata, capsules | Retain under declared coverage and evidence contracts |
| Restorable raw | Lossless packs, exceptional traces, detailed predictions | Cold or warm according to measured use/restore needs |
| Disposable derivatives | Rebuildable renderings/caches, redundant loose copies, declared transient logs | Retire after verification and grace |
| Unknown | Missing identity, incomplete parser, unregistered consumer, unresolved authority | HOLD |

Low score, old age, domination by a champion, or non-qualification alone is insufficient for deletion. A losing program can be a counterexample, a calibration point, or a useful stepping stone.

### 14.10 Complete roots and a concurrency fence

A best-effort text scan cannot prove absence of references. Build an authoritative registry of active runs, accepted states, learners, replay snapshots, claims, failure investigations, readers, pack/index manifests, and legacy roots. Required unreadable/unsupported sources make the root snapshot incomplete and block retirement. Independent scanning remains a veto.

A correct race protocol must prevent this sequence:

~~~text
GC sees no reference
→ a learner publishes a new reference
→ GC deletes the bytes
~~~

Use one immutable **retention catalog generation** selected by a single CAS HEAD. It includes location mappings, registered strong pins, and reserved retirement sets. Every governed publisher registers a dependency pin through this authority **before** advancing its run/accepted-state pointer.

If publication later fails, an orphan pin is conservative. Reconcile it later. A time limit or an apparently unpublished HEAD is insufficient to reap a pin while a stalled publisher can still commit. First cancel/revoke and drain that publication authority, then establish that no committed/current root requires the pin. Registering the pin after publication is unsafe.

This is a cooperative protocol over an explicitly managed scope. Unregistered legacy writers/consumers require migration or verified quiescence. Their prefixes remain HOLD; an application-level catalog cannot govern arbitrary external actors.

### 14.11 Exact-version retirement protocol

The existing prefix classifier stays read-only. A new object-level plan and separate executor implement:

1. **Prepare retained copies.** Upload immutable packs/snapshots/records and verify destination restoration.
2. **Publish locations and roots.** Commit a coherent catalog generation; old direct readers continue to protect their original copies until migrated.
3. **Build the exact plan.** Name every source version, proof rule, retained replacement, root snapshot, scan coverage, lifecycle state, grace period, object/byte cap, and cost estimate.
4. **Obtain the required execution authority for that exact plan.** This is part of a future destructive operation, not an action performed by this review.
5. **Reserve through CAS.** Against the latest catalog generation, atomically validate the complete current strong-pin closure and confirm that the deletion set excludes every retained replacement version and every incompatible existing reservation. Commit that validation and the retirement set together through CAS. A conflict requires full revalidation against the new generation. New strong pins to reserved versions are refused or redirected to verified replacements under an explicit contract.
6. **Wait the declared grace and recheck.** Re-enumerate roots, drain/migrate old readers, verify source/kept versions, protection state, and restore proof under the reservation.
7. **Journal and delete exact versions.** Record per-target intent, request identity, result, and observed after-state. Use exact VersionId; no prefix deletion or implicit-current “cleanup.”
8. **Recover after interruption.** Reservations persist; reconcile intents and outcomes. An absent object is not automatically reported as deleted by this executor.
9. **Verify protected closure and savings.** Resolve all roots, perform restore/evaluation checks, and report actual net bytes and failures.
10. **Close the reservation deliberately.** Do not release it while a stale executor retains effective deletion authority.

The first executor uses one controlled commit worker with durable reservations. Automatically expiring a lease while an old worker can still issue deletes is unsafe. Later parallelism needs a gateway/authority that enforces the fencing generation at each actual deletion and drains stale work.

Deleting without a VersionId in a versioned bucket generally creates a delete marker; it does not reclaim the target version. Exact-version deletion is irreversible. Respect Object Lock and legal holds. [AWS-D], [AWS-L]

### 14.12 Rule-specific proof requirements

| Rule family | Minimum proof |
|---|---|
| Duplicate or loose-to-pack replacement | Exact source/retained bytes match, retained location protected, reader migration complete, disaster-recovery purpose preserved |
| Intermediate checkpoint retirement | Current/milestone/claim/resume roots retained, parameter/optimizer state obligations released, exact historical resume limitation recorded |
| Telemetry distillation | Independent complete source census including failures, identity/multiplicity reconciliation, all promised scientific questions supported |
| Terminal/context redundancy | Body/program/score/protocol subset proof, no hidden observations or state dependency |
| Noncurrent version retirement | Exact old versions, root/protection/lifecycle checks, explicit authorized plan; no inference from age alone |

A compact record can satisfy a declared future-learning contract without reproducing every raw log byte. That is **lossy scientific retention with explicit scope**, not a lossless replacement proof.

### 14.13 Lifecycle is an independent deletion path

Application pins and IAM restrictions do not override an applicable S3 Lifecycle expiration rule. AWS explicitly documents that bucket policies cannot prevent lifecycle actions. A “keep” tag or additional keep rule is not a general override of a broad matching expiration rule. [AWS-E]

The managed store must establish that no enabled matching expiration rule can remove a protected physical version or required retained replacement. Evaluate actual prefixes, tags, size/date/day conditions, noncurrent-version rules, replication state, and lock status. Unsupported fields remain UNKNOWN.

The repository records a historical policy allowing 90-day noncurrent expiration even for some T0 classifications. That is an existing policy fact, not a guarantee that exact pinned old versions are permanent. Prefer new never-overwritten content-addressed current keys for new protected objects, while verifying no current-expiry rule covers them. Existing exact-version consumers may require verified relocation/migration or a separately reviewed policy exception. [C-RET-LIFECYCLE], [C-RET-POLICY]

Object Lock protects versions under its rules, but a delete marker can still affect ordinary key reads, and missing encryption keys can make retained bytes unusable. Do not confuse replication, retention, and recoverability. [AWS-L]

### 14.14 Storage economics

Maintain a price/configuration snapshot and actual counters. Do not reuse a historical price table as a current estimate.

A useful expected-cost model is:

$$
C_{\mathrm{store}}=
C_{\mathrm{bytes}}
+C_{\mathrm{requests}}
+C_{\mathrm{transitions}}
+C_{\mathrm{restore}}
+C_{\mathrm{encryption}}
+C_{\mathrm{packing\ compute}}
+C_{\mathrm{egress}}
+C_{\mathrm{temporary\ duplication}}.
$$

For a proposed transition/retirement, report before, peak transitional, and after bytes; request counts; measured compression; pack tails; restore probability/latency; and minimum-duration charges. Tiny-object transitions can cost more than they save, and AWS defaults/eligibility rules include size and duration constraints. [AWS-T]

A proposed initial development budget can cap hot replay at 5 GiB and staging at 10 GiB, with a separately approved raw/evidence envelope. Those are planning defaults, not measurements of the user's bucket. Use the current actual inventory to select operational values.

Do not promise a fixed percentage of S3 savings. The first storage experiment should take one well-understood artifact family, measure packing/readback cost, compute actual net savings, and prove a real restore before expanding.

### 14.15 Recovery objectives

Define per-class recovery targets in the run/store profile:

- current learner resume: hot state and recent committed replay available promptly;
- accepted predictor: deterministic artifact resolution and runnable evaluator;
- qualification evidence: complete paired metrics and source dependencies recoverable;
- cold raw diagnostics: explicit restore latency and cost;
- retired disposable artifacts: tombstone and declared non-recoverability.

Conduct a full restore drill using the retained reader path, not a separate script that quietly bypasses the production resolver. Measure whether a new host can reconstruct a run, load the exact support/checkpoint, and evaluate a retained program.

## 15. Advanced research with explicit entry gates

### 15.1 Search-level policy gradients can credit good seeds

There is a useful distinction from the invalid descendant-likelihood shortcut.

Let a raw seed or seed population \(z\sim\pi_\theta(\cdot\mid c)\), and let a fixed, parameter-independent GP procedure produce a fixed-budget episode return \(R(\operatorname{GP}(z,\xi))\). Then:

$$
\nabla_\theta\mathbb E[R]
=
\mathbb E\left[
(R-b(c))\nabla_\theta\log\pi_\theta(z\mid c)
\right],
$$

under the usual score-function conditions and an action-independent baseline.

This credits the **sampled seed action** for its downstream search return. It does not claim that the final descendant has probability \(\pi_\theta(z)\). If the GP operator policy also depends on \(\theta\), its sampled decisions must be included or the omitted dependency otherwise handled.

Why defer it: each reward requires a complete budgeted GP episode, variance can be high, and a population is a large action. First compare against cheaper ExIt imitation. Then run paired seed-population episodes with the same GP/evaluator/budget and independent episode accounting. Success is improved fresh selected quality per lifetime cost.

This is an original engineering application of the policy-gradient identity. It supplies a principled future route for learning “seeds with useful descendants.”

### 15.2 Value of information for candidate evaluation

A quality score predicts which candidate looks best. A useful allocator should also predict **which measurement would most improve the final decision**.

A proposed two-stage acquisition model estimates:

1. expected improvement conditional on feasibility;
2. feasibility probability;
3. expected consumed cost, including failed attempts;
4. expected reduction in decision uncertainty.

The simple baseline is:

$$
a(p)=
\frac{
P(\mathrm{feasible}\mid p,c)
\mathbb E[(u(p)-u_{\mathrm{inc}})_+
\mid p,c,\mathrm{feasible}]
}{
\mathbb E[C_{\mathrm{consumed}}\mid p,c]
}.
$$

If improvement already includes zero for infeasible outcomes, do not multiply by feasibility again.

A later value-of-information term may favor a measurement that distinguishes two operator families or calibrates a blind region even when that candidate is unlikely to win immediately. Its success criterion includes future rounds, with a fixed exploration budget and a control that spends the same resources on immediate expected improvement.

### 15.3 Planning over meaningful edits

MCTS begins only after:

- legal typed edits exist;
- partial-state/continuation value has fresh calibration;
- depth-two or depth-three decisions contain useful dependencies;
- equal-cost best-first/beam/GP/halving comparators are established;
- planning overhead is a measured minority of the budget.

Use exact transition semantics and a state identity including task, population/partial program, visible evidence, pending work, remaining budget, and versions. Share an evaluation cache by `EvalRequestId`; do not merge planning nodes solely because they contain the same recipe.

A possible PUCT experiment selects:

$$
Q(s,a)+
c_{\mathrm{puct}}P(a\mid s)
\frac{\sqrt{N(s)+1}}{1+N(s,a)}
-\lambda_C\widehat C(s,a),
$$

with explicit normalization and measured/model tags. This is a proposed heuristic. Backup the declared single-agent terminal return; do not alternate signs as if two opponents take turns. Use mean rollout returns for expected value, not a maximum of noisy samples masquerading as an unbiased value estimate.

Progressive widening must admit an initial action:

$$
|\mathcal A(s)|\le
\min\left(A_{\max},
\max\left(1,\lfloor k(N(s)+1)^\alpha\rfloor\right)\right),
\quad 0<\alpha<1.
$$

Specify valid-action sampling, duplicates, stop actions, and budget exhaustion. Root Gumbel/sequential-halving is tested first and reuses existing comparators. [R04], [C-ABLATIONS]

### 15.4 Macros as search compression

The strongest macro criterion is not frequency alone. A macro should reduce the effort required to reach useful algorithms on new families.

Proposed score components:

- number of independent training families supporting it;
- reduction in construction/search depth;
- transfer improvement at a fixed search budget;
- expanded runtime and memory cost;
- precision of exact expansion;
- whether it encodes task-specific constants or identifiers.

Mine from the existing quarantined motif path. Compare primitive-only search, macro-enabled search, and an equal-token-budget larger primitive decoder. Count expanded cost to prevent hiding a large computation behind one cheap token. Preserve macro IDs forever as immutable semantics.

DreamCoder motivates reusable abstractions and recognition; JopeDime must prove benefit under its regression/evidence contracts. [R08], [C-MOTIFS]

### 15.5 Curriculum near the competence frontier

Start with stratified task sampling and learning-progress replay. Only then consider a bounded task generator.

A generated task must have:

- a declared source/generator family;
- valid target and split semantics;
- a solvability/learnability check using a fixed reference portfolio;
- bounded size/noise/cost;
- novelty relative to training templates;
- no access to qualification or sealed targets.

Teacher rewards should combine learner regret/progress with validity and coverage, not simply reward making the learner fail. Impossible noise tasks are not a useful curriculum. Keep uniform/stratified replay as a comparator and cap generated-task allocation initially.

POET, PAIRED, and PLR supply different mechanisms—co-evolution, regret-based environment design, and task replay. They should not be conflated into a single “self-play curriculum” switch. [R32], [R33], [R37]

### 15.6 Policy leagues

Maintain immutable old policy snapshots and structurally diverse references now. Use them to measure slice-specific regressions and specialization.

A league scheduler becomes worthwhile if policies have cyclic strengths: A beats B on one regime, B beats C on another, C beats A elsewhere, and a simple fixed mixture is inadequate. PSRO-style methods can then help define a portfolio. [R38]

League payoff cells must include task distribution, budget, archive access, support, and uncertainty. A table of aggregate Elo from different panels is not a valid meta-game. The league state is included in the accepted-state manifest; no separate unsynchronized champion pointer.

### 15.7 GFlowNet experiment

Use a finite typed construction DAG with canonical terminal identity. For a positive, frozen reward \(R(p,c)\), trajectory balance uses:

$$
L_{\mathrm{TB}}(\tau)=
\left[
\log Z(c)
+\sum_t\log P_F(s_{t+1}\mid s_t,c)
-\log R(p,c)
-\sum_t\log P_B(s_t\mid s_{t+1},c)
\right]^2.
$$

This targets reward-proportional terminal sampling under its assumptions, not simply the single best program. Multiple derivations require a correct backward policy or a canonical construction. An edit graph with cycles needs a finite step/budget index and valid reverse transitions. [R39], [R65]

Freeze reward temperature and numerical bounds. Invalid states cannot receive a substantial arbitrary reward floor. Noisy reward inside a log changes the learning problem in general; \(\mathbb E[\log\hat R]\neq\log\mathbb E[\hat R]\). Compare with the same model trained by weighted imitation plus a diversity archive.

Entry gate: the system has already demonstrated that useful diversity improves final search and that mode collapse is a real limitation. Otherwise GFlowNets add complexity without a diagnosed problem.

### 15.8 Inventing task-level neural architectures, losses, and optimizers

After typed fitting and Tier-2 execution are established, extend the **algorithm recipe**, not the evaluator, with bounded learning components.

| Searchable component | Initial bounded design | Required safeguards |
|---|---|---|
| Small neural predictor | Depth 1–4; widths from a finite set; explicit activation/normalization/residual/ensemble options | Fit budget, parameter/memory cap, deterministic initialization identity |
| Feature encoder | Typed numeric/categorical/missingness blocks, bounded embedding dimensions | Schema binding and no hidden target access |
| Loss family | Squared, absolute, Huber, bounded robust mixtures; declared target normalization | Nonnegative weights, stable reduction, no access to outer targets |
| Optimizer | Fixed validated families and bounded schedules first | Exact state ABI, finite-step/runtime cap, stable numeric operations |
| Learned update rule | Restricted tensor expression over parameters, gradients, and bounded state | Typed shapes, safe divisions/scales, fuel/memory bounds, independent gradient/update oracle |
| Ensemble/gating | Small OOF-trained blends or conditional experts | Full fit DAG, expanded cost, independent prediction semantics |

A loss recipe can take the form:

$$
L_\phi=
\frac1n\sum_i
w_\phi(x_i)\,
\rho_\phi\left(
\frac{\hat y_i-y_i}{s_{\mathrm{FIT}}}
\right),
$$

with nonnegative normalized weights, bounded robust parameters, and all learned quantities fitted only inside the allowed scope. Prevent trivial solutions such as driving all weights to zero or making the scale unbounded. The external assessment metric remains fixed.

A learned optimizer may use only declared tensor operations over \(w_t,g_t,m_t,v_t\), with bounded persistent state and a known update horizon. It cannot read the outer evaluation loss, alter the data split, make network calls, or write arbitrary host files. Evaluate the resulting discrete executable recipe, not only a differentiable relaxation.

This is a credible route from deep encodings to GP to code: the representation gradually acquires richer **learning procedures**, while the evidence and execution boundary stays stable.

### 15.9 Bounded code lane

Use a separate worker/process sandbox with:

- no network or ambient credentials;
- explicit read-only inputs and output channels;
- memory/process/time/fuel limits;
- deterministic RNG capability;
- allowlisted runtime/import surface;
- static admission plus runtime enforcement;
- compiler/evaluator identity and full failure capture.

Correctness tests include reference comparisons, dimensional/shape invariants, metamorphic cases, and held-out generated tests. A candidate that passes a finite test set is not universally proved correct. New trusted primitives require an explicit promotion process.

FunSearch and AlphaEvolve motivate program archives, evaluation cascades, and evolutionary source proposals. Their architectural lessons do not establish that an unchanged model's weight distribution is learning. Preserve that distinction in the demo and research claims. [R06], [R66]

### 15.10 Advanced-method budget policy

Each advanced workstream gets:

- one written hypothesis;
- a strongest affordable comparator;
- an exact primary endpoint and diagnostic metrics;
- a finite development budget;
- a fixed stop/defer rule;
- an artifact/capsule whether it wins or loses.

A proposed portfolio is 70% of research resources on the proven baseline/closure and measurement path, 20% on near-term extensions, and 10% on high-risk methods. Tune this allocation to actual capacity; do not let exciting experiments starve the regression suite, storage integrity, or the next independent evaluation.

1. Fresh search emits typed proposals, GP ancestry, requests, attempts, and terminal outcomes.
2. A deterministic eligibility decision selects measured TRAIN-only teachers.
3. Support expands under an immutable transition with executable sampler/scorer conformance.
4. The optimizer makes a finite nonzero parameter update under the declared loss.

### 17.3 Independent study and lifetime cost

An illustrative L2 allocation with 128 eligible families, two search seeds, four arms, and a 0.5 CPU-core-hour discovery cap per episode would reserve:

$$
128\times2\times4\times0.5=512\text{ CPU core-hours}.
$$

The 512 core-hours are a **CPU subtotal**. GPU proposal inference still belongs to each primary discovery episode and receives an additional explicit device-time cap or calibrated resource-credit charge. Meta-training and post-selection outer assessment have separate campaign accounts. All are included in the lifetime-cost report. This is not a launch recommendation until DEVELOPMENT variance, actual family independence, episode feasibility, hardware, and budget are established. The §12 power example requires approximately 127 families under its illustrative assumptions; a similar-looking count does not validate those assumptions.

Run the confirmatory comparison once its protocol is frozen. A four-arm study has one declared primary weight-learning contrast; the other comparisons are labeled secondary or assigned their own multiplicity budget. A three-trajectory L3 experiment adds genuine retraining cost and crossed uncertainty; it is not obtained by relabeling three search seeds.

Maintain both cost views:

- **Per-task product cost:** cold and explicitly defined warm scenarios, discovery, fitting, compilation, inference, and required retrieval.
- **Research/lifetime cost:** failed experiments, training, evaluation, qualification, storage/retrieval, and eventually amortized savings over declared deployment volume.

A search policy that saves ten seconds per task after a million GPU-seconds of training may be scientifically interesting but needs a realistic reuse volume before being an economical product improvement.

### 17.5 Stop and defer rules

Stop expansion and repair the baseline when:

- the candidate's actual scoring path is unclear or target-derived features cross a forbidden split;
- proposal/scorer probabilities disagree, or a claimed teacher is outside the learner's support;
- resource counters or repeated attempts do not reconcile;
- fresh-search results are explained by unequal archives, support, caches, or budgets;
- missing assessment evidence makes the planned comparison invalid;
- recovered state combines incompatible checkpoint/support/search epochs;
- a snapshot or lifecycle rule can invalidate a protected dependency;
- an advanced method's overhead removes its apparent equal-evaluation gain.

A negative L2 result should produce an explicit next diagnostic: insufficient expert advantage, poor teacher transfer, support bottleneck, encoder weakness, loss imbalance, or excessive search overhead. Do not respond automatically by increasing model size or adding another RL acronym.

### 19.1 Four draws, three requests, four physical attempts

For this arithmetic-only fixture, assume ten fit credits and zero ancillary charges. A real discovery budget must additionally reserve/debit generation, lookup, compilation, fallback, and other measured overhead. The neural policy draws `A, A, B, C`; the first two draws are identical under the same deterministic evaluation request.

| Event | Logical outcome | Charged credits | Consequence |
|---|---|---:|---|
| Draw A, first request | Completed measured fit | 2 | One terminal observation for A |
| Draw A again | Exact request cache hit | 0 fit credits in this illustrative fixture | Second draw retained; actual lookup/generation overhead would still be charged in a real ledger |
| Draw B, attempt 1 | Worker/process failure | 1 | No fabricated error label; request remains retryable under frozen policy |
| Draw B, attempt 2 | Completed measured fit | 3 | One terminal successful observation for B; failed attempt retained |
| Draw C | Fit timeout at its cap | 4 | Terminal budget failure; unconstrained quality unknown |

The totals are four draws, three distinct evaluation requests, four physical attempts, two successful measured candidates, one terminal timeout, and ten credits. A's duplicate draw is not a second independent noisy evaluation.

Suppose A's inner error is 1.0 and B's is 0.8. The search selects B using those permitted inner measurements. Only after selection freezes does outer assessment find MSE 0.92 for B and 1.0 for the declared comparison predictor. With a negligible regularizer in this illustrative scale, the log error-ratio gain is approximately:

$$
\log(1/0.92)\approx0.0833816.
$$

That is one task's observation. It supplies no family-level confidence interval, no learned-transfer conclusion, and no basis to score C's unknown predictive error.

For on-policy learning, whether A's cached outcome can be reused depends on the declared environment: an exactly deterministic request can reuse its deterministic return while preserving draw multiplicity; a noisy reward law cannot be turned into independent repeated measurements by cloning the first reward. The update's sampling and reward assumptions must match the actual process.

### 19.5 One round with an inconclusive comparison

Consider a real implementation following this sequence:

~~~text
Freeze parent/support/archive/search/data roles.
Run measured training search and close attempt ledgers.
Build eligible replay and a support transition.
Train and reload a child.
Run fresh DEVELOPMENT searches.
Compile capsule and compare under the declared method.
Keep the parent accepted because evidence is inconclusive.
Retain child, update lineage, and negative/inconclusive evidence.
Begin the next planned round from the declared accepted state.
~~~

This would be a functioning learning mechanism. Its value is that every transition is inspectable and the inconclusive result improves the next experiment's design. It does not justify depicting the child as the new champion or training repeatedly against a supposedly unseen final panel.

## 20. Risks, rejected approaches, and completion definition

### 20.1 Principal risks and responses

| Risk | Early diagnostic | Response |
|---|---|---|
| Search teacher is not better than the parent proposal distribution | Small or negative equal-cost expert advantage on DEVELOPMENT | Improve search/allocation or stop imitation expansion |
| Useful children remain unreachable | Teacher rejection rate by codec/support; zero proposal mass | Repair representability/support before training longer |
| Encoder misses task structure | Weak cross-family transfer despite in-context teacher fitting | Test context features, feature pointers, order/graph encoding with fixed decoder |
| Distillation collapses diversity | Entropy, behavior coverage, frontier occupancy and restart success fall | Bound weights, preserve coverage, compare archive mixture and QD |
| Frequent neural intervention disrupts GP | Seed-only GP wins at equal lifetime cost | Keep generation-zero seeding; narrow intervention to measured bottlenecks |
| Surrogate is confidently wrong on novel programs | Full-fit audit disagrees with screened rank/uncertainty | Reduce pruning, recalibrate, reserve random audits and exact evaluation |
| Success is caused by accumulated archive information | Frozen-weight/growing-archive arm explains gain | Claim retrieval improvement and redesign weight-learning comparison |
| Benchmarks are adaptively overfit | Repeated panel access or contamination ancestry | Retire panel from confirmatory use, preserve exposure, use fresh controlled assessment |
| “Compression” deletes future counterexamples | Blind memory queries fail; restoration gaps; coverage drift | Keep bounded representative/failure evidence and improve distillation contract |
| Snapshot retains all historical bytes | Strong closure remains proportional to full history | Introduce explicit new root semantics; do not market packing as semantic pruning |
| Stalled writers race cleanup | Old publication resumes after pin removal | Revoke/drain publisher authority before unpinning; atomic pin/reservation checks |
| Repository becomes harder to navigate | Duplicate active import names, multiple schema owners | One pinned manifest/owner per active lineage; compatibility views for history |
| Advanced method consumes the research program | More infrastructure than independent comparisons | Enforce gates, finite caps, strongest simple baseline and stop decisions |

### 20.2 Approaches explicitly rejected for the initial program

- Rewriting the whole repository or introducing a new suite of core crates before the first closed learning cycle.
- Calling arbitrary GP descendants on-policy samples because their ancestors came from a neural model.
- Declaring a policy gradient invalid merely because GP follows the seed: the valid seed-return estimator in §15.1 is distinct from a fabricated child probability.
- Measuring an oracle maximum over outer scores and calling it deployable search performance.
- Treating a perfect-looking zero fallback or in-sample substitute as cross-validation.
- Transplanting a board-game Elo or win-rate gate without defining the actual tabular estimand.
- Expanding model width while the successful program remains outside the legal support.
- Adding MCTS, a world model, GFlowNets, and a new optimizer in one unidentifiable experiment.
- Deleting low-scoring history by age or score alone, or using a percentage sample as a permanent storage bound.
- Calling matching object counts/bytes, a digest-shaped string, or a prefix allowlist an independent retirement proof.
- Assuming object versioning, Object Lock, or bucket policy alone solves every lifecycle/deletion race.
- Equating LLM summaries, source-code novelty, benchmark victories, and learned cross-task algorithm invention.

### 20.3 Completion criteria for the recommended program

The first release is complete when G0–G4 are implemented and independently reviewed, a real L1 loop is demonstrated, and the planned L2 result is reported with the correct positive/negative/inconclusive interpretation. **A statistically positive effect is a research outcome, not something engineering can guarantee.**

The technology has advanced even if the first L2 comparison is negative, provided the system can now answer precisely:

- What did search discover?
- Which discoveries were eligible and reachable?
- What changed in the learner?
- Which data and objective caused the update?
- What did the reloaded child do on fresh tasks?
- Which part of the gain came from weights, archive, search, or resources?
- What evidence survives, what is reconstructible, and what can be safely retired?
- What is the next experiment most likely to distinguish the remaining explanations?

The more ambitious milestone is a sequence of qualified learning and language changes that improves performance on independent regression families at an acceptable lifetime cost. Its cumulative memory should make future experiments cheaper to design and less likely to repeat known failures. The architecture in this specification makes that ambition falsifiable, recoverable, and maintainable.

### 21.5 Evidence limits carried forward

This specification recommends future work. It does not report a new JopeDime accuracy record, a newly trained checkpoint, a reproduced historical flywheel gain, an implemented v7 package, a complete Rust/GPU qualification, a live S3 inventory, or achieved storage savings. The only newly executed repository tests are the narrow existing Python modules identified in §§2.2 and 18.1. All example run values in §19 are synthetic. Estimates, thresholds, quotas and allocations are explicitly proposed settings for review and calibration.

Keep those distinctions in generated experiment capsules and future public demonstrations. They are what allow the system's research memory to become more useful over time without turning earlier uncertainty into apparent fact.
