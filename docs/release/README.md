# Releases

A JopeDime release is cut on **xbabe2** by [`deploy/release/release.sh`](../../deploy/release/release.sh), under owner decision D-D (2026-09-27): a fast signed host release.

Releases are published on `github.com/neverhuman/JopeDime` under tags `vX.Y.Z`. Each release is signed with a static cosign key whose files are root-only on xbabe2. [Key custody](#key-custody) describes who can actually use that key. There is no GitHub build-provenance attestation, no Sigstore transparency-log entry, and no Python wheel.

[`release.yml`](../../.github/workflows/release.yml) is **dispatch-only** and is not used. See [Why release.yml is dispatch-only](#why-releaseyml-is-dispatch-only).

## What a release contains

| Asset | Contents |
| --- | --- |
| `jope-vX.Y.Z-x86_64-unknown-linux-gnu` | The `jope` CLI. It is built by `cargo build --release --locked -p jope-cli --bin jope` inside `rust:1.97.1-bookworm`, pinned by digest (`rust@sha256:0e2bcaef…4a97`; glibc 2.36, rustc 1.97.1). |
| `jope-vX.Y.Z.build-receipt.json` | A `jope.product_evaluator_build.v1` receipt from `jope-build-receipt`. It records the binary's sha256, the toolchain, the `NEEDED` libraries, the sha256 of the commit's `Cargo.toml` and `Cargo.lock`, and the result of the glibc and GPU bounds checks. Its `git` field is `null` because the build reads a `git archive` export; the manifest names the commit. |
| `jope-vX.Y.Z.spdx.json`, `jope-vX.Y.Z.cdx.json` | SBOMs of the committed source tree (the verified export of the commit), produced by syft 1.40.0 in SPDX JSON and CycloneDX JSON. |
| `RELEASE-NOTES-vX.Y.Z.md` | The `## [X.Y.Z]` section of the committed `CHANGELOG.md`. The changelog is generated by git-cliff 2.14.1 from `cliff.toml` in the release PR. |
| `release-manifest-vX.Y.Z.json` | A `jope.release-manifest/v1` record. It holds the tag, the git commit, the crate version, the builder image digest, the glibc ceiling and the observed maximum, the hashes of the model and dataset manifests, and the sha256 of every asset listed above. |
| `SHA256SUMS-vX.Y.Z.txt` | The sha256 of every asset except itself and the signature. |
| `SHA256SUMS-vX.Y.Z.txt.sig` | The cosign signature over `SHA256SUMS-vX.Y.Z.txt`, made with the JopeDime release key. |

Model bundles and datasets are not release assets. The manifest refers to them only by hash.

## Verify a release

You need `gh` (or the web UI), cosign 2.x (releases are made with v2.4.3), coreutils, `jq`, `git` and binutils (`objdump`). Replace `/path/to/JopeDime` with your checkout of the repository.

1. Download the release into a directory you own. On shared hosts, do not use `/tmp`.

   ```sh
   TAG=v0.2.0
   D=$HOME/jope-release-$TAG
   gh release download "$TAG" -R neverhuman/JopeDime -D "$D"
   cd "$D"
   ```

2. Take the public key from the repository at the tag, and check its fingerprint.

   ```sh
   git -C /path/to/JopeDime fetch origin tag "$TAG"
   git -C /path/to/JopeDime show "$TAG:docs/release/signing.pub" > signing.pub
   sha256sum signing.pub
   ```

   The output must be exactly:

   ```text
   de84945ec5326877d202d0738e655492a8b2c3b794873a2eb248939c4d326e4e  signing.pub
   ```

3. Check the signature over SHA256SUMS.

   ```sh
   TUF_ROOT="$D/.tuf" cosign verify-blob --key signing.pub --insecure-ignore-tlog=true \
     --signature "SHA256SUMS-$TAG.txt.sig" "SHA256SUMS-$TAG.txt"
   ```

   The last line of the output must be `Verified OK`.

4. Check every asset against the signed sums. Every line must say `OK`.

   ```sh
   sha256sum -c --strict "SHA256SUMS-$TAG.txt"
   ```

5. Check that the manifest names the tag's commit. The two commit hashes must be equal.

   ```sh
   jq -r '.tag, .git_sha, .crate_version' "release-manifest-$TAG.json"
   git -C /path/to/JopeDime rev-parse "$TAG^{commit}"
   ```

6. Check the binary.

   ```sh
   B=jope-$TAG-x86_64-unknown-linux-gnu
   objdump -T "$B" | grep -oE 'GLIBC_[0-9]+(\.[0-9]+)+' | sort -Vu | tail -n1
   objdump -p "$B" | grep NEEDED
   chmod +x "$B" && "./$B"
   ```

   - The glibc line must be `GLIBC_2.36` or lower. The binary is built for Debian bookworm.
   - The `NEEDED` list must not include `libcuda*`, `libcudart*`, `libnvidia*`, `libtorch*`, `libc10*` or any other CUDA library.
   - The first line printed by the binary must be `jope X.Y.Z`.

About `--insecure-ignore-tlog=true` in step 3:

- The release key is a static key. Signatures are deliberately not uploaded to the public Rekor transparency log, because the repository is private and the signer is a single host.
- cosign therefore prints `WARNING: Skipping tlog verification is an insecure practice…`. That warning is expected.
- Without the flag, cosign tries to fetch the Sigstore TUF root and then fails.
- Setting `TUF_ROOT` keeps cosign's cache inside the download directory.

A negative check shows that verification actually tests something:

```sh
cp "SHA256SUMS-$TAG.txt" tampered.txt && printf x >> tampered.txt
TUF_ROOT="$D/.tuf" cosign verify-blob --key signing.pub --insecure-ignore-tlog=true \
  --signature "SHA256SUMS-$TAG.txt.sig" tampered.txt
```

This must fail with `invalid signature`.

## Key custody

- **Key.** The key is a cosign ECDSA P-256 key pair from `cosign generate-key-pair`. The private key is encrypted with a random password.
- **Where it lives.** It lives on xbabe2 only, in `/etc/jope-release/`:
  - the directory is `0700 root:root`;
  - `signing.key` and `signing.password` are `0600 root:root`;
  - `signing.pub` is `0644`.
- **Never uploaded.** The private key and its password are:
  - not a GitHub Actions secret;
  - not in any repository, working tree or evidence directory;
  - never under `/tmp`.
- **Signing.**
  - `release.sh` signs on xbabe2 through `sudo -n`.
  - The password is read by root's shell and passed only in cosign's environment. It never appears in an argument list, in the calling shell's environment, or in a log.
  - `~/.local/bin/cosign` is owned and writable by `ubuntu`. Root therefore does not run it in place:
    1. root copies it into a new directory under `/root`, which only root can enter (`/run` is mounted `noexec` on xbabe2);
    2. root checks the copy's sha256 against the digest pinned in `release.sh` (cosign v2.4.3, `caaad125acef1cb81d58dcdc454a1e429d09a750d1e9e2b3ed1aed8964454708`);
    3. root runs only that copy, then removes it.

    A replaced or upgraded cosign is refused before it sees the password. Changing the pin is a reviewed change to `release.sh`.
  - cosign writes the signature root-owned with mode `0600`. The script then changes its owner back to the operator and sets mode `0644`.
- **Public key.** The public key is [`docs/release/signing.pub`](signing.pub). Its sha256 is `de84945ec5326877d202d0738e655492a8b2c3b794873a2eb248939c4d326e4e`. `release.sh` refuses to run unless all three of these are true:
  - the committed key has exactly this fingerprint;
  - it is byte-identical to `/etc/jope-release/signing.pub`;
  - a fresh signature verifies against it.
- **Custody receipt.** The key was generated on 2026-09-28. The receipt is on xbabe2 in `~/jope-evidence/release-v0.2.0/custody/`. It contains `key-custody-stat.txt` and `signing.pub.sha256`, plus a sign/verify self-test with a tampered-copy negative. It does not contain the key.
- **The real trust boundary: anyone who can act as `ubuntu` on xbabe2.**
  - The files are root-only, but that is not the boundary. On xbabe2 the `ubuntu` account has passwordless sudo: `sudo -n -l` shows `(ALL) NOPASSWD: ALL` (checked 2026-09-28). `ubuntu` is also in the `docker` group, which is root-equivalent.
  - So every process running as `ubuntu` can read `signing.key` and `signing.password`, or sign directly, without a prompt and without `release.sh`. That includes every agent session on the host (Claude, Codex, Grok) and anything they start.
  - The cosign pin guards against a replaced or upgraded binary. It is not a boundary against someone who can already run `sudo`.
  - The same holds for the Cargo cache that release runs of one tag share (`~/jope-evidence/release-vX.Y.Z/target/`). `release.sh` refuses a cargo home that holds anything besides cargo's own caches, such as a `config.toml` or credentials. The cache contents themselves are trusted to the same degree as the `ubuntu` account.
  - Narrowing this boundary is an owner decision, and none is recorded yet. It would take a sudoers rule that lets `ubuntu` run only a root-owned signing command, not `ALL`.
- **What a valid signature means.**
  - It means that `SHA256SUMS` was signed with this key by someone who could act as `ubuntu` or root on xbabe2.
  - In practice, the signed files came from a `release.sh` run, but only to the extent that every process running as `ubuntu` on xbabe2 is trusted.
  - It is not a Sigstore keyless identity, a transparency-log entry, or a SLSA provenance attestation.
- **Rotation.**
  1. Generate a new pair in `/etc/jope-release/` by the same procedure.
  2. In one reviewed PR, commit the new `signing.pub` and update both this fingerprint and `PUBKEY_SHA256` in `release.sh`.
  3. Old releases stay verifiable with the key committed at their own tag (`git show <tag>:docs/release/signing.pub`).
  4. If the key may be compromised, record that here and in `MASTER_PLAN.md`, rotate, and list the tags it signed.

  An offline backup of the key and a rotation schedule are owner decisions, and none is recorded yet. Losing the key does not invalidate releases already published. The next release then needs a new key.

## Cutting a release (operator)

The release PR must first merge to `main`. It carries `docs/release/signing.pub` and:

- bumps the release version: the `[workspace.package]` version in `Cargo.toml` and the explicit versions of `jope-engine` and `jope-campaigns`, then regenerates `Cargo.lock` with `cargo update --workspace --offline`. `release.sh` compares `jope-cli` and every product crate with the tag through `cargo metadata`; the vendored smartcluster crates keep their own versions. `python/pyproject.toml` is not part of a release while no wheel ships;
- updates the `jope X.Y.Z` lines in `README.md`;
- commits `CHANGELOG.md`, generated with git-cliff 2.14.1 from `cliff.toml` and curated by PR.

Then, on xbabe2, from a clean registered worktree whose `HEAD` is that merge commit:

```sh
deploy/release/release.sh vX.Y.Z <merge-sha>             # dry run: build, sign, verify; no tag, no release
deploy/release/release.sh vX.Y.Z <merge-sha> --publish   # repeats every check, then tags, releases and reads back
```

### Guards

The script refuses to run, and exits non-zero with a message, if any of these holds:

- the host is not xbabe2 (an exact match on the short host name, so `xbabe20` is refused);
- it is not run from the repository root;
- the tree has changes or untracked files;
- an index entry is marked assume-unchanged or skip-worktree (`git status` cannot see edits to such a file);
- `HEAD` differs from the given SHA;
- the given SHA differs from `origin/main` after a fresh fetch;
- the tag is not `vMAJOR.MINOR.PATCH`;
- the workspace version (from `cargo metadata --locked`) differs from the tag;
- the tag already exists, locally or on GitHub;
- `rust-toolchain.toml` does not match the pinned builder;
- `CHANGELOG.md` has no section for the version;
- the signing key or public key does not match custody;
- the evidence directory already holds a run;
- `~/.local/bin/cosign` does not match the pinned sha256;
- with `--publish`: the tagger is not the writer identity, or a GitHub release of that name already exists.

### What is built

The build never reads the working tree:

1. The script exports the merge commit with `git archive <sha> | tar -x -m` into the run's `src/`.
2. It checks the export against `git ls-tree -r <sha>`: the same paths, the same blob ids (hashed without filters) and the same modes, with nothing extra, not even an empty directory. It refuses submodules.
3. The builder, `jope-build-receipt`, `cargo metadata` and syft all read that export, which is mounted read-only at `/src`.
4. After the build and the SBOM, and before signing, the export is checked against the commit again.

So no file in the checkout that `git status` does not show can reach a release: not an ignored `.cargo/config.toml`, a file listed in `.git/info/exclude`, or an edit hidden by assume-unchanged or skip-worktree. The guards also refuse assume-unchanged and skip-worktree entries outright. The shared Cargo cache is a separate input, trusted as described in [Key custody](#key-custody).

- `tar -m` gives the files the extraction time. Without it, the shared Cargo target directory could keep stale workspace crates from an earlier build.
- A git archive export has no `.git`, so the receipt's `git` field is `null`. The binding to the commit comes from `source-export.json` and from the receipt's `Cargo.toml` and `Cargo.lock` hashes, which are checked against the commit.
- Each run gets its own `HOME`. The shared cargo home must hold only cargo's own caches (`registry/`, `git/` and its lock and tracking files). Anything else, such as `config.toml`, `credentials.toml` or `bin/`, is refused.

### What the run does

1. Exports and verifies the commit (see [What is built](#what-is-built)), builds in the pinned image, then checks the binary:
   - the glibc ceiling, from `objdump -T`;
   - that no GPU library appears in `NEEDED`;
   - the version line, both on the host and inside the bookworm image.
2. Runs `jope-build-receipt`.
3. Writes the SBOMs, then re-checks the export, then writes the notes, the manifest and `SHA256SUMS`.
4. Signs as root, with the pinned cosign copy.
5. Verifies the result: the signature, a tampered-copy negative, `sha256sum -c`, and the manifest binding. The tampered-copy negative counts only if the untouched file verifies and the copy fails with `invalid signature`. A missing file fails it.

With `--publish`, after all of that has passed, the script:

1. re-checks freshness;
2. creates an annotated tag `vX.Y.Z` on the merge commit and pushes it (through `gh-role writer`);
3. reads the tag back with `ls-remote`;
4. creates the GitHub release with every file in `dist/`;
5. reads the release back into `readback/` and records every check in `readback.json`:
   - it reads the tag from origin again, and requires the pushed tag object and its peel to the merge commit;
   - it downloads the assets and checks the asset set against `dist/` byte for byte, the signature, the tampered-copy negative, `sha256sum -c` and the manifest;
   - it runs the downloaded binary only if the asset-set, signature and `sha256sum -c` checks all passed, which makes it byte-identical to the binary that was already checked. Otherwise the binary is not executed, and the check is recorded as failed.

If anything fails after the tag is pushed, the script prints the exact manual recovery steps. It never deletes or moves a tag.

### Evidence

Each run writes to `~/jope-evidence/release-vX.Y.Z/<dryrun|publish>-<UTC stamp>/`. The directory holds:

- `release.log`;
- `dist/`;
- `source-export.json`, which records the commit, its tree and the entry count of the verified export;
- `builder/`, `checks/`, `receipt/` and `verify/`;
- `home/`, which is the build's `HOME`;
- for a publish run, `readback/` and `readback.json`;
- `run.json`.

The directory is sealed by a closing `SHA256SUMS`. The seal leaves out:

- `src/`, the verified export. It can be reproduced with `git archive <sha>`.
- the `tmp/` and `tuf/` caches.

The Cargo target directory is shared per tag at `~/jope-evidence/release-vX.Y.Z/target/`. That directory is a cache, not evidence. To force a cold build, move it aside; do not delete evidence to do so.

Nothing is written under `/tmp`. Before anything else runs, the script sets `TMPDIR` to `~/jope-evidence/release-tmp/` (created `0700`), and to the run's `tmp/` once the run directory exists.

## Why release.yml is dispatch-only

[`.github/workflows/release.yml`](../../.github/workflows/release.yml) was written for hosted runners, and it has **never run**: the repository had no tags, no releases and no `release.yml` runs when this path was chosen. It cannot be the release path today, for these reasons:

- **Hosted runner and attestation.**
  - It was written to run on `ubuntu-24.04` and to request `id-token: write` and `attestations: write` for `actions/attest-build-provenance`. Build-provenance attestation is not available to this private repository on its current plan, and D-D drops it.
  - The repository also has no Actions secrets and no environments, so the workflow would have no signing key.
- **The self-hosted fleet refuses it.**
  - The runner admission hook admits only `full-main.yml` and `main-guard.yml` in the `main` domain, and only `ci.yml` in the `pr` domain. Any other job is killed.
  - The runner containers have no Docker, so they cannot do the `rust:1.97.1-bookworm` container build that holds the glibc 2.36 bound.
- **The wheel.** It builds and publishes a Python wheel whose smoke test would fail: `import jope` pulls in `numpy` and `torch`, but the wheel is installed with `--no-deps`. D-D ships no wheel.
- **It would race `release.sh`.** `release.sh` pushes the `vX.Y.Z` tag. With the old `push: tags: ["v*"]` trigger, that push would start a second, unsigned release attempt on hosted runners, racing to `gh release create` the same tag. The trigger is therefore removed and only `workflow_dispatch` is kept.

The workflow stays in the tree as a reference until the self-hosted release lane lands. That lane needs:

- a bookworm release runner image;
- release-domain admission in the ported runner hook;
- the repository-held signature.

Until then, do not dispatch it. It fails closed if it is dispatched anyway: its first step prints the dispatch-only notice and exits 1, so no later step runs, and the job holds only `contents: read`.
