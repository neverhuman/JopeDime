# Releases

The model-inclusive `jopedime` appliance is specified in
[`deploy/appliance/`](../../deploy/appliance/README.md), with an
[implementation checklist](../../deploy/appliance/IMPLEMENTATION_CHECKLIST.md) and
[amendments](../../deploy/appliance/AMENDMENTS.md). Its CPU build, packaging, release-stage
signing message, sealing and independent verification are implemented and exercised in CI;
release-host integration, the neural profile and publication are pending, and no `jopedime`
package has been published. A sealed package is signed by the same key as this release
(`signing.pub`). The procedure below describes the currently implemented `jope` release.

A JopeDime release is cut on **xbabe2** by [`deploy/release/release.sh`](../../deploy/release/release.sh), under owner decision D-D (2026-09-27): a fast signed host release.

Releases are published on `github.com/neverhuman/JopeDime` under tags `vX.Y.Z`. Each release is signed with a static cosign key whose files are root-only on xbabe2. [Key custody](#key-custody) describes who can actually use that key. There is no GitHub build-provenance attestation, no Sigstore transparency-log entry, and no Python wheel.

[`release.yml`](../../.github/workflows/release.yml) is **dispatch-only** and is not used. See [Why release.yml is dispatch-only](#why-releaseyml-is-dispatch-only).

## What a release contains

| Asset | Contents |
| --- | --- |
| `jope-vX.Y.Z-x86_64-unknown-linux-gnu` | The `jope` CLI. It is built by `cargo build --release --locked -p jope-cli --bin jope` inside `rust:1.97.1-bookworm`, pinned by digest (`rust@sha256:0e2bcaef…4a97`; glibc 2.36, rustc 1.97.1). |
| `jope-vX.Y.Z.build-receipt.json` | A `jope.product_evaluator_build.v1` receipt from `jope-build-receipt`. It records the binary's sha256, the toolchain, the `NEEDED` libraries, the sha256 of the commit's `Cargo.toml` and `Cargo.lock`, and the result of the glibc and GPU bounds checks. Its `git` field is `null` because the build reads a `git archive` export; the manifest names the commit. |
| `jope-vX.Y.Z.spdx.json`, `jope-vX.Y.Z.cdx.json` | SBOMs of the committed source tree (the verified export of the commit), produced in SPDX JSON and CycloneDX JSON by syft 1.40.0, which is pinned by sha256 (see [Tools](#tools)). Each SBOM names `syft` 1.40.0 as the tool that made it. |
| `RELEASE-NOTES-vX.Y.Z.md` | The `## [X.Y.Z]` section of the committed `CHANGELOG.md`. The changelog is generated by git-cliff 2.14.1 from `cliff.toml` in the release PR. |
| `release-manifest-vX.Y.Z.json` | A `jope.release-manifest/v1` record. It holds the tag, the git commit, the crate version, the builder image digest, the pinned versions and sha256 of syft and cosign, the glibc ceiling and the observed maximum, the hashes of the model and dataset manifests, and the sha256 of every asset listed above. |
| `SHA256SUMS-vX.Y.Z.txt` | The sha256 of every asset except itself and the signature. |
| `SHA256SUMS-vX.Y.Z.txt.sig` | The cosign signature over `SHA256SUMS-vX.Y.Z.txt`, made with the JopeDime release key. |

Model bundles and datasets are not release assets. The manifest refers to them only by hash.

## Verify a release

You need `gh` (or the web UI), cosign 2.x (releases are made with v2.4.3), coreutils, `jq`, `git` and binutils (`objdump`). Replace `/path/to/JopeDime` with your checkout of the repository.

1. Download the release into a directory you own. On shared hosts, do not use `/tmp`.

   ```sh
   TAG=v0.3.0
   D=$HOME/jope-release-$TAG
   gh release download "$TAG" -R neverhuman/JopeDime -D "$D"
   cd "$D"
   ```

2. Take the public key from the repository at the tag, and check its fingerprint.

   ```sh
   git -C /path/to/JopeDime fetch origin tag "$TAG"
   git -C /path/to/JopeDime show "$TAG:docs/release/signing.pub" > signing.pub
   sha256sum signing.pub
   ```

   The output must be exactly:

   ```text
   de84945ec5326877d202d0738e655492a8b2c3b794873a2eb248939c4d326e4e  signing.pub
   ```

3. Check the signature over SHA256SUMS.

   ```sh
   TUF_ROOT="$D/.tuf" cosign verify-blob --key signing.pub --insecure-ignore-tlog=true \
     --signature "SHA256SUMS-$TAG.txt.sig" "SHA256SUMS-$TAG.txt"
   ```

   The last line of the output must be `Verified OK`.

4. Check every asset against the signed sums. Every line must say `OK`.

   ```sh
   sha256sum -c --strict "SHA256SUMS-$TAG.txt"
   ```

5. Check that the manifest names the tag's commit. The two commit hashes must be equal.

   ```sh
   jq -r '.tag, .git_sha, .crate_version' "release-manifest-$TAG.json"
   git -C /path/to/JopeDime rev-parse "$TAG^{commit}"
   ```

6. Check the binary.

   ```sh
   B=jope-$TAG-x86_64-unknown-linux-gnu
   objdump -T "$B" | grep -oE 'GLIBC_[0-9]+(\.[0-9]+)+' | sort -Vu | tail -n1
   objdump -p "$B" | grep NEEDED
   chmod +x "$B" && "./$B"
   ```

   - The glibc line must be `GLIBC_2.36` or lower. The binary is built for Debian bookworm.
   - The `NEEDED` list must not include `libcuda*`, `libcudart*`, `libnvidia*`, `libtorch*`, `libc10*` or any other CUDA library.
   - The first line printed by the binary must be `jope X.Y.Z`.

About `--insecure-ignore-tlog=true` in step 3:

- The release key is a static key. Signatures are deliberately not uploaded to the public Rekor transparency log, because the repository is private and the signer is a single host.
- cosign therefore prints `WARNING: Skipping tlog verification is an insecure practice…`. That warning is expected.
- Without the flag, cosign tries to fetch the Sigstore TUF root and then fails.
- Setting `TUF_ROOT` keeps cosign's cache inside the download directory.

A negative check shows that verification actually tests something:

```sh
cp "SHA256SUMS-$TAG.txt" tampered.txt && printf x >> tampered.txt
TUF_ROOT="$D/.tuf" cosign verify-blob --key signing.pub --insecure-ignore-tlog=true \
  --signature "SHA256SUMS-$TAG.txt.sig" tampered.txt
```

This must fail with `invalid signature`.

## Key custody

- **Key.** The key is a cosign ECDSA P-256 key pair from `cosign generate-key-pair`. The private key is encrypted with a random password.
- **Where it lives.** It lives on xbabe2 only, in `/etc/jope-release/`:
  - the directory is `0700 root:root`;
  - `signing.key` and `signing.password` are `0600 root:root`;
  - `signing.pub` is `0644`.
- **Never uploaded.** The private key and its password are:
  - not a GitHub Actions secret;
  - not in any repository, working tree or evidence directory;
  - never under `/tmp`.
- **Signing.**
  - `release.sh` signs on xbabe2 through `sudo -n`.
  - The password is read by root's shell and passed only in cosign's environment. It never appears in an argument list, in the calling shell's environment, or in a log.
  - `~/.local/bin/cosign` is owned and writable by `ubuntu`. Root therefore does not run it in place:
    1. root copies it into a new directory under `/root`, which only root can enter (`/run` is mounted `noexec` on xbabe2);
    2. root checks the copy's sha256 against the digest pinned in `release.sh` (cosign v2.4.3, `caaad125acef1cb81d58dcdc454a1e429d09a750d1e9e2b3ed1aed8964454708`);
    3. root runs only that copy, with its `TMPDIR` inside that directory ([Temporary files](#temporary-files)), then removes the directory.

    A replaced or upgraded cosign is refused before it sees the password. Changing the pin is a reviewed change to `release.sh`.
  - cosign writes the signature root-owned with mode `0600`. The script then changes its owner back to the operator and sets mode `0644`.
- **Public key.** The public key is [`docs/release/signing.pub`](signing.pub). Its sha256 is `de84945ec5326877d202d0738e655492a8b2c3b794873a2eb248939c4d326e4e`. `release.sh` refuses to run unless all three of these are true:
  - the committed key has exactly this fingerprint;
  - it is byte-identical to `/etc/jope-release/signing.pub`;
  - a fresh signature verifies against it.
- **Custody receipt.** The key was generated on 2026-09-28. The receipt is on xbabe2 in `~/jope-evidence/release-v0.2.0/custody/`. It contains `key-custody-stat.txt` and `signing.pub.sha256`, plus a sign/verify self-test with a tampered-copy negative. It does not contain the key.
- **The real trust boundary: anyone who can act as `ubuntu` on xbabe2.**
  - The files are root-only, but that is not the boundary. On xbabe2 the `ubuntu` account has passwordless sudo: `sudo -n -l` shows `(ALL) NOPASSWD: ALL` (checked 2026-09-28). `ubuntu` is also in the `docker` group, which is root-equivalent.
  - So every process running as `ubuntu` can read `signing.key` and `signing.password`, or sign directly, without a prompt and without `release.sh`. That includes every agent session on the host (Claude, Codex, Grok) and anything they start.
  - The cosign pin guards against a replaced or upgraded binary. It is not a boundary against someone who can already run `sudo`.
  - The same holds for the Cargo cache that release runs of one tag share (`~/jope-evidence/release-vX.Y.Z/target/`). `release.sh` refuses a cargo home that holds anything besides cargo's own caches, such as a `config.toml` or credentials. The cache contents themselves are trusted to the same degree as the `ubuntu` account.
  - Narrowing this boundary is an owner decision, and none is recorded yet. It would take a sudoers rule that lets `ubuntu` run only a root-owned signing command, not `ALL`.
- **What a valid signature means.**
  - It means that `SHA256SUMS` was signed with this key by someone who could act as `ubuntu` or root on xbabe2.
  - In practice, the signed files came from a `release.sh` run, but only to the extent that every process running as `ubuntu` on xbabe2 is trusted.
  - It is not a Sigstore keyless identity, a transparency-log entry, or a SLSA provenance attestation.
- **Rotation.**
  1. Generate a new pair in `/etc/jope-release/` by the same procedure.
  2. In one reviewed PR, commit the new `signing.pub` and update both this fingerprint and `PUBKEY_SHA256` in `release.sh`.
  3. Old releases stay verifiable with the key committed at their own tag (`git show <tag>:docs/release/signing.pub`).
  4. If the key may be compromised, record that here and in `MASTER_PLAN.md`, rotate, and list the tags it signed.

  An offline backup of the key and a rotation schedule are owner decisions, and none is recorded yet. Losing the key does not invalidate releases already published. The next release then needs a new key.

## Cutting a release (operator)

The release PR must first merge to `main`. It carries `docs/release/signing.pub` and:

- bumps the release version: the `[workspace.package]` version in `Cargo.toml` and the explicit versions of `jope-engine` and `jope-campaigns`, then regenerates `Cargo.lock` with `cargo update --workspace --offline`. `release.sh` compares `jope-cli` and every product crate with the tag through `cargo metadata`; the vendored smartcluster crates keep their own versions. The Lambda workspaces under `deploy/lambda/` have locks of their own that pin the root crates they take by path, and each such lock and its `deploy/lambda/SNAPSHOT.json` record move with the version. `just bump X.Y.Z` does all of this (`deploy/release/bump.sh`), checks the result as `release.sh` and the hygiene lane do, and lists the lines of `README.md` and this file that still name the old version. It needs a git checkout and runs cargo `--offline`, so each Lambda workspace's dependencies must already be in the cargo cache (`cargo fetch --locked --manifest-path <workspace>/Cargo.toml`; `deploy/ci/lambda.sh` also fills it); it refuses with that command when they are not. `python/pyproject.toml` is not part of a release while no wheel ships;
- updates the `jope X.Y.Z` lines in `README.md`;
- commits `CHANGELOG.md`, generated with git-cliff 2.14.1 from `cliff.toml` and curated by PR.

Then, on xbabe2, from a clean registered worktree whose `HEAD` is that merge commit:

```sh
deploy/release/release.sh vX.Y.Z <merge-sha>             # dry run: build, sign, verify; no tag, no release
deploy/release/release.sh vX.Y.Z <merge-sha> --publish   # repeats every check, then tags, releases and reads back
```

Run the script as shown. Its `#!` line is `#!/bin/bash -p`: it starts the system bash by absolute path, so no `PATH` lookup chooses the interpreter, and in privileged mode. `bash -p deploy/release/release.sh` is accepted too when that `bash` is the root-owned system one; preflight checks the running interpreter like a host tool (see [Tools](#tools)). A plain `bash deploy/release/release.sh` is refused (see [Tool configuration](#tool-configuration)).

### Guards

The script refuses to run, and exits non-zero with a message, if any of these holds:

- bash was not started in privileged mode (`bash -p`, which the script's `#!` line runs), or `SHELLOPTS` is exported (see [Tool configuration](#tool-configuration));
- the host is not xbabe2 (an exact match on the short host name, so `xbabe20` is refused);
- it is not run from the repository root;
- the tree has changes or untracked files;
- an index entry is marked assume-unchanged or skip-worktree (`git status` cannot see edits to such a file);
- `HEAD` differs from the given SHA;
- the given SHA differs from `origin/main` after a fresh fetch;
- the tag is not `vMAJOR.MINOR.PATCH`;
- the workspace version (from `cargo metadata --locked`) differs from the tag;
- the tag already exists, locally or on GitHub;
- `rust-toolchain.toml` does not match the pinned builder;
- `CHANGELOG.md` has no section for the version;
- the signing key or public key does not match custody;
- the evidence directory already holds a run;
- `~/.local/bin/cosign` or `~/.local/bin/syft` does not have its pinned sha256, or does not report its pinned version (see [Tools](#tools));
- a host tool that the script runs, looked up in the fixed system `PATH` (`/usr/sbin:/usr/bin:/sbin:/bin`, never the operator's), is not a root-owned file reached only through root-owned directories and symlinks that neither group nor others can write, or the bash running the script is not (see [Tools](#tools));
- the repository's own git config sets a key that could send the fetch, the tag checks or the push to a server other than GitHub: a URL rewrite (`url.*.insteadOf`, `url.*.pushInsteadOf`), a remote named after the release URL or any other URL (`remote.<URL>.*`: git looks a URL on its command line up as a remote name first, so that remote's `url` would send the fetch, the tag checks and the push to another repository, and its `pushurl` the push alone), or a TLS setting (`http.*sslVerify`, `http.*sslCAInfo`, `http.*sslCAPath`). Remotes with other names, such as `origin`, are allowed, because the script gives git the URL, never a remote name;
- a tool's private configuration directory is not empty (see [Tool configuration](#tool-configuration));
- with `--publish`: the tagger is not the writer identity, or a GitHub release of that name already exists. git takes the tagger from `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`, or else from `user.name` and `user.email` in the repository's own config; `~/.gitconfig` is not read. When none of these sets an email, git falls back to the `EMAIL` variable. `check_publish_ready` reads the identity git resolves (`git var GIT_COMMITTER_IDENT`) and compares its email with the writer identity's, so a tagger from any of these sources is refused unless it is the writer.

All of these are checked before anything is exported, built or signed.

### What is built

Every release build, binary-check and receipt container has a fixed **4 CPU**, **20 GiB RAM**
budget, no additional swap allowance, and `CARGO_BUILD_JOBS=4`. These bounds apply inside Docker,
so the daemon cannot turn a capped host launcher into an unrestricted Cargo build. Containers
carry `ai.jopedime.release.tag` and `ai.jopedime.release.run` labels; operators can inspect the
actual limits and monitor only this run without interfering with other fleet jobs. Admit the run
under the current fleet CPU/RAM controls and pause only its labelled containers if host pressure
exceeds those controls.

The build never reads the working tree:

1. The script exports the merge commit with `git archive <sha> | tar -x -m` into the run's `src/`.
2. It checks the export against `git ls-tree -r <sha>`: the same paths, the same blob ids (hashed without filters) and the same modes, with nothing extra, not even an empty directory. It refuses submodules.
3. The builder, `jope-build-receipt`, `cargo metadata` and syft all read that export, which is mounted read-only at `/src`.
4. After the build and the SBOM, and before signing, the export is checked against the commit again.

So no file in the checkout that `git status` does not show can reach a release: not an ignored `.cargo/config.toml`, a file listed in `.git/info/exclude`, or an edit hidden by assume-unchanged or skip-worktree. The guards also refuse assume-unchanged and skip-worktree entries outright. The shared Cargo cache is a separate input, trusted as described in [Key custody](#key-custody).

- `tar -m` gives the files the extraction time. Without it, the shared Cargo target directory could keep stale workspace crates from an earlier build.
- A git archive export has no `.git`, so the receipt's `git` field is `null`. The binding to the commit comes from `source-export.json` and from the receipt's `Cargo.toml` and `Cargo.lock` hashes, which are checked against the commit.
- Each run gets its own `HOME`. The shared cargo home must hold only cargo's own caches (`registry/`, `git/` and its lock and tracking files). Anything else, such as `config.toml`, `credentials.toml` or `bin/`, is refused.

### Tools

Every command that shapes a release or its checks is pinned, checked as a host tool, or run inside the pinned builder image, with two named exceptions: the host `cargo` and `gh-role`. No pinned or host tool reads per-user configuration that could change what it reports to a check or writes into a release (see [Tool configuration](#tool-configuration)).

- **Pinned: syft and cosign.** Both live in `~/.local/bin`, which `ubuntu` can write. `release.sh` pins each one by sha256 and by the version it reports:

  | Tool | Version | sha256 |
  | --- | --- | --- |
  | syft | 1.40.0 | `eb9714fb8e4b8f2a647e7bb312f1e0b9f83a7aa30418658bf46583cfa83d27d2` |
  | cosign | v2.4.3 | `caaad125acef1cb81d58dcdc454a1e429d09a750d1e9e2b3ed1aed8964454708` |

  - Preflight refuses a binary with any other digest without running it. It then refuses one whose `syft version -o json` or `cosign version --json` reports any other version.
  - The scan runs only a copy of syft in the run's `tmp/syft/`. The copy is checked again, digest and version, just before the scan.
  - syft runs with an empty environment. Its `TMPDIR`, `HOME`, XDG directories and cache all lie under `~/jope-evidence/release-tmp/syft-preflight/` for the version check in preflight, and under the run's `tmp/syft/` for the copy's check and the scan. It reads only the configuration file that the script writes (`sbom/syft.yaml`), not `~/.syft.yaml` or a `.syft.yaml` in the export. Neither the operator's configuration nor an earlier run's cache can change the SBOMs.
  - Both SBOMs must name syft 1.40.0 as the tool that made them.
  - cosign's digest is checked again before each verification on the host. Root checks its own copy before it signs (see [Key custody](#key-custody)).
  - On the host, cosign runs with an empty environment, like syft: `PATH`, `TMPDIR`, a `HOME` that is an empty private directory, and for verification a `TUF_ROOT` in the run directory.
  - The release manifest records both versions and digests. Upgrading either tool is a reviewed change to `SYFT_VERSION` and `SYFT_SHA256`, or `COSIGN_VERSION` and `COSIGN_SHA256`, in `release.sh`.
- **Host tools: every other command the script runs by name on the host, as the operator or as root through `sudo`.** These are `git`, `jq`, `objdump`, `tar`, `find`, `grep`, `sed`, `diff`, `sudo`, `docker`, `sh`, `dpkg-query`, and `sha256sum`, `mktemp` and the rest of coreutils (`HOST_TOOLS` in `release.sh`). They come from the host's packages: Ubuntu's, and Docker's apt repository for `docker`. They are not pinned by digest:
  - security updates replace them routinely, so a digest pin would stop every release after each update;
  - only root can replace them, and root is already inside the trust boundary (see [Key custody](#key-custody)).

  Instead:
  - **A fixed `PATH`.** Before it runs any command, the script sets `PATH` to `TRUSTED_PATH`, `/usr/sbin:/usr/bin:/sbin:/bin`, and makes it read-only. The operator's `PATH`, whose first entry is `~/.local/bin`, is never searched, so a copy there is never found, let alone run, and nothing later in the run can put a directory in front. `/usr/local` is left out: no host tool lives there, the host's packages never install there, and on xbabe2 `/usr/local/bin` holds root-owned symlinks into `~/.local/bin`.
  - **Every step of the way.** Preflight walks each tool's path from `/` down, without following a link unchecked: every directory and the file itself must be root-owned and closed to group and other writes, and every symlink must be root-owned, with its target walked the same way. A directory that the operator owns anywhere on the way refuses the tool, even when a symlink in it leads only to root-owned directories, because the operator could swap that symlink after the check.
  - **Trusted helpers.** The walk runs `/usr/bin/stat` and `/usr/bin/readlink` by absolute path, after bash builtins alone have shown that the operator cannot write them or any directory above them. A `stat` that the operator puts first on some `PATH` cannot vouch for anything.
  - **The same file later.** A lookup of each name must return the file just checked. The commands root runs through `sudo` (`test`, `cat`, `chown`, `chmod` and `sh`) are given those absolute paths, because `sudo` would otherwise search its own `secure_path`, `/usr/local` first, and the sign script sets root's `PATH` to the same fixed value before its `mktemp`, `mkdir`, `cp`, `chmod`, `sha256sum`, `cat` and `rm`.
  - **bash.** The running interpreter is walked the same way, so `bash -p deploy/release/release.sh` with a bash other than the system one is refused.

  Each run records every host tool's path, resolved file, sha256, package and package version in `tools.json`.
- **The builder.** `cargo`, `rustc`, `ldd` and `jope-build-receipt` run inside the `rust:1.97.1-bookworm` image, which is pinned by digest.
- **The two exceptions.** Both are run by absolute path from `~/.local/bin`, which `ubuntu` can write, never looked up, and both read the operator's own configuration:
  - **The host `cargo`** (the rustup shim) runs only `cargo metadata --no-deps` in preflight, on the checkout. It decides nothing on its own: the builder runs `cargo metadata` again inside the pinned image, on the verified export, and the run stops unless that answer is also right.
  - **`gh-role`** (publish only) is the host's credential router. It hands `git` the GitHub token and runs `gh release view`, `create` and `download` as the writer role. It is trusted as part of the `ubuntu` account, and it cannot change what was signed: it uploads `dist/`, which is signed before it runs, and the readback compares the downloaded assets with `dist/` byte for byte and verifies the signature again.

#### Tool configuration

No per-user file and no variable of the operator's may change what a pinned or host tool reports to a check or writes into a release. `release.sh` removes or replaces each one that could before `main` runs, so every command it starts inherits that. It never writes the operator's own files. The audit, on xbabe2:

| Tool | Configuration it would read | What `release.sh` does |
| --- | --- | --- |
| `jq` 1.7 | `~/.jq` (and `~/jq/main.jq`), loaded into every program. A definition there changes what a program means: a `~/.jq` that redefines `startswith` and `any` made the SBOM check accept a file that is not SPDX, and one could as well change the signed manifest or the version check. `JQ_*` variables. | Every `jq` runs with `HOME` set to `jq-home/`, an empty private directory in the current `TMPDIR`; anything found there stops the run. `JQ_*` is unset. |
| `git` 2.43 | `/etc/gitconfig` and `~/.gitconfig`. On xbabe2 `~/.gitconfig` rewrites the GitHub URLs of other repositories to the local forge, so one more line would send the fetch, the tag checks and the push somewhere else. `~/.config/git/ignore` and `~/.config/git/attributes`, read even without `~/.gitconfig`. Replace refs, which make `git archive`, `ls-tree` and `cat-file` show another commit's tree under the released SHA. `GIT_*` variables. The repository's own config. | `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_NO_REPLACE_OBJECTS=1`. Through `GIT_CONFIG_COUNT`, which outranks every configuration file: `core.excludesFile` and `core.attributesFile` are `/dev/null`, `core.hooksPath` is `/dev/null` (no repository hook runs), `core.fsmonitor` is `false`, `tag.gpgSign` is `false` and `push.followTags` is `false` (with it, the tag push would also send every other local annotated tag in the commit's history that GitHub lacks; the push passes `--no-follow-tags` as well). Every other `GIT_*` variable is unset, except `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL`. Preflight refuses URL rewrites, remotes named after a URL, and TLS settings in the repository's config (see [Guards](#guards)). The GitHub credential helper is passed with `git -c`, which outranks all of this, so the fetch and the push still authenticate as the writer role. |
| `tar` 1.35 | `TAR_OPTIONS`: `--exclude=...` there drops files from the export. | Unset. |
| `objdump` 2.42 | `GNUTARGET`: `GNUTARGET=binary` hides every `NEEDED` entry. | Unset. |
| `grep` 3.11 | Nothing: `GREP_OPTIONS` has been ignored since grep 3.6, and colours apply only with `--color`. | `GREP_OPTIONS` is unset anyway. |
| `sed` 4.9, `find` and coreutils (`sha256sum`, `sort`, `head`, `tail`, `stat`, `cp`, `install`, `ls` and the rest) | No configuration file. `POSIXLY_CORRECT` changes how GNU tools, and `bash`, behave. | `POSIXLY_CORRECT` is unset. `LC_ALL=C` and `TMPDIR` are set, and `date` always runs with `-u`. |
| Every dynamically linked host tool | `LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT` and the other `LD_*` variables, `GCONV_PATH`, `LOCPATH` and `GLIBC_TUNABLES`, which load or tune code from a path of the operator's choosing. | Unset. So are `SSL_CERT_FILE`, `SSL_CERT_DIR` and `CURL_CA_BUNDLE`: `git`'s TLS trust stays the system's. |
| `dpkg-query` | `DPKG_ADMINDIR` and `DPKG_ROOT`. They could only change the package versions recorded in `tools.json`. | `DPKG_*` is unset. |
| `docker` CLI 29 | `~/.docker/config.json`: a current context chooses the daemon, `proxies` are added to every container's environment, and credential helpers and plugin hooks run. `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_DEFAULT_PLATFORM` and the other `DOCKER_*` variables. | Every `docker` runs with `DOCKER_CONFIG` set to `docker-config/`, an empty private directory in the run's `TMPDIR`, and `DOCKER_HOST=unix:///var/run/docker.sock`. Every other `DOCKER_*` variable is unset. The daemon's own configuration belongs to root, and the image is pinned by digest. |
| cosign v2.4.3 | `COSIGN_*`, `SIGSTORE_*`, token and `TUF_ROOT` variables, and `~/.sigstore`. | On the host it runs with an empty environment (see [Tools](#tools)). Root's copy runs under `sudo`, which resets the environment. |
| syft 1.40.0 | `~/.syft.yaml`, its XDG configuration, `SYFT_*` variables, and a `.syft.yaml` in the scanned directory. | It runs with an empty environment and reads only the configuration file the script writes (see [Tools](#tools)). |
| `sudo` | `/etc/sudoers`, which belongs to root. | Nothing: `sudo` resets the environment. |
| `bash` 5.2 | Before the script's first line, a bash started without `-p` imports exported functions (`export -f`), runs a `BASH_ENV` file, and applies `SHELLOPTS` and `BASHOPTS`; it also reads `CDPATH` and `GLOBIGNORE`. An imported function stands in for the command or the builtin of its name: a `git` function can hide an untracked file from `git status`, an `unset` function can keep every variable in this table, and a `command` function can hand `jq` a hostile `~/.jq`. `SHELLOPTS=noexec` runs nothing and exits 0. `BASHOPTS=nocasematch` makes `[[ ]]` accept an uppercase SHA. Even `bash -p` reads `BASH_COMPAT` (another bash version's semantics, such as a quoted `=~` operand read as a pattern), `TMOUT` (a timeout on every `read`, which ends a loop over a tool's output at the first pause in it, such as the release notes read from `git cat-file` or the export's file list read from `find`), `FUNCNEST` (a nesting limit, which stops the run wherever that depth is first reached), `GLOBSORT` (bash 5.3's glob order) and the locale. | The `#!` line starts `/bin/bash -p` (privileged mode) by absolute path. It imports no function, and it ignores `BASH_ENV`, `SHELLOPTS`, `BASHOPTS`, `CDPATH` and `GLOBIGNORE`. The first lines refuse any bash that is not privileged, and an exported `SHELLOPTS`, because a bash started without `-p` takes privileged mode from it. They test with keywords only, and no function can stand in for a keyword. `main` is guarded by the same test, so a function standing in for `exit` cannot carry a run past the refusal. `BASH_COMPAT`, `TMOUT`, `FUNCNEST` and `GLOBSORT` are unset and `LC_ALL=C` is set before anything is checked. `BASH_ENV` is unset too, so that no child bash runs it. |

What remains, and why it cannot change a result:

- `git` still reads the repository's own configuration, `.git/info/attributes` and `.git/info/exclude`. They belong to the checkout. The keys that could change a result are forced or refused as above. Attributes cannot change the export unnoticed, because the export is compared with the commit's tree blob by blob (see [What is built](#what-is-built)). An exclude rule, or a key such as `core.fileMode`, can hide a working-tree change from the clean-tree guard, but the build reads only the verified export, never the working tree.
- `git`'s HTTP library reads `~/.netrc`, and a credential-store helper reads `~/.git-credentials`. These choose only which account authenticates, not what the fetch, `ls-remote` or the push see: TLS verifies github.com, and git compares object ids. The store helper is configured in `~/.gitconfig`, which is not read, and the GitHub helper list is reset with `git -c`. xbabe2 has no `~/.netrc`.
- The host `cargo` and `gh-role` are the two exceptions described in [Tools](#tools).
- A bash started without `-p` is refused by the script's first lines, and they cannot refuse what happens before they run. With `SHELLOPTS=noexec`, such a bash reads the script, runs no line of it and exits 0: nothing is checked, built, signed or published, and nothing reports a pass. A `BASH_ENV` file runs in the script's own shell before its first line and can do anything there, including turning the privileged flag on. Both are the operator's own shell set-up, and like the rest of the `ubuntu` account they are inside the trust boundary (see [Key custody](#key-custody)). Run the script as shown, and take a run's result from its `DRY RUN passed` or `PUBLISHED` line and its sealed evidence directory, not from the exit status alone.
- Exported functions stay in the environment of the commands the script runs, because bash cannot unset a variable whose name is not an identifier. Only a bash imports them, and no host tool is a bash script: on xbabe2 every one is an ELF binary, and `sh` is dash, which imports no functions (checked 2026-09-29).

### What the run does

1. Exports and verifies the commit (see [What is built](#what-is-built)), builds in the pinned image, then checks the binary:
   - the glibc ceiling, from `objdump -T`;
   - that no GPU library appears in `NEEDED`;
   - the version line, both on the host and inside the bookworm image.
2. Runs `jope-build-receipt`.
3. Writes the SBOMs with the checked copy of syft, then re-checks the export, then writes the notes, the manifest and `SHA256SUMS`.
4. Signs as root, with the pinned cosign copy.
5. Verifies the result: the signature, a tampered-copy negative, `sha256sum -c`, and the manifest binding. The tampered-copy negative counts only if the untouched file verifies and the copy fails with `invalid signature`. A missing file fails it.

With `--publish`, after all of that has passed, the script:

1. re-checks freshness;
2. creates an annotated tag `vX.Y.Z` on the merge commit and pushes that tag and no other ref (`--no-follow-tags`, through `gh-role writer`);
3. reads the tag back with `ls-remote`;
4. creates the GitHub release with every file in `dist/`;
5. reads the release back into `readback/` and records every check in `readback.json`:
   - it reads the tag from origin again, and requires the pushed tag object and its peel to the merge commit;
   - it downloads the assets and checks the asset set against `dist/` byte for byte, the signature, the tampered-copy negative, `sha256sum -c` and the manifest;
   - it runs the downloaded binary only if the asset-set, signature and `sha256sum -c` checks all passed, which makes it byte-identical to the binary that was already checked. Otherwise the binary is not executed, and the check is recorded as failed.

If anything fails after the tag is pushed, the script prints the exact manual recovery steps. It never deletes or moves a tag.

### Evidence

Each run writes to `~/jope-evidence/release-vX.Y.Z/<dryrun|publish>-<UTC stamp>/`. The directory holds:

- `release.log`;
- `dist/`;
- `source-export.json`, which records the commit, its tree and the entry count of the verified export;
- `tools.json`, which records the pinned tools with the versions they reported, and every host tool's path, sha256 and package version (see [Tools](#tools));
- `builder/`, `checks/`, `receipt/`, `sbom/` (syft's configuration file and version report) and `verify/`;
- `home/`, which is the build's `HOME`;
- for a publish run, `readback/` and `readback.json`;
- `run.json`.

The directory is sealed by a closing `SHA256SUMS`. The seal leaves out:

- `src/`, the verified export. It can be reproduced with `git archive <sha>`.
- the `tmp/` and `tuf/` caches. `tmp/` is the run's `TMPDIR`, created `0700`. It also holds the containers' temporary directory, `tmp/container/`, syft's home and cache, `tmp/syft/`, and the empty configuration directories of jq, docker and cosign (see [Tool configuration](#tool-configuration)). Empty directories in it are removed when the run ends.

The Cargo target directory is shared per tag at `~/jope-evidence/release-vX.Y.Z/target/`. That directory is a cache, not evidence. To force a cold build, move it aside; do not delete evidence to do so.

### Temporary files

Nothing is written under `/tmp`, on the host or in a container. The script names the temporary directory at every process boundary, because none of them passes the host's `TMPDIR` on by itself:

| Boundary | How `TMPDIR` crosses it |
| --- | --- |
| The script and the host commands it runs (git, tar, jq, gh-role and the rest) | Before anything else runs, the script exports `TMPDIR` as `~/jope-evidence/release-tmp/` (created `0700`), and as the run's `tmp/` (also `0700`) once the run directory exists. |
| Every `docker run` (the build, `cargo metadata`, the receipt, and the binary run inside bookworm) | Docker passes a container no variable that is not named with `-e`, and the image's `/tmp` is its own. Every container is started by one function, which bind-mounts the run's `tmp/container/` (`0700`) at `/release-tmp`, sets `TMPDIR=/release-tmp`, and mounts the same directory over the container's `/tmp`. The last mount covers glibc's `tmpfile(3)` and any tool that ignores `TMPDIR`. |
| Root's signing shell (`sudo -n sh -c`) | `sudo` resets the environment. Root's shell creates its work directory from an explicit `/root/jope-release-sign.XXXXXX` template, then exports `TMPDIR` as the `0700` `tmp/` inside it before it runs anything else. cosign and every other command there see that `TMPDIR`, and the directory is removed when the shell exits. |
| `sudo -n test`, `cat`, `chown` and `chmod` | These read or change one named file and create no temporary files. |
| The empty-environment runs (`env -i`): the binary's version check, syft and cosign on the host | Each names `TMPDIR`: the current `TMPDIR` for the binary and cosign. For syft it is `~/jope-evidence/release-tmp/syft-preflight/tmp/` for the version check in preflight, and the run's `tmp/syft/tmp/` for the check of the copy and the scan (see [Tools](#tools)). |

`docker pull` and the image store belong to the Docker daemon, a system service outside the run. The image is pinned by digest.

## Why release.yml is dispatch-only

[`.github/workflows/release.yml`](../../.github/workflows/release.yml) was written for hosted runners, and it has **never run**: the repository had no tags, no releases and no `release.yml` runs when this path was chosen. It cannot be the release path today, for these reasons:

- **Hosted runner and attestation.**
  - It was written to run on `ubuntu-24.04` and to request `id-token: write` and `attestations: write` for `actions/attest-build-provenance`. Build-provenance attestation is not available to this private repository on its current plan, and D-D drops it.
  - The repository also has no Actions secrets and no environments, so the workflow would have no signing key.
- **The self-hosted fleet refuses it.**
  - The runner admission hook admits only `full-main.yml` and `main-guard.yml` in the `main` domain, and only `ci.yml` in the `pr` domain. Any other job is killed.
  - The runner containers have no Docker, so they cannot do the `rust:1.97.1-bookworm` container build that holds the glibc 2.36 bound.
- **The wheel.** It builds and publishes a Python wheel whose smoke test would fail: `import jope` pulls in `numpy` and `torch`, but the wheel is installed with `--no-deps`. D-D ships no wheel.
- **It would race `release.sh`.** `release.sh` pushes the `vX.Y.Z` tag. With the old `push: tags: ["v*"]` trigger, that push would start a second, unsigned release attempt on hosted runners, racing to `gh release create` the same tag. The trigger is therefore removed and only `workflow_dispatch` is kept.

The workflow stays in the tree as a reference until the self-hosted release lane lands. That lane needs:

- a bookworm release runner image;
- release-domain admission in the ported runner hook;
- the repository-held signature.

Until then, do not dispatch it. It fails closed if it is dispatched anyway: its first step prints the dispatch-only notice and exits 1, so no later step runs, and the job holds only `contents: read`.
